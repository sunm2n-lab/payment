# S3 — 부분취소 초과 환불 계획

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 선행 계획: [plan/S2.md](S2.md) · 실습 기록: [phase1/S3.md](../phase1/S3.md) · 이슈: #25

## 1. 배경

S1 은 **같은 결제의 승인** 경쟁을, S2 는 **서로 다른 결제가 같은 지갑**을 건드리는 경쟁을 막았다. 취소 경로는 어느 쪽도 적용받지 않았다. `PaymentService.cancel` 은 Phase 0 그대로다.

```java
Payment payment = support.findOwnedPayment(merchantId, paymentKey);     // 잠금 없는 읽기
if (payment.getBalanceAmount() < cancelAmount) throw ...;              // 검사
payment.setBalanceAmount(payment.getBalanceAmount() - cancelAmount);   // 읽은 값으로 계산한 절대값
...
Wallet wallet = support.loadWallet(payment);                           // MONEY: 지갑도 잠금 없이
wallet.setBalance(Amounts.add(wallet.getBalance(), cancelAmount));
```

같은 결제에 동시에 들어온 부분취소는 모두 같은 `balance_amount` 를 읽고 검사를 통과해 서로의 차감을 덮어쓴다. S2 와 같은 Lost Update 이고 대상만 `payment.balance_amount` 다.

MONEY 환불에는 결함이 하나 더 있다. 본선 승인이 지갑을 `FOR UPDATE` 로 잠가도, **환불이 잠그지 않고 읽으면** 같은 지갑의 차감을 덮어쓴다. 락 규칙은 유스케이스가 아니라 **행 단위로** 지켜져야 한다.

## 2. 확정된 설계 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 비교 범위 | **naive + 비관적 락** 둘만 공존 | SCENARIO 155행이 S2-b 결론 적용을 확정했다. 조건부 UPDATE·낙관적 락은 S2 에서 비교를 마쳤으므로 기록에서만 다룬다 |
| 취소 이음매 | `PaymentCanceller` — naive / pessimistic | S1 의 `PaymentConfirmer` 와 같은 방식. 트랜잭션 경계는 구현체 |
| 공통 본문 | `PaymentSupport.cancel(payment, amount, reason, updater)` | `PaymentSupport.approve` 와 같은 방식. 두 구현의 차이가 **결제를 읽는 방식과 updater 조합** 하나로 설명되게 한다 |
| 환불 이음매 | `WalletBalanceUpdater.refund(walletId, paymentId, amount)` | 차감·충전·환불이 한 전략으로 묶여 **같은 행에 서로 다른 잠금 규칙이 조합될 수 없다**. 별도 환불 이음매를 두면 "차감은 비관적, 환불은 naive" 같은 틀린 조합이 가능해진다 |
| 결제 생성의 지갑 조회 | `WalletService.findIdByMemberId` | 잔액을 바꾸지 않으므로 전략이 아니라 조회 책임. `WalletService` 에는 이미 조회(`get`)가 있다 |
| 의존 방향 | `payment` 는 `wallet.infrastructure` / `wallet.domain` 을 import 하지 않는다 | RESTRUCTURE 에서 S3 로 미룬 "환불 서비스 추출"을 끝낸다. Phase 2 지갑 포트의 원형 |
| 마이그레이션 | **없음** | 기존 컬럼만 쓴다 |
| 오류 계약 | 변경 없음. 검사 순서 **상태 → 금액** 유지 | API 계약 보존 |
| 트랜잭션 경계 | 취소 전체가 단일 트랜잭션. 카드 취소 호출도 안 | 분리는 S8 |

## 3. 본선의 잠금 순서

```
1. findOwnershipByPaymentKey      잠그지 않는 스칼라 조회 (id, merchantId). 없으면 404
2. merchantId 불일치 → 404        불변 값이라 락 없이 검사해도 안전하다
3. findByIdForUpdate(id)          PK 레코드 X 락. 엔티티는 여기서 처음 로드한다
4. 상태 → 금액 검사                잠근 뒤의 현재 값으로 검사한다
5. payment_cancel 저장, balance_amount·status 갱신
6. MONEY → updater.refund (wallet FOR UPDATE) / CARD → cardApprovalClient.cancel
```

**바뀌지 않는 사실(존재, 소유 가맹점)은 잠그기 전에, 바뀌는 사실(상태, 잔여 금액)은 잠근 뒤에** 검사한다.

### 3.1 엔티티를 먼저 읽지 않는다

엔티티를 평범하게 읽어 둔 뒤 같은 id 를 `FOR UPDATE` 로 조회하면 영속성 컨텍스트에 이미 있는 엔티티가 그대로 돌아온다. 락은 잡았는데 값은 잠그기 전의 것이 되어 개선이 무효가 된다. S2 의 비관적 충전이 `findIdByMemberId` 로 id 만 찾고 잠근 것과 같은 이유다. 그래서 1단계는 엔티티가 아니라 스칼라(`id`, `merchantId`)를 돌려준다.

### 3.2 `payment_key` 로 바로 잠그지 않는다

`SELECT ... WHERE payment_key = ? FOR UPDATE` 는 키가 없을 때 REPEATABLE READ 에서 unique 인덱스의 **그 키가 들어갈 갭**에 갭 락을 건다. 트랜잭션이 끝날 때까지 **그 갭에 들어오는** 결제 INSERT 가 막힌다. 존재를 확인한 뒤 PK 등치로 잠그면 레코드 락 하나로 끝난다.

전제: **결제를 물리 삭제하는 경로가 없다.** 1단계에서 확인한 행이 3단계에도 있다. 삭제가 생기면 PK 조회도 없는 행을 대상으로 할 수 있다 — 3단계에서 없으면 데이터 불일치로 보고 예상 밖 오류(5xx)로 둔다.

### 3.3 승인과의 경쟁

잠금 순서는 승인과 같은 `payment → wallet` 이다. 같은 결제에서 승인과 취소가 겹치면 **payment 락을 먼저 잡은 쪽이** 결과를 정한다.

- 승인이 CAS 로 먼저 잡고 정상 커밋 → 취소는 대기 후 DONE 을 읽는다 (잠금 읽기는 최신 커밋 값을 읽는다)
- 취소가 먼저 잡음 → READY 를 읽고 `INVALID_PAYMENT_STATUS`. 정상이다
- 승인이 롤백 → 취소는 READY 를 읽는다

이 경쟁의 테스트는 이번 범위가 아니다 (8절).

### 3.4 오류 우선순위

검사 순서는 **상태 → 금액** 이다. 그래서 같은 경쟁이라도 탈락자의 예외가 승자에 따라 다르다.

| 승자 | 탈락자가 읽는 상태 | 탈락자의 예외 |
|---|---|---|
| 7,000 부분취소 (10,000 결제) | PARTIAL_CANCELED, 잔여 3,000 | `CANCEL_AMOUNT_EXCEEDED` |
| 10,000 전액취소 | CANCELED | `INVALID_PAYMENT_STATUS` |

탈락자는 잠근 뒤의 현재 값을 읽었으므로 예외 메시지의 잔여 금액이 사실이다. S2 조건부 감산의 탈락자가 RR 스냅샷 때문에 잔액을 주장할 수 없었던 것(`notEnough`)과 다르다.

## 4. 코드 변경

```
payment.application.cancellation      (신규)
├── PaymentCanceller
├── NaivePaymentCanceller             Phase 0 의 결제 읽기 + 주입받은 updater (재현)
└── PessimisticLockPaymentCanceller   3절의 잠금 순서 + 주입받은 updater (본선)

payment.application.PaymentSupport
  + cancel(payment, cancelAmount, reason, updater)    공통 본문
  + findOwnedPaymentId(merchantId, paymentKey)         1·2단계
  - loadWallet                                         삭제
  - WalletRepository 의존                              삭제

payment.infrastructure.PaymentRepository
  + findOwnershipByPaymentKey → Optional<PaymentOwnership(id, merchantId)>
  + findByIdForUpdate          @Lock(PESSIMISTIC_WRITE)

wallet.application.balance.WalletBalanceUpdater
  + refund(walletId, paymentId, amount)
    naive / pessimistic 은 직접 구현, atomic / guarded / optimistic 은 credit 처럼 naive 에 위임

wallet.application.WalletService
  + findIdByMemberId

bootstrap.config.ConcurrencyStrategyConfig
  + naivePaymentCanceller(support, naiveUpdater)
  + pessimisticPaymentCanceller(support, paymentRepository, pessimisticUpdater)   @Primary
```

`PaymentService.cancel` 은 `PaymentCanceller` 에 위임만 한다. `create` 는 `WalletService.findIdByMemberId` 를 쓴다.

**부수 효과 하나.** `create` 가 `findByMemberId`(`WALLET_READ` 지점) 대신 `findIdByMemberId`(지점 아님)를 탄다. 게이트는 무장 후 워커 스레드에서만 동작하고 결제 생성은 준비 단계라 영향이 없어야 한다 — 전체 테스트로 확인한다.

## 5. 동기화 지점

| 지점 | 종류 | 대상 | 그 시점 보유 락 |
|---|---|---|---|
| `PAYMENT_READ` (기존) | barrier, 반환 직후 | `findByPaymentKey` — naive canceller 의 읽기 | 없음 |
| `PAYMENT_LOCK_ATTEMPT` (신규) | barrier, **호출 직전** | `PaymentRepository.findByIdForUpdate` | 없음 — 선행 조회는 잠그지 않는다 |
| `WALLET_LOCK_ATTEMPT` (기존) | barrier, 호출 직전 | `WalletRepository.findByIdForUpdate` | 경로마다 다르다 (6절 회귀 3) |
| **hold** (신규 방식) | 순서 게이트 | 이름 붙은 지점 하나 | 쓰는 곳마다 명시 |

- `findOwnershipByPaymentKey` 에는 게이트를 걸지 않는다. `findIdByMemberId` 와 같은 취급이다
- **락을 잡은 뒤에는 barrier 에 참가자를 모으지 않는다** (plan/S2.md 4.1)

### 5.1 hold — 순서 게이트

barrier 는 "동시에 출발" 만 보장한다. 재현 2 는 **"A 가 읽음 → B 가 커밋 → A 가 씀"** 이라는 순서가 필요하다.

- `armHold(name)` 으로 무장한다. 그 지점에 **처음 도착한 스레드 하나만** 붙잡고, 나머지 스레드는 그냥 지나간다
- 붙잡힌 스레드는 도착을 알리고 `release(name)` 까지 멈춘다. 상대는 `awaitArrival(name)` 으로 도착을 기다린다
- 10초 상한, 스레드당 1회, 정리 규약의 `reset` 해제 — 기존 규약을 그대로 따른다
- **붙잡힌 쪽이 보유한 락이 상대 경로와 겹치지 않아야 한다.** 겹치면 상대가 DB 락에 막혀 커밋하지 못하고 상한에 걸려 실패한다

## 6. 재현과 회귀

| # | 배선 | 동기화 | 기대 결과 | 불변식 |
|---|---|---|---|---|
| 재현 1 | naive canceller, CARD 10,000 에 7,000 × 2 | `PAYMENT_READ` ×2 | 성공 2, 취소 합계 14,000, `balance_amount` 3,000, 카드사 취소 2회 | 2·3 위반 |
| 재현 2 | naive 취소(P1) + 본선 승인(P2), **같은 지갑·다른 결제** | 환불 워커를 `WALLET_READ` 에서 hold → P2 승인 커밋 → release | 잔액 7,000 (원장 합계 4,000) | 1 위반 |
| 회귀 1 | 본선, CARD 7,000 × 2 | `PAYMENT_LOCK_ATTEMPT` ×2 | 성공 1 / `CancelAmountExceeded` 1, `payment_cancel` 1건, 카드사 취소 1회 | 유지 |
| 회귀 2 | 본선, MONEY 7,000 × 2 (같은 결제) | `PAYMENT_LOCK_ATTEMPT` ×2 | 성공 1, REFUND 원장 1건, 잔액 == 원장 합계 | 유지 |
| 회귀 3 | 본선 취소(P1) + 본선 승인(P2), 같은 지갑 | `WALLET_LOCK_ATTEMPT` ×2 | 잔액 == 원장 합계 == 4,000 | 유지 |
| 회귀 4 | 본선, 전액 10,000 + 부분 7,000 (같은 결제) | `PAYMENT_LOCK_ATTEMPT` ×2 | 성공 1, 탈락자 예외는 3.4 표대로 승자와 짝이 맞는다 | 유지 |

**재현 2 의 수치.** 충전 10,000 → P1(5,000) 승인 → 잔액 5,000. P1 2,000 부분취소와 P2(3,000) 승인을 경쟁시킨다. 환불 워커가 5,000 을 읽고 멈춘 사이 P2 승인이 2,000 을 커밋하고, 풀려난 환불이 5,000 + 2,000 = **7,000** 을 쓴다. 옳은 값은 **4,000** 이다.

- **같은 결제를 쓰지 않는다.** payment 락에서 먼저 직렬화되어 wallet 경쟁이 가려진다
- 두 워커는 `ConcurrentRunner` 안에서 돈다. 워커 0 은 취소, 워커 1 은 `awaitArrival` → 승인 → `release`. 러너의 폭주 워커 점검이 그대로 적용된다
- **hold 가 안전한 이유.** hold 시점에 naive 취소가 보유한 락은 IDENTITY 로 즉시 INSERT 된 `payment_cancel` 행뿐이다. payment 의 UPDATE 는 아직 나가지 않았다 — 지갑 조회가 `em.find` 라 auto-flush 를 일으키지 않는다. P2 승인은 P2 행·wallet·`wallet_ledger` 만 건드리므로 겹치지 않는다. 락 캡처로 확인한다 (6.2)

**회귀 3 시점의 보유 락.** plan/S2.md 4.2 가 "S3 에서 재사용할 때 다시 점검하라" 고 남긴 항목이다. 취소 워커는 P1, 승인 워커는 CAS 로 P2 의 X 락을 들고 있다. 서로 다른 행이라 막지 않는다.

### 6.1 공통 단언

- 탈락 요청: 그 결제의 `payment_cancel` 추가 0건, REFUND 원장 추가 0건, 카드사 취소 호출 추가 0건
- 예상 밖 오류 0건 — 나오는 실패는 3.4 표의 두 예외뿐이다
- 기존 `Invariants` 3개를 그대로 쓴다. 불변식 2(`balance_amount == amount - 취소 합계`)와 3(`취소 합계 <= 승인 금액`)이 재현 1 의 대상이다

### 6.2 락 관측

로컬 docker-compose MySQL 에 `root` 로 붙어 `performance_schema.data_locks` / `data_lock_waits` 로 캡처해 `phase1/S3.md` 에 남긴다.

- 두 번째 취소가 payment **PK 레코드 락**(`LOCK_MODE = X,REC_NOT_GAP`)에서 대기
- `payment → wallet` 순서
- 재현 2 의 hold 시점 보유 락
