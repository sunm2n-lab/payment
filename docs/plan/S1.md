# S1 — 중복 승인 계획

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 선행 계획: [plan/PHASE0.md](PHASE0.md) · 실습 기록: [phase1/S1.md](../phase1/S1.md)

## 1. 배경

Phase 0 은 "정상 케이스에서는 동작하는" naive 구현을 만들었다. S1 은 그 구현을 처음으로 무너뜨린다.

`PaymentService.confirm` 은 READY 인지 확인한 뒤 DONE 으로 바꾼다. 확인은 잠금 없는 `SELECT` 이고 갱신은 flush 시점의 `UPDATE` 다. 두 문장 사이에 원자성이 없으므로, 같은 `paymentKey` 로 동시에 들어온 승인은 모두 READY 를 읽고 모두 성공한다. REPEATABLE READ 와 READ COMMITTED 모두에서 발생하며 격리 수준 전환으로는 해결되지 않는다.

## 2. 확정된 설계 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 해결책 | 조건부 UPDATE (`WHERE status='READY'`) | SCENARIO 124행에서 이미 확정. 검사와 전이를 한 문장으로 원자화한다 |
| 실패 버전 보존 | `PaymentConfirmer` 인터페이스로 naive/CAS 를 **코드에 공존** | `plan/PHASE0.md` 2절의 방침. 과거 실습을 언제든 다시 실행할 수 있어야 한다. S1 이 두 번째 구현이 처음 생기는 단계다 |
| 마이그레이션 | **없음** | CAS 는 기존 컬럼만 쓴다. 과거 스키마 전용 컨테이너도 필요 없고, 재현 테스트가 최신 스키마를 그대로 쓴다 |
| 동기화 장치 | 테스트가 소유한다 (리포지터리 프록시 + 게이트) | 프로덕션 코드에 관측 훅을 심으면 실습 대상인 naive 구현이 원래 모습을 잃는다 |
| 트랜잭션 경계 | 승인 전체가 단일 트랜잭션 | SCENARIO 125행. 경계 분리는 S8 |

## 4. 구현 계획

### 4.1 동시성 테스트 자산 (S2~S10 재사용)

"동시에 시작시키는 것만으로 결과를 보장하지 않는다"(SCENARIO 94행). 필요한 시점을 barrier 로 맞춘다.

- **`ConcurrencyGate`** — 이름 붙은 게이트. `arm` 하기 전에는 no-op 이라 나머지 테스트에 영향이 없다. 대기에 상한을 두어 참가자가 모이지 않으면 멈추는 대신 실패한다
  - **스레드당 한 번만 통과시킨다.** CAS 구현은 성공 후 엔티티를 재조회하므로 같은 리포지터리 메서드를 두 번 호출한다. 두 번째로 barrier 에 걸리면 나머지 참가자가 오지 않아 테스트가 멈춘다
- **`ConcurrencyGateConfig`** — `BeanPostProcessor` 가 `PaymentRepository`/`WalletRepository` 를 JDK 동적 프록시로 감싸 조회 **반환 직후** 게이트를 통과시킨다. `@TestConfiguration` 이라 컴포넌트 스캔에 걸리지 않고, `AbstractIntegrationTest` 가 import 하므로 모든 통합 테스트가 컨텍스트 하나를 계속 공유한다
  - `@MockitoSpyBean` 은 쓰지 않는다. Mockito 의 호출 기록·스텁 동작은 여러 스레드의 동시 호출을 보장하지 않는다. 동기화 장치 자체가 불확실하면 관측 결과를 믿을 수 없다
- **`ConcurrentRunner`** — N 개 작업 동시 시작, 워커별 성공·실패 수집, 타임아웃, executor 종료. 예상한 실패와 예상 밖 오류를 타입으로 구분할 수 있게 한다
- **게이트 해제**는 `AbstractIntegrationTest` 의 정리 규약이 맡는다. 실행 헬퍼에 두면 게이트를 무장한 테스트가 동시 실행에 도달하기 전에 실패했을 때 다음 테스트로 샌다

**워커 수는 5** 다. 게이트에서 대기하는 워커는 이미 커넥션을 점유하므로 `maximum-pool-size` 10 보다 작아야 한다. 아니면 관측하려던 경쟁 대신 커넥션 획득 타임아웃을 보게 된다.

### 4.2 재현

| 결제수단 | 동기화 지점 | 기대 결과 |
|---|---|---|
| CARD | payment 조회 직후 | 승인 5회, 승인번호 5개 발급, DB 에는 1개만 |
| MONEY | payment 조회 직후 + wallet 조회 직후 | 차감 1회, PAY 원장 5건 → **불변식 1 위반** |

재현 테스트는 깨진 결과를 그대로 assert 하므로 **결함이 재현될 때 green** 이다. FK 0건이나 인덱스 부재를 테스트로 고정하는 것과 같은 성격이고, 개선 후에도 naive 구현이 계속 같은 결과를 내는지 확인하는 기록이 된다.

### 4.3 개선

```
application/
  PaymentConfirmer          interface — 트랜잭션 경계를 구현체가 소유한다
  NaivePaymentConfirmer     실패 버전 보존
  CasPaymentConfirmer       @Primary
  PaymentSupport            공통: 소유권 조회, 상태 사전 검사, 값 검사, 승인 본문
  PaymentService            create/cancel/get + confirm 은 기본 구현에 위임
```

두 구현의 차이는 **상태 전이를 어떻게 확정하느냐** 하나뿐이어야 한다. 그래야 재현과 개선의 비교가 그 차이 하나로 설명된다.

**검사 순서: 소유권 → 상태 사전 검사 → orderId/amount → CAS**

사전 검사를 CAS 앞에 남긴다. 없애면 *이미 DONE 인데 요청 값도 틀린* 경우의 응답이 `INVALID_PAYMENT_STATUS` 에서 `PAYMENT_MISMATCH` 로 바뀐다. 기존 오류 우선순위를 보존하려는 것이고, 경쟁의 최종 판정은 CAS 가 한다.

**탈락 판정은 갱신 건수 0 으로만 내린다.** 탈락한 요청은 아무 행도 바꾸지 않았고 RR 스냅샷은 첫 조회 시점에 고정돼 있으므로, 평범한 재조회는 승자가 커밋한 최신 상태가 아니라 여전히 `READY` 를 돌려준다. 그 값으로 메시지를 만들면 거짓말이 된다. **재조회는 CAS 성공 경로 전용**이며 `clearAutomatically` 로 detached 된 엔티티를 대신한다 — 자기 트랜잭션의 변경은 자기에게 보이므로 `IN_PROGRESS` 를 얻는다.

**응답**: 탈락은 409 `INVALID_PAYMENT_STATUS`. 새 에러 코드를 만들지 않는다.

### 4.4 회귀

재현과 **같은 게이트**(payment 조회 직후)를 그대로 쓴다. 잠금 없는 읽기라 개선된 구현에서도 5개가 모두 게이트에 도달하고 그 다음 CAS 에서 하나만 통과한다. 게이트를 CAS 뒤에 두면 참가자가 하나뿐이라 테스트가 멈춘다 (SCENARIO 95행).

**MONEY 의 지갑 게이트는 재현 전용**이다. 개선된 구현에서 탈락한 요청은 지갑을 읽지 않으므로 참가자가 모이지 않는다.

트랜잭션 경계도 함께 고정한다. MONEY 잔액이 부족하면 `IN_PROGRESS` 전이까지 같이 롤백되어 결제는 `READY` 로 남아야 한다. 커밋된 중간 상태를 만드는 것은 S8 의 주제다.

## 5. 작업 순서 (커밋 단위)

1. `test`: 동시성 테스트 자산 + 자산 자체의 검증
2. `test`: 재현 테스트 (CARD / MONEY)
3. `feat`: `PaymentConfirmer` 추출 + CAS. **기본 구현이 바뀌므로 재현 테스트의 naive 빈 고정도 이 커밋에서 함께 한다** — 커밋 단위로 green 을 유지한다
4. `test`: 회귀 테스트 (경쟁 / 롤백 / RR 스냅샷)
5. `docs`: 이 계획과 실습 기록

## 6. 검증

```bash
./gradlew spotlessCheck test
```

**통과 조건**

- naive 구현에서 중복 승인이 결정적으로 재현된다
- CAS 구현에서 동시 5건 중 성공 1건 / 상태 거절 4건 / **예상 밖 오류 0건**, 외부 승인·PAY 원장 각 1건
- 잔액 부족 시 `IN_PROGRESS` 까지 롤백되어 `READY` 유지
- 불변식 3개 유지, 기존 실패 규약 불변
- Phase 0 의 69개를 포함해 전부 green
