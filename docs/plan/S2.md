# S2 — 머니 잔액 동시 차감 계획

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 선행 계획: [plan/S1.md](S1.md) · 실습 기록: [phase1/S2.md](../phase1/S2.md)

## 1. 배경

S1 은 **같은 결제** 한 건의 경쟁을 막았다. 그 조건부 UPDATE 는 `payment` 행 하나를 잠글 뿐이므로, **서로 다른 결제가 같은 지갑**을 건드릴 때는 아무것도 막지 못한다.

`PaymentSupport.approve` 의 MONEY 분기는 여전히 Phase 0 의 절대 규칙 그대로다.

```java
Wallet wallet = loadWallet(payment);
if (wallet.getBalance() < amount) throw new InsufficientBalanceException(...);
wallet.setBalance(wallet.getBalance() - amount);   // 읽은 값으로 계산한 절대값을 쓴다
```

`WalletService.charge` 도 같은 모양(`Amounts.add`)이다. 읽기는 잠금 없는 consistent read 라 둘 다 같은 잔액을 읽고, flush 시점의 `UPDATE wallet SET balance = <절대값>` 이 서로를 덮어쓴다. 전형적인 read-modify-write Lost Update 다.

## 2. 이번 시나리오의 핵심 난점

S1 은 구현이 **둘**(naive / CAS)로 갈라졌다. S2 는 SCENARIO 138~144행이 **비교 실험 4개**를 요구하므로 잔액 변경 전략이 **다섯**으로 갈라진다. 그래서 이 계획의 대부분은 "어떻게 고치느냐"가 아니라 **"다섯 구현을 어떻게 공존시키느냐"** 다.

### 2.1 씨앗을 어디에 두는가

전략이 갈라지는 지점은 `PaymentSupport.approve` 의 MONEY 분기와 `WalletService.charge` 다. 둘 다 "지갑 잔액을 바꾸고 원장을 남긴다" 하나로 묶인다.

```java
public interface WalletBalanceUpdater {
  /** 승인 차감. PAY 원장까지 남긴다. 부족하면 InsufficientBalanceException */
  void debit(Long walletId, Long paymentId, long amount);

  /** 충전. CHARGE 원장까지 남긴다 */
  Wallet credit(Long memberId, long amount);
}
```

차감은 `payment.wallet_id` 를 이미 들고 있어 id 로 받지만, **충전은 `memberId` 로 받는다.** 지갑을 어떻게 찾느냐부터 전략마다 다르기 때문이다(2.2 의 충전 경로 참고). 호출자가 스칼라 id 만 조회해 넘기는 방식도 가능하므로 이것은 강제가 아니라 **설계 선택**이다 — 두 조회 경로를 전략 안에 모아 "어느 전략이 지갑을 어떻게 읽는가"를 한곳에서 읽히게 한다.

호출자가 **엔티티를** 먼저 로드해 넘기는 방식만은 피해야 한다. 그 뒤 `FOR UPDATE` 로 같은 id 를 조회해도 영속성 컨텍스트에 이미 있는 엔티티는 상태가 갱신되지 않아, 락은 잡았는데 값은 잠그기 전의 것이 된다.

| 구현 | 대응 | 방식 |
|---|---|---|
| `NaiveWalletBalanceUpdater` | 실패 버전 보존 | 현재 코드 그대로 (엔티티 더티체킹) |
| `AtomicDecrementWalletBalanceUpdater` | 비교 실험 1 (139행) | 검사 후 `balance = balance - ?` |
| `GuardedDecrementWalletBalanceUpdater` | 비교 실험 2 (140행) | `... AND balance >= ?` |
| `OptimisticLockWalletBalanceUpdater` | S2-a (142행) | `@Version` |
| `PessimisticLockWalletBalanceUpdater` | **S2-b 본선** (144행) | `SELECT ... FOR UPDATE` |

`credit` 이 `Wallet` 을 반환하는 이유는 `WalletController` 가 `WalletResponse.from(walletService.charge(...))` 로 `memberId`·`balance` 를 읽고 `WalletServiceTest` 도 반환값의 잔액을 단언하기 때문이다. void 로 바꾸면 API 와 기존 테스트가 함께 흔들린다.

비교 실험 3개(atomic / guarded / optimistic)는 `credit` 을 naive 에 위임한다. SCENARIO 가 요구하는 충전 경쟁 비교는 **naive ↔ 본선** 두 가지이고, 이 셋은 차감만 관찰 대상이기 때문이다.

### 2.2 조합을 빈으로 등록하는 이유

`@Transactional` 프록시는 컨테이너가 만든다. 손으로 조립한 confirmer 에는 프록시가 없어 트랜잭션 경계가 생기지 않는다. 그래서 **confirmer 의 트랜잭션 프록시를 유지하면서 (confirmer × updater) 조합을 명시하려고** 배선을 설정 클래스로 옮긴다. (updater 자체는 외부 트랜잭션이 있으면 수동 생성 객체도 참여할 수 있다. 빈으로 두는 것은 조합을 한곳에 모으기 위한 선택이다.)

| 빈 이름 | confirmer | updater | 용도 |
|---|---|---|---|
| `naivePaymentConfirmer` | Naive | naive | **S1 재현 (기존 그대로)** |
| `naiveDebitConfirmer` | CAS | naive | S2 재현 — "전제: S1 적용"(134행) |
| `atomicDebitConfirmer` | CAS | atomic | 비교 실험 1 |
| `guardedDebitConfirmer` | CAS | guarded | 비교 실험 2 |
| `optimisticDebitConfirmer` | CAS | optimistic | S2-a |
| `casPaymentConfirmer` **@Primary** | CAS | **pessimistic** | 본선 (커밋 8 이후) |

`PaymentSupport.approve` 는 `WalletBalanceUpdater` 를 **인자로 받는다.** 전략은 호출자가 넘긴다 — 빈 하나가 가변 상태로 전략을 바꾸는 방식은 쓰지 않는다.

충전도 같은 방식으로 빈 두 개다. `walletService`(`@Primary`, pessimistic) / `naiveWalletService`(재현용). 테스트 전용 오버로드를 프로덕션 시그니처에 만들지 않는다.

- 본선 충전: `findIdByMemberId` → `findByIdForUpdate` → 검사·변경
- naive 충전: 기존 `findByMemberId` 그대로 (재현 게이트가 이 경로에 걸린다)

### 2.3 영속성 컨텍스트 — 원자적 UPDATE 가 `IN_PROGRESS` 를 커밋시킬 수 있다

`CasPaymentConfirmer` 는 CAS 뒤 `Payment` 를 재조회하고, `PaymentSupport.approve` 가 **마지막에** 그 엔티티를 DONE 으로 바꾼다.

```java
else { updater.debit(...); }              // ← 여기서 em.clear() 가 일어나면
payment.setStatus(PaymentStatus.DONE);    // inProgress 는 이미 detached
payment.setApprovedAt(LocalDateTime.now());
```

`@Modifying(clearAutomatically = true)` 는 `EntityManager.clear()` 를 부른다. 지갑만 골라서 비울 수 없다. 이걸 지갑 UPDATE 에 복사하면 DONE·`approved_at` 이 유실되는 정도가 아니라 **결제가 `IN_PROGRESS` 상태로 커밋된다.** S1 이 "이 단계에서 DB 에 커밋된 IN_PROGRESS 가 남는 것으로 설명하지 않는다"(SCENARIO 127행)고 못 박은 현상을 S8 보다 여섯 단계 앞서 사고로 만들어 내는 것이다.

더 나쁜 것은 **실험 2 의 기대값(잔액 1,000 / PAY 원장 3건)은 그대로 통과한다**는 점이다. 잔액과 원장만 보면 이 결함이 보이지 않는다.

**방침** — atomic / guarded 는 `Wallet` 엔티티를 **로드하지 않는다.** 스칼라 조회(`findBalanceById`) + native `@Modifying` UPDATE 만 쓰고, 두 옵션 모두 기본값으로 둔다. 근거는 각각 다르다.

- **clear 하지 않는 이유**: 관리 중인 `Payment` 를 살려 둬야 한다. 오래된 `Wallet` 엔티티는 애초에 만들지 않으므로 비울 대상도 없다
- **강제 flush 하지 않는 이유**: 이 UPDATE 앞에 먼저 반영해야 할 미반영 변경이 이 흐름에 없다. `flushAutomatically = false` 는 Spring Data 가 `em.flush()` 를 먼저 부르지 않는다는 뜻일 뿐, Hibernate 의 자동 flush 를 금지하지 않는다 — 두 이야기를 섞지 않는다

pessimistic / optimistic 은 각자 `Wallet` / `VersionedWallet` 을 로드해 더티체킹만 쓴다. native UPDATE 를 섞지 않는다.

**그래서 모든 성공 경로 단언에 `status = DONE` 과 `approved_at IS NOT NULL` 을 넣는다.**

### 2.4 `@Version` 을 `Wallet` 에 붙일 수 없다

`Wallet` 에 `@Version` 을 붙이면 **naive 구현까지 낙관적 락을 갖게 되어 S2 재현이 사라진다.** S1 에서 CAS 를 `@Primary` 로 올리는 순간 재현 테스트가 깨졌던 것과 같은 문제다.

→ `wallet` 테이블을 가리키는 **두 번째 엔티티** `VersionedWallet` 을 만들고 `OptimisticLockWalletBalanceUpdater` 만 쓴다. 기존 `Wallet` 은 `version` 컬럼을 매핑하지 않는다 (`ddl-auto: validate` 는 매핑되지 않은 컬럼을 문제 삼지 않는다).

**대신 보호 범위에 제한이 생긴다.** 다른 전략의 UPDATE 는 `version` 을 올리지 않으므로, 낙관적 락은 **참가자가 모두 optimistic 전략일 때만** 유실을 막는다. 실습 규약으로 고정한다.

- 낙관적 실험은 참가자 전원이 optimistic 전략이다
- 낙관적 실험 중 충전은 **사전 시딩만** 한다 (동시 충전을 섞지 않는다)
- 한 트랜잭션에서 `Wallet` 과 `VersionedWallet` 을 함께 변경하지 않는다

### 2.5 재시도는 트랜잭션 바깥에서

낙관적 락 충돌은 flush/commit 에서 터지고 **트랜잭션 전체가 롤백**된다 (SCENARIO 97행). 그런데 전략은 confirmer 의 트랜잭션 **안**에 있으므로, 재시도는 confirmer **바깥**을 감싸야 한다.

```
RetryingPaymentConfirmer (트랜잭션 없음)  →  optimisticDebitConfirmer (@Transactional)
```

- Spring Retry 를 도입하지 않고 손으로 짠 루프를 쓴다. advice 순서를 확인하는 대신 경계가 눈에 보이게 한다
- 재시도 횟수·지연·상한 초과를 카운터로 노출한다 (143행의 "측정")
- **재시도 대상은 낙관적 충돌로 한정한다.** 잔액 부족은 이 요청의 **업무상 거절**이며, 이번 재시도 정책은 낙관적 충돌 복구에만 적용한다
- `maxAttempts` 는 **최초 호출을 포함**한다
- **S1 의 트랜잭션 경계 결정이 여기서 값을 한다**: 롤백되면 `IN_PROGRESS` 전이도 함께 취소되므로(127행), 재시도는 다시 `READY` 를 보고 CAS 를 정상적으로 통과한다

## 3. 마이그레이션

**V2 하나.** `ALTER TABLE wallet ADD COLUMN version BIGINT NOT NULL DEFAULT 0`

- 다섯 전략 전부 이 컬럼이 있는 상태에서 동작한다. naive/atomic/guarded/pessimistic 은 컬럼을 건드리지 않고, `DEFAULT 0` 이 시드·테스트의 INSERT 를 덮는다
- FK·인덱스는 추가하지 않는다 (S4 / S6 의 실습 대상). `SchemaConstraintTest` 의 `noForeignKeys`/`onlyThreeUniqueIndexes` 는 영향 없음

**SCENARIO 94행과의 관계.** 문서는 "과거 실패 재현은 전용 DB 를 해당 버전으로 초기화하고, 최신 스키마를 공유하지 않는다"고 금지한다. 이번 V2 는 그 예외에 해당한다고 본다 — additive 하고 `DEFAULT` 가 있으며 **기존 엔티티에 매핑되지 않는** 컬럼이라, 재현 경로가 이 컬럼을 읽지도 쓰지도 않는다.

판단으로 끝내지 않고 **검증으로 확인한다**: V2 를 얹는 커밋 이후에도 **S1 재현(CARD/MONEY)과 S2 naive 재현(차감 유실·충전 경쟁)이 모두 green** 이어야 한다. 이 근거로 PR 2 에서 SCENARIO 94행에 좁은 예외를 함께 반영한다. 그러지 않으면 `plan/S2.md` 와 SCENARIO 가 모순된 채로 남는다.

## 4. 동기화 지점 확장

### 4.1 반환 직후 게이트 (기존 방식)

| 메서드 | 게이트 | 이유 |
|---|---|---|
| `PaymentRepository.findByPaymentKey` | `PAYMENT_READ` | 기존 |
| `WalletRepository.findById` | `WALLET_READ` | 기존 |
| `WalletRepository.findByMemberId` | `WALLET_READ` | **충전 경쟁** — naive 충전이 이 경로로 잔액을 읽는다 |
| `WalletRepository.findBalanceById` | `WALLET_READ` | 비교 실험 1 의 "검사" 읽기 |
| `VersionedWalletRepository.findById` | `WALLET_READ` | S2-a |
| `WalletRepository.findIdByMemberId` | **없음** | 잔액을 읽는 시점이 아니다 |
| `WalletRepository.findByIdForUpdate` | **절대 없음** | ↓ |

**`FOR UPDATE` 조회의 반환 직후에는 게이트를 걸면 안 된다.** 먼저 X 락을 잡은 워커가 barrier 에서 대기하는 동안 나머지는 락에 막혀 게이트에 도달하지 못한다 → 테스트가 영영 멈춘다. S1 §4.4 의 "게이트를 CAS 뒤에 두면 참가자가 하나뿐이라 멈춘다"와 같은 종류의 함정이다.

### 4.2 호출 직전 게이트 (신규)

현재 프록시는 **반환 직후**에만 게이트를 쏜다. 여기에 **호출 직전(pre)** 지점을 추가한다.

| 지점 | 시점 | 이유 |
|---|---|---|
| `WalletRepository.findByIdForUpdate` | **호출 직전** `WALLET_LOCK_ATTEMPT` | 승인·충전 두 경로가 **wallet 락을 잡기 전에** 만나는 유일한 공통 지점 |

본선 회귀의 "충전 + 승인 동시" 테스트는 `PAYMENT_READ` 로 맞출 수 없다. **충전은 `PaymentRepository` 를 아예 타지 않으므로** 참가자 2명이면 타임아웃이고 1명이면 경쟁을 보장하지 못한다.

**보장 범위를 정확히 적는다.** `WALLET_LOCK_ATTEMPT` 가 보장하는 것은 **참가자 누구도 아직 wallet 락을 획득하지 않았다**는 것뿐이다. 승인 워커는 그 시점에 이미 S1 CAS 로 **payment 의 X 락을 보유**하고 있다. 이 테스트에서는 충전 워커가 payment 를 건드리지 않고 승인 워커도 한 명이라 서로 막지 않지만, **S3·S4 에서 재사용할 때는 그 시점까지 획득한 락을 다시 점검해야 한다.**

또한 이 게이트는 **DB 락 대기가 실제로 일어났다는 증거가 아니다.** 동시 출발만 보장한다. 잔액 정합성 회귀에는 충분하고, 대기 관계는 `data_locks` / `data_lock_waits` 캡처로 따로 남긴다.

신규 게이트에도 기존 규약(10초 상한, `ConcurrentRunner.verifyNoRunawayWorkers`)이 그대로 적용된다.

## 5. 재현·관찰·회귀

별도 표기가 없으면 지갑 잔액 10,000(충전으로 심는다), 결제 4건 × 3,000, **워커 4개**.

| # | 배선 | 게이트 | 기대 결과 | 불변식 |
|---|---|---|---|---|
| 재현 1 | `naiveDebitConfirmer` | `WALLET_READ` ×4 | 성공 4건, PAY 원장 4건, **잔액 7,000** | 1 위반 (합계 불일치) |
| 재현 2 | naive 충전 1 + 승인 1 | `WALLET_READ` ×2 | 잔액 7,000 또는 15,000 — **12,000 이 아니다** | 1 위반 |
| 실험 1 | `atomicDebitConfirmer` | `WALLET_READ` ×4 | 성공 4건, **잔액 −2,000** | 1 위반 (**합계는 일치, 음수**) |
| 실험 2 | `guardedDebitConfirmer` | `PAYMENT_READ` ×4 | 성공 3 / 부족 1, 잔액 1,000, PAY 원장 3건 | 전부 유지 |
| S2-a | `optimisticDebitConfirmer` + 재시도 | `WALLET_READ` ×4 | 성공 3 / 부족 1, 잔액 1,000, **재시도 ≥ 3** | 전부 유지 |
| 회귀 1 | 본선 (pessimistic) | `PAYMENT_READ` ×4 | 성공 3 / 부족 1, 잔액 1,000, PAY 원장 3건 | 전부 유지 |
| 회귀 2 | 본선 충전 1 + 승인 1 | `WALLET_LOCK_ATTEMPT` ×2 | 잔액 12,000 = 원장 합계 | 전부 유지 |
| 회귀 3 | 본선, 같은 결제 5건 | `PAYMENT_READ` ×5 | **S1 회귀** — 성공 1건 | 전부 유지 |

**실험 1 의 관찰이 이번 시나리오에서 가장 값지다.** 원자적 감산은 차감 유실을 없애서 `balance == SUM(ledger)` 는 지켜지는데, 검사와 감산이 여전히 따로라 **잔액이 −2,000 이 된다.** 불변식 1 의 두 조건 중 하나만 깨지는 것이고, Phase 0 이 `UNSIGNED`/`CHECK` 를 일부러 넣지 않은 이유가 여기서 회수된다.

### 5.1 실패 경로 공통 단언

부족 / 낙관적 충돌 / 재시도 상한 초과 모두에 적용한다.

- 실패한 결제는 `READY` 이고 그 결제의 PAY 원장은 0건
- 성공한 결제는 `DONE` + `approved_at IS NOT NULL` 이고 PAY 원장은 정확히 1건
- 재시도 중 실패한 시도의 잔액·원장 변경이 남지 않는다

### 5.2 탈락 판정에 잔액을 주장하지 않는다

guarded 의 탈락자는 **아무 행도 바꾸지 않았고** RR 스냅샷은 앞선 payment 조회 시점에 고정돼 있다. 이어서 평범하게 SELECT 하면 1,000 이 아니라 **10,000** 이 돌아온다. S1 의 `lostConfirmRace` 와 같은 함정이다.

→ `InsufficientBalanceException.notEnough(walletId, amount)` 팩토리를 추가한다. **잔액을 주장하지 않는다.** 기존 생성자는 실제로 읽은 값을 아는 경로(naive / pessimistic)에 남긴다.

API 계약은 변하지 않는다. `ApiExceptionHandler` 는 409 `INSUFFICIENT_BALANCE` + `ErrorResponse(code, message)` 로 매핑하고 `FailureContractApiTest` 는 상태와 코드만 단언한다. 게다가 API 경로는 본선(pessimistic)이라 지갑을 실제로 읽으므로 기존 생성자를 그대로 쓴다.

### 5.3 재시도 테스트는 둘로 나눈다

`ConcurrencyGate` 는 **스레드당 한 번만** 통과를 막는다(CAS 재조회 때문). 그래서 2차 시도부터는 워커들이 동기화 없이 흩어지고, 상한 초과 여부가 **결정적이지 않다** — 우연히 겹치면 나고 아니면 안 난다. 참가자 수가 라운드마다 줄어(4→3→2) 고정 참가자 `CyclicBarrier` 로 라운드별 재무장을 하기도 어렵다.

| 테스트 | 범위 |
|---|---|
| `OptimisticLockConcurrencyTest` (컨테이너) | 1차 시도 충돌은 게이트가 보장한다 → **충돌 → 전체 롤백 → 재시도 성공**까지. 최종 상태는 성공 3 / 부족 1 |
| `RetryPolicyTest` (컨테이너 없음) | `ObjectOptimisticLockingFailureException` 을 k 번 던지는 통제된 delegate 로 **최대 시도·상한 초과·카운터·지연**을 결정적으로 검증 |

**재시도 예산은 `maxAttempts = 4`(최초 호출 포함)로 잡는다.** 근거: 버전을 올리는 것은 커밋에 성공한 차감뿐이고 잔액 10,000 / 건당 3,000 이면 성공은 최대 3건이다. 따라서 어떤 워커도 최대 3회까지만 충돌할 수 있어 4번째 시도에서 반드시 판정이 난다. 1차 시도는 게이트가 4명을 모으므로 **충돌 3건이 결정적으로 보장**된다 (재시도 카운터 ≥ 3 단언의 근거).

### 5.4 경합 관찰 (SCENARIO 143행)

잔액 부족과 락 충돌을 분리하려고 **충분한 잔액**(회차당 워커 수 × 3,000 을 넘는)으로 실행한다.

- 같은 조건에서 optimistic / pessimistic 두 전략을 N 회차 반복한다
- **회차마다 지갑 잔액과 결제를 새로 준비한다.** 한 번만 시딩하고 반복하면 잔액이 줄어 결국 잔액 부족이 측정에 섞인다
- 시딩·정리 시간은 측정에서 **제외**한다. 경쟁 구간만 계측한다
- 기록: 총 소요, 요청별 지연, 재시도 횟수(회차별 차이 또는 회차 시작 시 초기화), 상한 초과 비율
- **성능 수치에는 단언을 걸지 않는다.** CI 임계값으로 만들면 flaky 해진다. green 조건은 정합성 단언만이다
- 이 조건(워커 N, 단일 지갑)의 관측으로 해석하고 일반적인 우열로 확대하지 않는다

### 5.5 락 관측

S1 과 같이 로컬 docker-compose MySQL 에 `root` 로 붙어 `performance_schema.data_locks` / `data_lock_waits` 로 `wallet` 행의 X 락 보유·대기를 캡처해 `docs/phase1/S2.md` 에 남긴다. 승인이 `payment → wallet` 순서로 잠그는 것도 여기서 확인한다.
