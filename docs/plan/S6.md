# S6 — 인덱스 없는 조건의 락 계획

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 선행 계획: [plan/S5.md](S5.md) · 선행 기록: [phase1/S5.md](../phase1/S5.md) · 이슈: #31

SCENARIO 참조는 S6 절의 **항목명**과 행 번호를 함께 적는다. 행 번호가 어긋나면 항목명으로 찾는다.

## 1. 배경

S5 까지의 잠금은 모두 **unique 인덱스나 PK 의 등치**로 행을 찾았다 — `payment_key`, `payment.id`, `wallet.id`, 멱등키. 그래서 "잠근 것" 과 "찾은 것" 이 같았다. 서로 다른 결제는 서로 다른 행을 잠그므로 만나지 않았다.

S6 은 인덱스가 없는 조건으로 잠그며 읽는다 (SCENARIO S6 "재현", 194행).

```
T1 (가맹점 A)  SELECT ... WHERE merchant_id = A AND order_id = 'order-a-1' FOR UPDATE   결과 1행
T2 (가맹점 B)  SELECT ... WHERE merchant_id = B AND order_id = 'order-b-1' FOR UPDATE   T1 이 끝날 때까지 대기
```

두 요청은 가맹점도 결제도 멱등키도 다르다. 결과는 각각 1행이다. 그런데 InnoDB 는 **조건에 맞은 행**이 아니라 **찾느라 스캔한 인덱스 레코드**를 잠근다. 쓸 인덱스가 없으면 클러스터 인덱스 전체가 스캔 대상이고, REPEATABLE READ 는 조건에 맞지 않은 행의 락도 풀지 않는다 (SCENARIO S6 "원인", 196행). 최종 결과 행 수로 잠금 범위를 판단하면 안 된다.

개선은 SCENARIO 가 정한 순서로 비교한다. 인덱스 없음 → `merchant_id` 단일 인덱스 → `(merchant_id, order_id)` 복합 unique (SCENARIO S6 "개선 비교", 197행). **세 단계에서 SQL 과 서비스 코드는 같고 스키마만 다르다.** S1~S5 는 실패 구현과 개선 구현을 코드에 공존시켰지만, S6 의 실패와 개선은 마이그레이션 버전으로 갈린다.

복합 unique 는 잠금 범위와 함께 **주문 유일성**도 해결한다. 지금은 같은 가맹점이 같은 `orderId` 로 결제를 몇 번이든 만들 수 있다 (SCENARIO 84행이 S6 으로 미룬 제약).

### 1.1 착수 전 확인 — unique 하나로 기존 테스트가 얼마나 깨지는가

계획 전에 임시 worktree 에서 `ALTER TABLE payment ADD UNIQUE KEY uk_payment_merchant_order (merchant_id, order_id)` 만 추가하고 전체 테스트를 돌렸다 (S4 계획 1.1 과 같은 확인). **211개 중 8개 실패.**

| 실패 | 원인 |
|---|---|
| `FkPromotionDeadlockReproductionTest` 3건 (S4 재현 1·2, 대조) | `Duplicate entry '1-order-s4' for key 'payment.uk_payment_merchant_order'` |
| `FkDeadlockRegressionTest` 2건 (S4 회귀 1·2) | 같은 위반, `order-s4r` |
| `WalletLockRegressionTest` 1건 (S2-b 회귀 1) | 같은 위반, `order-s2b` |
| `SchemaConstraintTest` 2건 (payment 인덱스 전제, unique 목록) | 예상된 실패 |

앞의 6건은 모두 **"서로 다른 결제 N건" 을 주문 id 상수 하나로 만드는 테스트**다. 실험이 보려는 것(지갑 경합, FK 락)과 주문 id 는 무관한데, 같은 가맹점이 같은 주문으로 결제를 여러 개 만들고 있었다. 주문 유일성이 없다는 것을 테스트 코드가 먼저 쓰고 있었던 셈이다.

세 가지가 따라 나온다.

- **최신 컨텍스트의 테스트는 결제마다 다른 주문 id 를 써야 한다.** V7 보다 먼저, 별도 커밋으로 고친다 (8절 7번). 바꾸는 것은 준비 데이터뿐이고 단언은 건드리지 않는다
- **과거 컨텍스트(V2·V4)의 재현은 영향이 없다.** 같은 모양으로 주문 id 를 재사용하는 테스트가 거기에도 있지만(`order-s2` 등) unique 가 적용되지 않는 DB 에서 돈다. 고치지 않는다
- **기존 API 계약 테스트는 전부 green 이었다.** unique 가 만드는 계약 변화는 중복 주문 생성(200 → 409) 하나다

### 1.2 착수 전 확인 — 주문 id 형식을 제한하면

지금 생성 요청의 `orderId` 는 `@NotBlank @Size(max = 64)` 만 검사한다. `a/b`, `a b`, `café` 도 유효한 주문 id 다. S6 은 이 값을 **경로 변수와 unique 키**로 쓰기 시작하므로 형식을 먼저 정한다 (2절).

임시 worktree 에서 `CreatePaymentRequest.orderId` 에 규칙만 추가하고 전체 테스트를 두 번 돌렸다.

| 추가한 규칙 | 결과 |
|---|---|
| 문자 집합만 — `[A-Za-z0-9_-]+` | **211개 전부 green** |
| 문자 집합 + 길이 — `[A-Za-z0-9_-]{6,64}` | **211개 중 2개 실패** |

실패한 둘은 `FailureContractApiTest` 의 "다른 가맹점의 승인·취소는 404"(주문 id `owned`, 5자)와 "잔액이 부족하면 409"(`poor`, 4자)다. 준비 단계의 결제 생성이 400 으로 거절돼 `paymentKey` 를 읽지 못했다. 검증 대상과 주문 id 는 무관하다.

- **통과했지만 고쳐야 하는 것이 하나 더 있다.** 같은 클래스의 "금액 0 은 400" 은 주문 id 가 `zero`(4자)다. 길이 규칙이 들어가면 금액이 아니라 주문 id 때문에 400 이 나와도 통과한다. 검증 대상이 금액 하나로 남도록 주문 id 를 규칙 안으로 바꾼다
- 세 주문 id 는 형식 제한 커밋에서 함께 고친다 (8절 3번). 바꾸는 것은 준비 데이터뿐이고 단언은 건드리지 않는다
- 형식 제한이 만드는 계약 변화는 "규칙 밖의 주문 id 로 생성하면 200 → 400" 하나다. **확인한 기존 테스트와 k6 스크립트에서 규칙 밖의 입력은 위 세 개뿐이다.** 테스트가 통과했다는 것이 그런 호출자가 없다는 증명은 아니다 — 로컬 DB 에 남은 데이터는 따로 확인한다 (4.6)
- 서비스를 직접 부르는 테스트(`paymentService.create(...)`)는 요청 DTO 를 거치지 않으므로 이 규칙의 영향을 받지 않는다. 과거 컨텍스트의 재현이 여기에 해당한다

| 트랜잭션 경계 | 취소 전체가 단일 트랜잭션 | 분리는 S8 |
| 본선 오류 계약 | 기존 API 에서 바뀌는 것은 **생성 둘뿐**이다 — 형식 밖 주문 id(200 → 400), 중복 주문(200 → 409). 승인 요청의 `orderId` 에는 형식 제한을 더하지 않는다 | 사전 확인에서 기존 API 계약 테스트의 단언은 그대로였고, 고칠 것은 준비 데이터의 주문 id 뿐이었다 (1.1, 1.2). 승인은 저장된 값과의 일치만 보므로 형식 밖의 값은 지금처럼 409 `PAYMENT_MISMATCH` 다 |

## 3. 단계별 실험

**준비 데이터** (4.5): 가맹점 100 × 가맹점당 CARD DONE 결제 100건 = 10,000건. JDBC batch 로 직접 넣고 `ANALYZE TABLE payment` 를 돌린다. 주문 id 는 `order-{가맹점 순번}-{순번}` 이라 전부 다르고 형식 규칙 안이다.

| 단계 | 스키마 | 재현 | 기대 결과 |
|---|---|---|---|
| 0 | V5 | 같은 가맹점이 같은 `orderId` 로 결제를 **순차로** 두 번 생성 | 2건 생성. 주문 기반 조회·취소는 결과가 2행이라 **500** — 주문 유일성이 없다는 증상 |
| 0' | V5 | `order-1` 로 만든 결제를 `ORDER-1` 로 조회. 이어서 `ORDER-1` 도 만든 뒤 다시 조회 | 앞은 **다른 주문의 결제**가 조회된다. 뒤는 2행이라 500 — 비교 규칙이 대소문자를 무시한다는 증상 (4.2) |
| 1 | V5 (인덱스 없음) | 3.1 의 대기 행렬 | 다른 가맹점·다른 결제가 **전부** 대기. `EXPLAIN` `type=ALL` |
| 2 | V6 (단일 인덱스) | 같은 행렬 | 다른 가맹점은 통과, **같은 가맹점의 다른 주문**은 대기. `type=ref` |
| 3 | 최신 V7 (복합 unique) | 같은 행렬 + 주문 유일성 | 같은 가맹점의 다른 주문도 통과. `type=const`. 중복 주문은 409 |

- **0·0'·1 단계는 처음부터 V5 컨텍스트에, 2 단계는 V6 컨텍스트에 둔다.** V6·V7 을 넣는 커밋에서 빨개지지 않는다 (S4·S5 의 교훈)
- 세 단계의 테스트는 **같은 시나리오 코드**를 쓴다. 베이스 클래스(스키마)와 기대 값만 다르다. 시나리오를 공통 헬퍼로 두고 스키마별 테스트 클래스가 기대를 넘긴다

### 3.1 대기 행렬

선행은 가맹점 A 의 주문 `order-a-1` 을 취소하다가 잠금 읽기 **반환 직후**(`ORDER_LOCKED`, 6절)에 붙잡힌다. 그 상태에서 후속을 하나씩 보낸다.

**키 배치를 고정한다.** 픽스처가 가맹점 id 를 명시해 넣는다. A 의 앞뒤 이웃(A−1, A+1)과 **떨어진** 가맹점 B 가 모두 결제를 갖는다. 새 결제의 `id` 는 AUTO_INCREMENT 라 기존의 어느 `id` 보다 크다. 단일 인덱스의 엔트리 순서는 `(merchant_id, id)` 다.

|---|---|---|---|---|
| 1 | 가맹점 **B** 의 주문 `order-b-1` 취소 (주문 기반) | 대기 | 통과 | 통과 |
| 2 | 가맹점 **A** 의 **다른** 주문 `order-a-2` 취소 (주문 기반) | 대기 | 대기 | 통과 |

| 10 | 가맹점 A 의 주문 `order-a-1` **조회** (`GET`, 비잠금) | 통과 | 통과 | 통과 |
| 11 | 선행 1 + 주문 기반 취소 7건 (모두 다른 가맹점) | 대기자 7 | 대기자 0 | 대기자 0 |

- 표는 **예상**이다. 잠금 모드(`X` / `X,REC_NOT_GAP` / `X,GAP`, supremum)는 계획에서 단정하지 않고 관측으로 확정해 기록한다 (6.1)
- **"대기" 의 판정**: 후속을 보낸 뒤 `LockWaitProbe` 가 `payment` 테이블의 대기자를 확인하고, 선행을 풀어 주면 후속이 성공한다. **"통과" 의 판정**: 선행이 붙잡힌 채로 후속이 끝까지 성공한다
- 10번은 대조군이다. 비잠금 읽기는 스냅샷을 읽으므로 어느 스키마에서도 막히지 않는다. 막히는 것은 잠금 읽기와 쓰기다
- 11번이 SCENARIO 의 "완전 직렬화 여부" 다 (S6 "관찰", 195행). V5 에서 선행이 락을 쥔 동안 나머지 **전원**이 대기하면 완전 직렬화다
- **† 는 키 배치에서 끌어낸 예상이고, 잠긴 갭을 확인한 뒤에만 단언으로 고정한다** (6.2). A−1 의 새 엔트리 `(A−1, 새 id)` 는 A 의 첫 엔트리 **앞의 갭**에 들어가는데, A 의 첫 엔트리에 걸린 next-key 락이 그 갭을 덮는다. A+1 의 새 엔트리는 A+1 의 기존 엔트리들 **뒤**에 들어가므로 A 의 스캔이 잠근 갭(A+1 의 첫 엔트리 앞) 밖이다. 같은 이유로 9번(A 의 새 엔트리는 A 의 마지막 엔트리 뒤)은 대기다
- 각 단계에서 공통 불변식(`balance_amount = amount − 취소 합계`)과 Fake 취소 호출 수 = 성공한 취소 수를 확인한다

## 4. 설계 상세

### 4.1 API

| 메서드 | 경로 | 동작 |
|---|---|---|
| GET | `/v1/payments/orders/{orderId}` | `WHERE merchant_id = ? AND order_id = ?` **비잠금** 조회 |
| POST | `/v1/payments/orders/{orderId}/cancel` | 같은 조건으로 **`FOR UPDATE`** 조회 → 상태·금액 검사 → 취소. 본문과 `Idempotency-Key` 는 기존 취소와 같다 |

- **주문 id 형식.** `[A-Za-z0-9_-]`, 6~64자. 규칙은 한 곳(`OrderIds`)에 두고 생성 요청의 `orderId` 와 두 API 의 경로 변수가 함께 쓴다. 위반은 400 `INVALID_REQUEST` 이고 조회·취소·생성을 실행하지 않는다
  - 토스페이먼츠의 주문번호 규칙 "영문 대소문자, 숫자, 특수문자 `-`, `_` 로 이루어진 6자 이상 64자 이하" 를 그대로 따른다. 주문 조회 경로도 같은 `/v1/payments/orders/{orderId}` 다 ([코어 API](https://docs.tosspayments.com/reference))
  - **최소 길이를 6자로 두는 근거.** 공개 규칙은 나중에 넓히면(6 → 1) 기존 호출자가 깨지지 않지만, 좁히면(1 → 6) 깨진다. 문자 집합을 제한하는 지금이 길이를 함께 정하기에 가장 싸다. 테스트를 고치지 않으려고 1자를 허용하는 것은 공개 규칙의 근거가 되지 못한다
  - **최소 길이가 해 주지 않는 것.** 정합성은 길이와 무관하다 — 잘못된 결제를 고르지 않게 하는 것은 `(merchant_id, order_id)` unique 다. 보안도 아니다 — `000001` 은 6자지만 추측하기 쉽다. 접근 권한은 가맹점 인증과 `merchant_id` 조건이 지킨다
  - 주문 id 는 **가맹점이 발급한다.** 우리는 형식만 검증하고 발급 방식을 정하지 않는다. 테스트와 픽스처는 `order-{…}` 처럼 규칙 안의 값을 쓴다
  - 주문 id 로 **취소**하는 API 는 토스에 없다 (취소는 `paymentKey` 로만). SCENARIO 가 잠금 읽기 실험을 위해 둔 API 다 (S6 "재현", 194행)
  - 규칙 밖의 값이 **경로**로 올 때의 검증은 둘로 나눈다
    - **MVC 가 받은 뒤의 판정**(형식 검증 400, 매핑 순서)은 기존처럼 MockMvc 테스트(`RoutingContractApiTest`)에 둔다
    - **인코딩된 경로**(`a%2Fb`, `a%20b`, `%C3%A9`)는 **내장 Tomcat 에 실제 HTTP 요청**을 보내는 테스트로 확인한다. MockMvc 는 실행 중인 서버 없이 MVC 를 부르므로 컨테이너가 경로를 어떻게 디코딩·거절하는지 보여 주지 못한다 ([MockMvc](https://docs.spring.io/spring-framework/reference/testing/mockmvc.html)). `IdempotencyKeyHeaderServerTest` 와 같은 방식(RANDOM_PORT + 소켓에 요청 바이트를 직접 쓴다)이다. 클라이언트 라이브러리가 경로를 다시 인코딩하지 않게 하기 위해서다
    - 응답이 형식 검증의 400 일지 컨테이너·라우팅 단계의 거절일지는 계획에서 단정하지 않는다. 실측해 고정한다. 어느 쪽이든 조회·취소가 실행되지 않는 것을 확인한다
- 가맹점은 `MerchantContext` 에서 온다. `merchant_id` 가 SQL 조건에 들어가므로 다른 가맹점의 주문은 결과가 없어 **404** 다. 기존 경로처럼 메모리에서 소유를 비교하지 않는다 — S6 의 실습 대상이 이 조건이다 (phase0/README 124행이 남긴 구분)
- 없는 주문은 404 `NOT_FOUND` (신규 예외, 핸들러에 명시)
- 기존 매핑과 겹치지 않는다. `GET /{paymentKey}` 는 세그먼트가 하나, `POST /{paymentKey}/cancel` 은 둘이다. `RoutingContractApiTest` 에 판정 순서를 추가해 고정한다
- V5·V6 에서 주문이 중복이면 결과가 2행이다. 조회는 `Optional` 로 받고 2행은 예외(500)로 둔다. 하나를 골라 응답하면 **잘못된 결제를 취소**할 수 있으므로 고르지 않는다. V7 이후에는 생길 수 없다

### 4.2 스키마

```
V6__payment_merchant_index.sql
  CREATE INDEX idx_payment_merchant_id ON payment (merchant_id);

V7__payment_order_unique.sql
  ALTER TABLE payment
      MODIFY order_id VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
      DROP INDEX idx_payment_merchant_id,
      ADD UNIQUE KEY uk_payment_merchant_order (merchant_id, order_id);
```

- **V7 은 ALTER 한 문장이다.** S5 의 V5 와 같은 이유다 — 문장 하나는 원자적이지만 여러 DDL 을 함께 되돌릴 수는 없다. unique 추가나 문자 집합 변환이 실패하면 단일 인덱스와 collation 이 그대로 남아야 한다 (4.6 에서 확인)
- **단일 인덱스를 남기지 않는다.** 복합 unique 의 선두 컬럼이 `merchant_id` 라 가맹점 검색도 이 인덱스가 받는다
- **collation.** V1 의 테이블은 `DEFAULT CHARSET = utf8mb4` 만 지정해 `utf8mb4_0900_ai_ci` 다. 그대로 unique 를 걸면 대소문자만 다른 주문 id 가 충돌하고, `order-1` 로 만든 결제가 `ORDER-1` 조회에 잡힌다 (0' 단계). S5 의 멱등키 컬럼과 같은 `ascii` / `ascii_bin` 으로 바꾸고 스키마 전제 테스트로 지킨다
- **악센트와 뒤 공백은 collation 이 아니라 형식 규칙이 막는다.** 규칙 밖의 문자는 DB 에 닿기 전에 400 이다. 단 이것은 **새로 들어오는 입력**에 대한 보장이다
- **`ascii_bin` 은 뒤 공백을 무시하고 비교한다** (PAD SPACE, [CHAR 와 VARCHAR](https://dev.mysql.com/doc/refman/8.0/en/char.html)). 형식 제한 전에 저장된 `'x '` 가 남아 있으면 유효한 입력 `x` 가 그 결제를 고른다. 그래서 형식 밖의 기존 데이터는 V7 **전에** 없애야 하고, V7 은 그것을 대신 막아 주지 않는다 (4.6)
- collation 변경은 V5·V6 의 대기 행렬 결과에 영향을 주지 않는다. 준비 데이터의 주문 id 가 전부 소문자·ASCII 이고 서로 다르다
- 엔티티 매핑은 바뀌지 않는다. 컬럼도 테이블도 늘지 않으므로 과거 컨텍스트의 `ddl-auto: validate` 는 계속 유지한다 (5절)
- `SchemaConstraintTest` 의 "payment 에는 검색 인덱스가 없다" 는 **V5 컨텍스트 전제 테스트로 옮긴다.** 최신 쪽은 "payment 의 인덱스는 PK, `uk_payment_payment_key`, `uk_payment_merchant_order` 뿐" 으로 바꾼다

### 4.3 주문 기반 취소와 조율자

```
OrderLockingPaymentCanceller.cancel(merchantId, orderId, cancelAmount, reason)     @Transactional
  payment = findByMerchantIdAndOrderIdForUpdate(merchantId, orderId)   없으면 404
  support.cancel(payment, cancelAmount, reason, pessimisticUpdater)     S3 의 취소 본문 그대로
```

- 잠금 읽기가 이 결제의 **첫 로드**다. 앞에서 엔티티를 읽어 두지 않으므로 S3 의 "락은 잡았는데 값은 잠그기 전" 함정이 없다
- 구현은 하나다. 실패 버전과 개선 버전이 코드로 갈리지 않으므로 전략 인터페이스를 새로 만들지 않는다. 빈 등록은 `ConcurrencyStrategyConfig` 에 둔다 (`@Transactional` 프록시)
- **SQL 을 고정한다.** `@Lock(PESSIMISTIC_WRITE)` + JPQL 이 실제로 내보내는 문장을 로그로 확인해 기록하고, `EXPLAIN` 은 **그 문장 그대로**에 건다 (SCENARIO 99행)
- **조율자는 취소 실행을 인자로 받게 바꾼다.** 지금 `IdempotentCancelCoordinator` 는 `PaymentService.cancel(paymentKey…)` 에 묶여 있다. 선점·저장·재생은 그대로 두고 "무엇을 실행하는가" 와 "요청 hash" 만 호출자가 넘긴다. 먼저 동작 무변화 refactor 로 분리한다 — 기존 S5 회귀가 수정 없이 green
- 키 INSERT 가 잠금 읽기보다 **먼저** 나간다 (S5 의 insert-first). 선점의 짧은 대기 상한은 INSERT 직후 복원되므로, payment 스캔의 대기에는 기본 50초가 적용된다 (S5 회귀 9')

### 4.4 생성의 중복 주문

| 상황 | V5·V6 | V7 |
|---|---|---|
| 같은 가맹점, 같은 `orderId` 순차 생성 | 2건 | 두 번째 409 `DUPLICATE_ORDER` |
| 같은 가맹점, 같은 `orderId` 동시 생성 2건 | 2건 | 성공 1, 409 1, 결제 1건 |
| 다른 가맹점이 같은 `orderId` | 각자 생성 | 각자 생성 |
| 대소문자만 다른 `orderId` | 각자 생성되지만 조회·취소가 둘을 구분하지 못한다 (0' 단계) | 각자 생성. 조회·취소가 **정확한 결제**를 고른다 (4.2) |
| 형식 밖의 `orderId` (악센트, 뒤 공백, `/`, 5자, 65자) | 400 | 400 |

- 형식 검사는 코드의 규칙이라 스키마와 무관하게 같다. 경계는 6자·64자 허용, 5자·65자 거절이다
- 중복의 판정은 `MySqlLockErrors.isDuplicateKey(e, "uk_payment_merchant_order")` 로만 한다. `uk_payment_payment_key` 위반(UUID 충돌)은 번역하지 않고 500 이다
- `Payment` 는 IDENTITY 라 `save` 가 곧 INSERT 다. 위반은 `save` 호출 지점에서 난다
- 동시 생성에서 후속 INSERT 는 선행의 커밋을 기다렸다가 1062 를 받는다. 선행이 롤백하고 대기자가 둘 이상이면 S5 5.6 의 데드락 모양이 여기서도 가능하다. 재현하지 않고 기록에 남긴다
- **재전송 응답은 이번 범위가 아니다.** 같은 내용이든 다른 내용이든 409 다. 종료 점검에서 "같은 내용이면 기존 결제로 응답" 을 얹는다

### 4.5 실행 계획을 결정적으로 만든다

잠금 범위는 옵티마이저가 고른 실행 계획을 따른다. 인덱스가 있어도 옵티마이저가 풀스캔을 고르면 V6 의 결과는 V5 와 같아진다.

- **데이터 분포.** 시드 가맹점은 둘뿐이다. 가맹점 둘에 결제를 반씩 넣으면 `merchant_id` 의 선택도가 50% 라 옵티마이저가 인덱스를 버릴 수 있다. 가맹점 100 × 100건으로 선택도를 1% 로 만든다
- **통계.** InnoDB 의 통계 자동 갱신은 비동기다. 대량 INSERT 직후의 계획은 통계가 갱신됐는지에 달려 있다. 준비 끝에 `ANALYZE TABLE payment` 를 돌린다
- **`EXPLAIN` 을 단언한다.** 대기 행렬을 보기 전에 `type` / `key` 를 먼저 확인한다 — V5 `ALL` / `NULL`, V6 `ref` / `idx_payment_merchant_id`, V7 `const` / `uk_payment_merchant_order`. 계획이 기대와 다르면 대기 결과를 해석하지 않고 실패한다
- 준비는 API 가 아니라 JDBC batch 로 넣는다. 10,000건을 테스트마다 HTTP 로 만들지 않는다. 추가 가맹점 98곳도 같은 픽스처가 넣는다

### 4.6 V7 적용 전 데이터 정리

V7 이 기대대로 동작하려면 대상 데이터가 세 조건을 만족해야 한다 (SCENARIO S6 "개선 비교", 197행). **V7 이 스스로 걸러 주는 것은 그중 둘뿐이다.**

| 데이터 | V7 의 ALTER | 남는 문제 |
|---|---|---|
| 중복 주문 | **실패** (1062). 스키마는 V6 그대로 | — |
| 비ASCII 주문 id (`café`) | **실패** (1366 `Incorrect string value`). 스키마는 V6 그대로 | — |
| ASCII 형식 위반 (`a/b`, `a b`, 5자 이하) | **성공** | 새 API 로 접근할 수 없는 주문이 남는다 |
| 뒤 공백 (`x `) | **성공** | `order_id = 'x'` 조회가 그 결제를 고른다. `x` 로 생성하면 1062 다 |
| `a` 와 `a ` 가 함께 있음 | **실패** (1062) | 아래 확인 2 는 이 둘을 중복으로 세지 않는다 |

표는 계획 단계에서 일회용 MySQL 8.0.44 컨테이너와 최소 테이블(`id`, `order_id`, `merchant_id`, 단일 인덱스)로 실측한 것이다. 길이 위반은 실측하지 않았다 — ASCII 문자열이라 같은 결과를 예상하고 리허설이 확인한다. 리허설 테스트가 실제 스키마와 Flyway 로 다시 확인한다.

**순서가 있다. 형식을 먼저 정상화하고, 그 다음에 중복을 센다.**

```sql
-- 확인 1. 형식 밖의 주문 id. 0행이어야 한다 — V7 적용의 필수 사전 조건
SELECT id, merchant_id, order_id FROM payment
WHERE NOT REGEXP_LIKE(order_id, '^[A-Za-z0-9_-]{6,64}$', 'c');

-- 확인 2. 중복 주문. 0행이어야 한다
-- 전제: 확인 1 이 0행이다. 형식이 정상화된 데이터에서만 이 비교가 V7 의 unique(ascii_bin)와 같다.
-- utf8mb4_0900_bin 은 뒤 공백을 구분하고 ascii_bin 은 무시하므로, 'a' 와 'a ' 가 남아 있으면
-- 여기서는 중복이 아닌데 V7 에서는 충돌한다. 공백이 없는 데이터에서는 두 비교가 같다.
SELECT merchant_id, order_id COLLATE utf8mb4_0900_bin AS order_id, COUNT(*), MIN(id), MAX(id)
FROM payment
GROUP BY merchant_id, order_id COLLATE utf8mb4_0900_bin HAVING COUNT(*) > 1;
```

- **사전 조건은 절차로만 지켜진다.** Flyway 는 애플리케이션 기동 때 V7 을 자동으로 적용하고, 확인 1 을 대신 돌려 주지 않는다. 로컬 DB 에 V7 을 처음 적용하기 전에 확인 1·2 를 직접 실행한다. DB 가 강제하게 하려면 같은 ALTER 에 CHECK 제약을 넣는 방법이 있지만 이번엔 넣지 않는다 (2절). "V7 이 실패로 알린다" 는 중복과 비ASCII 에만 해당하는 말이다
- **로컬 DB 에는 중복이 있을 가능성이 높다.** k6 스크립트의 주문 id 가 `k6-${__VU}-${__ITER}` 라 **부하를 두 번 돌리면 같은 주문 id 가 다시 나온다.** V7 이후에는 두 번째 실행의 생성이 409 가 된다. 스크립트가 실행마다 고유한 접두어를 쓰게 고친다
- 마이그레이션 안에서 지우거나 고치지 않는다. 결제에는 취소 이력과 원장이 매달려 있고, 중복 중 어느 쪽이 "진짜" 인지는 데이터를 봐야 안다

**정리 스크립트의 범위는 로컬 실습 데이터다.** 주문 id 는 가맹점이 발급한 식별자이고 가맹점의 주문 시스템이 그 값을 참조한다. 운영 데이터였다면 우리가 임의로 바꿀 수 없고 건별 확인과 가맹점 협의가 필요하다. 로컬은 볼륨을 지우고 다시 만드는 쪽이 더 간단하다 — 두 방법을 모두 기록에 남긴다.

**정리 절차.** 두 단계를 순서대로 한다. 각 단계에서 값을 바로 고치지 않는다 — 새 값을 먼저 만들고, 충돌이 없는 것을 확인한 뒤 적용한다.

| 단계 | 변경 대상 | 끝난 뒤 |
|---|---|---|
| ① 형식 정상화 | 확인 1 에 나온 행 전부 | 확인 1 이 0행 |
| ② 중복 정리 | 확인 2 의 묶음마다 `id` 가 가장 작은 행을 남긴 나머지 | 확인 2 가 0행 |

각 단계 안에서:

1. **새 값을 임시 테이블에 만든다.** `(id, merchant_id, new_order_id)`, 새 값은 `fixed-{id}`. 가장 짧아도 7자(`fixed-1`)이고 64자를 넘지 않아 형식 규칙 안이다. `fixed-{id}` 는 `id` 가 한 자리일 때 5자라 규칙 밖이다
2. **충돌을 검사한다. 0행이어야 한다**
   - 새 값 ↔ **기존 주문**: 같은 가맹점에 그 값을 이미 쓰는 결제가 있는가. 예를 들어 `id` 42 를 `fixed-42` 로 바꾸려는데 그 가맹점에 `fixed-42` 라는 주문이 이미 있으면, 정리한 뒤에도 V7 이 실패한다. 이 비교는 **뒤 공백을 무시하는 쪽**(V7 과 같은 쪽)으로 한다 — ① 단계에서는 아직 공백이 든 값이 남아 있을 수 있다
   - 새 값 ↔ **새 값**: 변경 대상끼리 같은 값을 받았는가. `id` 가 PK 라 `fixed-{id}` 끼리는 겹칠 수 없지만, 새 값을 만드는 규칙을 바꿔도 검사가 남도록 함께 둔다
3. 충돌이 있으면 **적용하지 않고 멈춘다.** 접두어를 바꿔 1번부터 다시 한다
4. 한 트랜잭션에서 UPDATE 하고 그 단계의 확인 쿼리가 0행인지 본다

**리허설 테스트.** 전용 DB 에서 V6 까지 적용한 뒤 아래를 각각 확인한다.

| # | 사례 | 기대 |
|---|---|---|
| 1 | 중복 주문이 있는 채로 V7 적용 | **실패.** 스키마는 V6 그대로 — 단일 인덱스 존재, unique 없음, collation 그대로 |
| 2 | 비ASCII 주문 id 가 있는 채로 V7 적용 | **실패.** 스키마는 V6 그대로 |
| 3 | **ASCII 형식 위반**(`a/b`, `a b`, `x `, 5자 `short`)만 있는 채로 V7 적용 | **성공한다** — V7 이 막지 못한다는 것을 고정한다. 확인 1 은 이 행들을 잡는다. `x ` 가 남은 채로는 `x` 조회가 그 결제를 고른다 |
| 4 | `a` 와 `a ` 가 함께 있음 | 확인 2 는 0행인데 V7 은 실패한다. 확인 1 은 `a ` 를 잡는다 — 순서를 지켜야 하는 이유 |
| 5 | 변경 대상의 새 값(`fixed-{id}`)을 **이미 쓰는 주문**이 있음 | 충돌 검사가 잡아낸다. 적용하지 않는다 |
| 6 | ① → ② 순서로 정리한 뒤 V7 적용 | 성공. 확인 1·2 가 0행 |

MySQL 은 DDL 트랜잭션이 없다. 실패한 마이그레이션이 Flyway 이력에 어떻게 남는지, 다시 적용하기 전에 `repair` 가 필요한지도 여기서 확인해 기록한다.

### 4.7 없는 주문을 잠그며 찾으면

V7 에서 **있는** 주문은 unique 등치라 **대상 결제 한 행으로 잠금 범위가 좁아진다**고 예상한다. 락 엔트리가 하나라는 뜻은 아니다 — 보조 인덱스로 찾아 배타적으로 잠그면 대응하는 클러스터 인덱스 레코드도 함께 잠긴다 ([Locks Set by Different SQL Statements](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)). **없는** 주문은 잠글 레코드가 없으므로 그 자리의 갭을 잠근다 (S5 2차와 같은 원리). 그 갭에 들어오는 결제 생성이 트랜잭션이 끝날 때까지 막힌다.

- S3 의 본선은 같은 이유로 `payment_key` 가 아니라 PK 로 잠갔다 (비잠금 소유 조회 → PK `FOR UPDATE`). 주문 기반 취소도 그렇게 바꿀 수 있지만 **이번엔 바꾸지 않는다.** 세 스키마의 비교가 같은 SQL 이어야 하고, S7 이 같은 SQL 을 RC 로 다시 돌린다
- 404 로 끝나는 요청은 곧 롤백하므로 갭락의 수명이 짧다. 관측 항목으로 둔다: 없는 주문의 잠금 모드와 범위, 그동안 막히는 생성
- 바꿀지는 S7 의 RC 결과를 본 뒤 정한다 (11절)

## 6. 동기화 지점과 회귀

| 지점 | 종류 | 대상 | 용도 |
|---|---|---|---|
| `ORDER_LOCKED` (신규) | hold, 반환 직후 | `PaymentRepository.findByMerchantIdAndOrderIdForUpdate` | 선행이 스캔한 락을 쥔 채 머문다. X 락은 공존하지 않으므로 barrier 로는 쓰지 않는다 |

**프로브 확장 (test support).** `LockWaitProbe` 는 대기자 수만 센다. S6 은 **무엇이 얼마나 잠겼는지**가 관측 대상이다.

- **측정 대상은 선행 트랜잭션 하나다.** DB·테이블로만 좁히면 후속이 가진 락과 후속의 대기 중인 요청까지 함께 세어진다. `data_locks` 의 `ENGINE_TRANSACTION_ID` 로 거른다 ([data_locks](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-data-locks-table.html))
- **측정 시점은 선행이 `ORDER_LOCKED` 에 도착한 직후, 후속을 보내기 전이다.** 이때 `payment` 에 락을 가진 트랜잭션이 **정확히 하나**인지 먼저 확인하고, 그 id 를 선행의 id 로 삼는다. 하나가 아니면 측정하지 않고 실패한다. 후속을 보낸 뒤의 집계는 이 id 로 필터링한다
- **구분해서 센다.** `LOCK_TYPE`(테이블 락 `TABLE` / 레코드 락 `RECORD`), `INDEX_NAME`(`PRIMARY` / 보조 인덱스), `LOCK_MODE`, `LOCK_STATUS`(`GRANTED` / `WAITING`) 별 집계를 돌려준다. 테이블의 의도 락(`IX`)을 레코드 락 개수에 섞지 않는다
- 자동 테스트는 선행의 `GRANTED` 레코드 락에 대해 **개수의 크기**만 단언한다 — V5 는 `PRIMARY` 가 전체 행 수 이상, V6 은 보조 인덱스와 `PRIMARY` 가 각각 그 가맹점의 행 수 수준, V7 은 보조 인덱스와 `PRIMARY` 를 합쳐 한 자리 수. 정확한 모드와 개수는 기록에 남긴다
- root 연결을 쓰는 방식은 그대로다

### 6.1 락 관측 (수동, 로컬 root)

- 세 스키마에서 선행이 락을 쥔 시점의 `data_locks` — 인덱스별 모드와 개수, supremum 포함 여부
- 없는 주문의 잠금 (4.7)
- V6 에서 이웃 가맹점의 INSERT (3.1 의 7·8번) — 선행이 잡은 갭락의 `LOCK_DATA` 와 새 엔트리가 들어갈 위치
- **slow query log**: `docker/mysql/conf.d/s6.cnf` 에 `slow_query_log`, `long_query_time`, `log_queries_not_using_indexes` 를 둔다 (SCENARIO 197·270행). 풀스캔 조회가 어떻게 찍히는지, 락 대기한 후속의 `Query_time` / `Lock_time` 이 어떻게 찍히는지 기록한다. 예상을 적지 않는다
- 데이터 100,000건에서 단건 지연과 `data_locks` 개수 (자동 테스트의 10배)

### 6.2 관측 실험 (자동)

관측한 결과를 회귀 단언으로 올리는 기준을 둔다. **반복해서 같은 결과가 나왔다는 것만으로는 올리지 않는다.** 5회가 같아도 결정적이라는 증명은 아니다.

| 대상 | 처리 |
|---|---|
| **대기 여부** (막힌다 / 통과한다) | 단언으로 올릴 수 있다. 조건은 그 결과를 **실행 계획, 키 배치, 동기화 순서**로 설명할 수 있고, 설명에 쓴 락을 `data_locks` 에서 확인한 것이다 |
| **지연 시간, 처리 시간** | 단언하지 않는다. 환경의 영향을 받는다. 5회의 분포(최소·중앙·최대)만 기록한다 |
| **잠금 개수** | 크기만 단언한다 (6절 프로브). 정확한 값은 기록한다 |

- 3.1 의 † (V6 의 7·8번)는 먼저 단언 없는 관측 테스트로 둔다. 선행이 잡은 갭락의 `LOCK_DATA` 로 **어느 레코드 앞의 갭이 잠겼는지** 확인하고, 새 엔트리가 그 갭의 안인지 밖인지를 키 배치로 설명할 수 있을 때 단언으로 고정한다. 설명과 관측이 어긋나면 고정하지 않고 어긋난 내용을 기록한다
- S5 6.2 는 "결과가 매번 같으면 고정" 이었다. 그때 고정한 결과(대기자 둘 중 한 명이 1213)는 락 모드로 설명이 됐으므로 이 기준에도 맞는다. S6 부터는 기준을 위 표로 좁힌다

## 11. 다음 단계에 남기는 것

- **S7 은 `payment_v5`(`AbstractV5SchemaTest`)에서 인덱스 없는 실험을 RC 로 다시 돌린다.** `SELECT FOR UPDATE` 는 이미 잠긴 행을 만나면 RC 에서도 기다릴 수 있다. `UPDATE` 의 semi-consistent read 와 비교하려면 같은 조건의 `UPDATE` 문이 필요한데 S6 은 만들지 않는다 — S7 이 최소 실험으로 추가한다
- **없는 주문의 갭락**이 RC 에서 사라지는지 S7 이 확인한다. 그 결과로 주문 기반 취소를 "비잠금 조회 → PK 잠금" 으로 바꿀지 정한다
- **생성의 재전송 응답**은 종료 점검에서 정한다. 장치(unique), 오류 코드(`DUPLICATE_ORDER`), 주문 id 형식 규칙은 S6 이 남긴다
- **대량 픽스처와 락 집계 프로브**는 S10 의 배치 실험(10만 건 `UPDATE`)이 다시 쓴다
