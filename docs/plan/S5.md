# S5 — 취소 재전송 중복과 멱등키 계획

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 선행 계획: [plan/S4.md](S4.md) · 선행 기록: [phase1/S4.md](../phase1/S4.md) · 이슈: #29

SCENARIO 참조는 S5 절의 **항목명**과 행 번호를 함께 적는다. 행 번호가 어긋나면 항목명으로 찾는다.

## 1. 배경

S4 는 **롤백된** 트랜잭션을 새 트랜잭션에서 다시 하는 재시도를 다뤘다. DB 가 이미 전부 되돌린 요청이라 다시 해도 안전했다. S5 는 반대다. 취소가 **커밋까지** 끝났는데 가맹점이 응답을 받지 못해 같은 요청을 다시 보낸다. 우리 서버에는 두 요청을 같은 요청으로 알아볼 식별자가 없으므로 두 번 처리한다 (SCENARIO S5 "재현"·"관찰"·"원인", 175~177행).

```
가맹점  POST /v1/payments/{key}/cancel  3,000   → 커밋 (잔여 7,000), 응답 유실
가맹점  POST /v1/payments/{key}/cancel  3,000   → 다시 커밋 (잔여 4,000)
```

S3 의 잠금은 **금액 상한**을 지킨다. 두 번째 요청도 상한 안이라 정당한 요청처럼 통과한다. 막아야 할 것은 초과가 아니라 **같은 요청의 두 번째 실행**이다.

해결은 SCENARIO 가 정한 순서로 간다. 키를 넣고(1차) → 동시 요청에서 뚫리고(관찰 2) → 조회를 잠그고(2차) → 갭락 데드락을 만나고(관찰 3) → unique + insert-first 로 간다(3차).

## 2. 확정된 설계 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 헤더 | `Idempotency-Key` **선택**. 없으면 기존 경로(중복 방지 없음) | 기존 API 계약 테스트가 수정 없이 green 인지로 호환성을 확인한다. 헤더를 **전달하지 않은 경우만** 기존 경로이고, 빈 값·형식 오류는 400 (4.1) |
| 스키마 | **V4**: 최종 컬럼을 다 갖춘 `idempotency_key` + 비유일 검색 인덱스. **V5**: 그 인덱스를 unique 로 교체 | 1·2차 재현을 V4 DB 에 고정할 수 있다. S7 이 unique 이전 스키마를 복원하기도 쉽다 (SCENARIO S5 "남기는 것", 189행) |
| 본선 | `(merchant_id, operation, idempotency_key)` unique + insert-first | SCENARIO S5 "개선 3차 후보" 1번 (183행). RC 전환은 멱등성 해결책이 아니다 (2번, 184행) — S7 |
| 키 저장소 | JDBC(`JdbcTemplate`) 전용. JPA 엔티티를 만들지 않는다 | 선점 INSERT 가 **실제로 먼저 나가야** 한다 (4.3). 엔티티가 없으므로 과거 컨텍스트의 `ddl-auto: validate` 문제도 이번엔 생기지 않는다 (5절) |
| 트랜잭션 | 키 INSERT·취소·결과 저장이 한 트랜잭션(tx1). 중복이면 새 트랜잭션(tx2)에서 기존 결과를 읽는다 | SCENARIO S5 "트랜잭션·응답 정책" (186행) |
| 저장 대상 | **성공 응답만.** 업무 실패(409 등)는 tx1 전체가 롤백되며 키도 사라진다 | 롤백 뒤에는 다시 선점할 수 있다 (SCENARIO S5 "트랜잭션·응답 정책", 186행) |
| 대기 상한 | 키 INSERT **한 문장에만** 짧은 `innodb_lock_wait_timeout` | 4.4 |
| 1213 응답 | 현재 규약대로 500. 번역하지 않는다 | 4.6 |
| 본선 데드락 재시도 | 하지 않는다 | S4 와 같은 이유. 모든 동시 요청의 성공 응답은 보장 범위 밖이다 (4.6) |
| 검증 결제수단 | 같은 경로를 CARD 도 지나지만, 최종 정합성은 **MONEY** 로 검증한다 | CARD 외부 취소는 DB 롤백으로 되돌아가지 않는다 — S8/S9 (SCENARIO S5 "범위", 187행) |
| 트랜잭션 경계 | 취소 전체가 단일 트랜잭션 | 분리는 S8 |
| 헤더 전달 확인 | 앞뒤 공백·중복 헤더는 **내장 Tomcat 실서버 테스트**(RANDOM_PORT + raw socket)로, 나머지 키 규칙은 MockMvc 로 | MockMvc 는 컨테이너를 거치지 않아 공백을 그대로 넘긴다. JDK HttpClient 는 전송 전에 헤더를 정규화할 수 있다 (4.1) |
| 1·2차 실패 배선의 응답 | `Payment` 를 반환하고 **응답을 저장하지 않는다.** 키 행은 hash·`COMPLETED` 만, `response_status`·`response_body` 는 NULL. 키가 이미 있으면 재생하지 않고 현재 결제를 조회해 반환 | 1·2차의 요점은 중복 실행과 데드락이지 재생이 아니다. 응답 스냅샷 타입(6번 커밋)보다 먼저(4번 커밋) 만들어진다 |

## 3. 단계별 실험

준비: 충전 100,000 → MONEY 결제 10,000 승인 (DONE, 잔여 10,000).

| 단계 | 구현 | 재현 | 기대 결과 | 스키마 |
|---|---|---|---|---|
| 0 | 현재 본선, 키 없음 | 3,000 취소를 **순차로** 두 번 | 취소 이력 2건, 잔여 4,000, REFUND 원장 2건. 불변식은 유지된다 | 최신 |
| 1차 | check-then-insert: 키 조회(잠금 없음) → 없으면 취소 → 키 저장 | 같은 키 두 요청이 `KEY_LOOKED_UP` barrier 에서 만난 뒤 진행 | 두 요청 모두 "없음" 을 보고 취소 2건. 키 행도 2건 (비유일이라 막히지 않는다) | V4 |
| 2차-① 최소 실험 | 멱등 테이블만. JDBC 두 세션 | 양옆 기준 행(`k10`, `k30`)을 두고 없는 `k20` 을 둘 다 `FOR UPDATE` → 둘 다 `k20` INSERT | X 갭락 둘 다 GRANTED → 각 INSERT 의 insert intention 이 상대 갭락에 WAITING → 1213 | V4 |
| 2차-② 서비스 적용 | 키 `FOR UPDATE` 조회 → 취소 → 키 저장 | `KEY_LOOKED_UP` barrier 뒤 진행 | 4.7 의 순환. 성공 1, 1213 1, 취소 1건 | V4 |
| 3차 (본선) | unique + insert-first | 6절 | 6절 | 최신(V5) |

- **0단계는 최신 컨텍스트에 둔다.** 헤더가 선택이라 "키 없이 재전송하면 두 번 처리된다" 는 본선에서도 계속 성립하는 동작이다. 이후 V5 가 들어와도 이 테스트는 green 이어야 한다
- **1·2차는 처음부터 V4 컨텍스트에 둔다.** V5 를 넣는 커밋에서 빨개지지 않는다 (S4 의 교훈)
- **2차-① 최소 실험이 먼저다** (SCENARIO S5 "개선 2차"·"관찰 3", 180~181행). 원인을 멱등 테이블 하나로 좁혀 확인한 뒤 서비스에 붙였을 때 payment 락이 순환에 끼는 모양을 기록한다
- 1·2차 실패 배선은 모두 **본선 canceller(`PessimisticLockPaymentCanceller`)를 그대로** 쓴다. 금액 상한은 지켜지는데 같은 요청이 두 번 실행된다는 것이 1차의 요점이다

## 4. 본선 설계

### 4.1 "같은 키", "같은 요청" 의 정의

해시 알고리즘보다 **무엇을 같다고 볼지**가 먼저다.

**키**

| 입력 | 처리 |
|---|---|
| 헤더 없음 | 기존 경로 |
| 빈 값, 공백뿐 | 400 `INVALID_REQUEST` |
| 길이 초과 (64자) | 400 |
| 허용 문자 밖 (`0x21`~`0x7E` 출력 가능한 ASCII 외) | 400 |
| 쉼표(`0x2C`) 포함 | 400 |
| 같은 헤더가 여러 번 | 400 |
| 대소문자 | **구분한다.** `abc` 와 `ABC` 는 다른 키 |

- 컬럼은 `VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin`. V1 의 테이블은 `DEFAULT CHARSET = utf8mb4` 만 지정해 MySQL 8 기본 collation `utf8mb4_0900_ai_ci`(대소문자·악센트 무시)를 쓴다. 그대로 두면 unique 가 `abc` 와 `ABC` 를 같은 키로 막는다. collation 을 명시하고 스키마 전제 테스트로 지킨다
- 키의 범위는 `(merchant_id, operation)` 이다. 다른 가맹점이 같은 키를 써도 서로 무관하다. `operation` 은 지금 `CANCEL` 뿐이고, Phase 1 종료 점검에서 `CHARGE` 가 같은 테이블을 쓴다
- 헤더 값 앞뒤 공백을 서블릿 컨테이너가 어떻게 전달하는지는 실서버 테스트로 확인하고 기록한다 (2절 "헤더 전달 확인"). 빈 헤더(`Idempotency-Key:`)와 헤더 없음이 컨트롤러에서 구분되는지도 테스트로 고정한다
- **쉼표를 허용 문자에서 뺀다.** 헤더를 `String` 으로 받으면 같은 헤더가 여러 번 온 요청은 값이 쉼표로 합쳐져 전달된다고 예상한다. 쉼표를 막으면 "복수 헤더" 와 "쉼표가 든 단일 값" 이 규칙 하나로 모두 400 이 되고, 둘을 구분할 필요가 없다. 받은 값을 쉼표로 나누지 않는다. 합쳐지는 동작과 바인딩 형태(`String` / 배열)에 따른 차이는 테스트로 확인하고 기록한다

**요청 내용 (fingerprint)**

- 입력: **고정 필드 순서의 JSON** `{"paymentKey":..., "cancelAmount":..., "reason":...}`. 구분자 이어 붙이기처럼 모호할 수 있는 표현은 쓰지 않는다
- `reason` 의 `null` 과 `""` 는 **다른 요청**이다. 저장되는 취소 사유가 다르기 때문이다
- `paymentKey` 를 포함한다. 같은 키로 다른 결제를 취소하려 하면 거절된다
- 해시는 SHA-256, 16진 64자 `CHAR(64)`
- **비교 대상은 성공해 저장된 요청뿐이다.** 업무 실패나 롤백으로 끝난 요청은 키 행이 남지 않으므로, 같은 키로 다른 내용을 보내도 `IDEMPOTENCY_KEY_REUSED` 가 아니라 새 요청으로 실행된다 (회귀 8)

같은 키에 fingerprint 가 다르면 409 `IDEMPOTENCY_KEY_REUSED`. 저장된 응답을 돌려주지 않는다.

### 4.2 스키마

```
V4__idempotency_key.sql
  idempotency_key
    id                BIGINT PK
    merchant_id       BIGINT       NOT NULL
    operation         VARCHAR(20)  NOT NULL
    idempotency_key   VARCHAR(64)  ascii / ascii_bin  NOT NULL
    request_hash      CHAR(64)     NOT NULL
    status            VARCHAR(20)  NOT NULL         IN_PROGRESS | COMPLETED
    response_status   INT          NULL
    response_body     TEXT         NULL             응답 스냅샷 JSON
    created_at, completed_at
  idx_idempotency_key_lookup (merchant_id, operation, idempotency_key)   비유일

V5__idempotency_key_unique.sql
  ALTER TABLE idempotency_key
      DROP INDEX idx_idempotency_key_lookup,
      ADD UNIQUE KEY uk_idempotency_key (merchant_id, operation, idempotency_key);
```

- 컬럼은 V4 에서 전부 만든다. 1·2차 실패 배선도 같은 컬럼을 쓰므로 V4 와 V5 는 **인덱스 유일성만** 다르다
- **V5 는 ALTER 한 문장이다.** MySQL 8.0 InnoDB 는 DDL **한 문장**의 원자성을 지원하지만 ([Atomic DDL](https://dev.mysql.com/doc/refman/8.0/en/atomic-ddl.html)), 여러 DDL 문장을 한 트랜잭션으로 함께 되돌릴 수는 없다. DROP 과 ADD 를 두 문장으로 나누면 unique 추가가 실패했을 때 검색 인덱스만 사라진 채 남는다
- **V5 적용 대상에는 중복 키가 없어야 한다.** 있으면 unique 추가가 실패한다. 1·2차 재현은 `payment_v4` DB 에서만 돌고 최신 DB 에는 중복을 만들지 않는다. V5 주석에 V3 처럼 확인 쿼리를 남긴다
  ```sql
  SELECT merchant_id, operation, idempotency_key, COUNT(*) FROM idempotency_key
  GROUP BY merchant_id, operation, idempotency_key HAVING COUNT(*) > 1;
  ```
- `status` 는 단일 트랜잭션인 S5 에서 **커밋된 값이 항상 `COMPLETED`** 다. 컬럼은 S8 에서 처리 중 상태가 따로 커밋될 때를 위해 둔다
- 보존 기간은 정책만 기록하고 정리 배치는 만들지 않는다. **정리·삭제 경로가 없다는 것이 4.3 의 "unique 위반 뒤 tx2 에는 행이 반드시 있다" 는 전제의 근거다.** 정리 경로가 생기면 이 전제를 다시 본다

### 4.3 insert-first 의 보장 — 코드 순서가 아니라 SQL 순서

```
IdempotentCancelCoordinator.cancel(merchantId, key, request)     트랜잭션 없음
  key == null → paymentService.cancel(...), 스냅샷 반환 (저장 없음)
  hash = fingerprint(request)
  try
    tx1 (TransactionTemplate)
      id       = store.claim(merchantId, CANCEL, key, hash)   JDBC INSERT, status=IN_PROGRESS  (4.4)
      payment  = paymentService.cancel(...)                  본선 canceller 가 tx1 에 참여
      snapshot = 스냅샷(payment)
      store.complete(id, 200, json(snapshot))                UPDATE, status=COMPLETED  (4.5)
    commit 성공 → snapshot 반환
  catch 키 선점 충돌 (tx1 은 이미 롤백됨)
    tx2 (새 트랜잭션, readOnly)
      row = store.find(merchantId, CANCEL, key)
      row 없음               → IllegalStateException (정리 경로가 없으므로 불가능)
      row.hash != hash       → IdempotencyKeyReusedException (409)
      row.status != COMPLETED → IllegalStateException (S5 에서 커밋된 행은 항상 COMPLETED)
      저장된 (status, body) 반환
  catch 키 선점 대기 상한 초과 → IdempotencyKeyInUseException (409)
```

**`PaymentService.cancel` 은 그대로 둔다.** 시그니처도 반환 타입(`Payment`)도 바꾸지 않는다. 컨트롤러는 조율자만 부르고, 조율자가 키 없는 경로와 키 있는 경로 모두에서 이 메서드에 위임한다. 이 메서드는 스스로 트랜잭션을 열지 않고 본선 canceller 에 위임하므로, tx1 안에서 부르면 canceller 가 tx1 에 참여한다. 이 메서드를 직접 부르는 기존 테스트는 수정하지 않는다.

구현이 지켜야 할 조건:

1. **키 INSERT 가 실제로 실행된 뒤에만 canceller 를 호출한다.** `JdbcTemplate` INSERT 는 호출 즉시 나간다. JPA 영속성 컨텍스트에 쌓였다가 flush 때 나가는 경로를 쓰지 않는다
2. **canceller 는 tx1 에 참여한다.** `PessimisticLockPaymentCanceller` 의 `@Transactional` 은 기본 전파(REQUIRED)다. 별도로 커밋되면 안 된다. `JpaTransactionManager` 는 같은 커넥션을 `JdbcTemplate` 에 노출하므로 키 INSERT 와 JPA 변경이 같은 트랜잭션이다 — 테스트로 확인한다 (키 INSERT 뒤 canceller 실패 시 키 행도 사라지는가)
3. **"키 선점 충돌" 은 선점 INSERT 의 대상 unique 위반으로만 한정한다.** 판정은 claim 호출 지점에서 에러 코드 1062 와 제약 이름 `uk_idempotency_key` 로 한다. 취소 과정에서 나는 다른 무결성 예외를 재조회로 보내지 않는다
4. **조율자는 tx1 의 커밋이 성공한 뒤에만 반환한다.** 커밋 실패는 성공 응답이 아니다
5. **`claim` 과 `complete` 는 활성 트랜잭션 안에서만 호출할 수 있다.** 트랜잭션이 없으면 SQL 을 보내기 전에 즉시 실패한다. 트랜잭션 밖에서는 키 INSERT 가 자동 커밋되어, 취소가 실패해도 키가 남는다. 검사는 `TransactionSynchronizationManager.isActualTransactionActive()` 로 명시적으로 한다. `@Transactional(MANDATORY)` 를 쓰지 않는 이유는 둘이다 — 프록시가 있어야만 동작하고, 저장소가 던진 예외가 트랜잭션에 rollback-only 표시를 남긴다

**롤백의 일반 흐름.** 선행 요청이 키를 INSERT 한 채 진행 중이면, 후속 요청의 INSERT 는 unique 검사에서 선행 트랜잭션이 끝나기를 기다린다.

| 선행의 결말 | 후속 INSERT |
|---|---|
| 커밋 | 1062 unique 위반 → tx1 롤백 → tx2 에서 저장된 응답 |
| 롤백 | **위반 없이 그대로 성공** → 후속이 직접 선점하고 취소를 진행 |

즉 "선행 롤백 → 후속 1062 → tx2 에서 행 없음" 은 일반 흐름이 아니다. 그래서 tx2 의 행 없음을 재선점으로 흡수하지 않고 예상 밖 상태로 드러낸다.

### 4.4 대기 상한 — 키 INSERT 한 문장에만

후속 INSERT 의 대기는 선행 트랜잭션이 끝날 때까지다. 기본 `innodb_lock_wait_timeout` 은 50초다. 상한을 짧게 두되 **적용 범위를 키 INSERT 한 문장으로 좁힌다.**

```
tx1 에 묶인 커넥션에서 (활성 트랜잭션 필수 — 4.3 조건 5)
  SELECT @@SESSION.innodb_lock_wait_timeout      기존 값
  SET SESSION innodb_lock_wait_timeout = N       (설정값, 기본 3초)
  INSERT INTO idempotency_key ...
  finally: SET SESSION innodb_lock_wait_timeout = 기존 값     INSERT 직후, canceller 호출 전
```

- **커넥션 일치와 트랜잭션 원자성은 서로 다른 조건이다.** 세션 변수 조회·변경·INSERT·복원은 tx1 에 묶인 동일 커넥션에서 수행한다 — 활성 트랜잭션 안의 `JdbcTemplate` 호출은 그 트랜잭션의 커넥션을 쓴다. `ConnectionCallback` 으로 네 문장을 한 커넥션에 묶는 것만으로는 부족하다. 커넥션은 같아져도 자동 커밋을 막지 못한다. 그래서 4.3 조건 5 가 트랜잭션을 강제한다
- 취소 전체가 끝난 뒤에 복원하면 payment·wallet 잠금 대기에도 짧은 상한이 적용된다. 그 1205 까지 `IDEMPOTENCY_KEY_IN_USE` 로 번역하면 실제 원인(payment·wallet 경합)을 잘못 설명한다
- **번역은 이 INSERT 에서 난 1205 만 한다.** 다른 문장의 1205 는 지금처럼 500 이다
- 1205 는 기본(`innodb_rollback_on_timeout=OFF`)에서 **문장만** 롤백하고 트랜잭션은 열려 있다 ([MySQL 8.0 InnoDB 파라미터](https://dev.mysql.com/doc/refman/8.0/en/innodb-parameters.html)). 예외를 tx1 밖으로 던져 **전체를 롤백**시킨다 — 번역은 조율자에서 tx1 이 끝난 뒤에 한다
- 세션 변수는 HikariCP 가 반환 시 되돌리지 않는다 (S4 3.3). 복원은 `finally` 에 둔다
- 응답: 409 `IDEMPOTENCY_KEY_IN_USE`. 같은 키로 다시 보내면 되는 **재시도 가능한** 충돌이다

### 4.5 응답 반환 경계

지금은 `PaymentService.cancel()` 이 `Payment` 를 반환하고 컨트롤러가 `PaymentResponse.from()` 을 부른다. 이 구조로는 저장된 응답을 재생할 수 없다 — 재생 때는 `Payment` 가 아니라 **그때의 응답**이 있어야 한다.

- application 계층에 응답 스냅샷 타입(`PaymentResponse` 와 같은 필드)과 결과 `(status, snapshot)` 을 둔다. 조율자가 이것을 반환하고, 컨트롤러는 상태 코드와 본문으로 그대로 쓴다
- 스냅샷은 **tx1 안에서** 만들어 저장한다. 커밋된 결과와 저장된 응답이 같은 시점의 값이다
- `response_status` 는 정수로 저장한다. application 계층이 `HttpStatus` 타입에 의존하지 않는다. S5 에서 저장하는 것은 성공(200)뿐이다
- 키 없는 경로도 같은 결과 타입을 반환해 컨트롤러 분기를 없앤다
- **직렬화는 조율자가 한다.** 조율자가 스냅샷을 JSON 문자열로 만들어 `store.complete` 에 넘기고, 재생 때는 저장된 JSON 을 스냅샷 타입으로 되읽어 반환한다. 키 저장소는 본문을 문자열로만 다루고 결제 타입을 모른다. 직렬화에는 MVC 가 쓰는 것과 같은 `ObjectMapper` 빈을 쓴다
- **"동일 응답" 의 기준은 HTTP 상태와 JSON 필드·값의 동일성이다.** 바이트 동일성은 요구하지 않는다. 최초 응답도 재생 응답도 스냅샷 타입을 MVC 가 직렬화한 것이므로, 필드 순서와 공백은 계약이 아니다. 회귀 1 은 HTTP 수준에서 두 응답의 본문을 JSON 으로 비교한다

**스냅샷 재생의 검증.** "키 A 로 3,000 취소 → 키 B 로 2,000 추가 취소 → 키 A 재전송" 에서 A 재전송은 **A 당시의 응답(잔여 7,000)** 을 받아야 한다. 최신 값(5,000)을 다시 조회해 돌려주면 이 테스트가 실패한다.

### 4.6 오류 응답과 보장 범위

| 상황 | 응답 |
|---|---|
| 같은 키·같은 내용, 선행 완료 | 저장된 응답 (200, 당시 본문) |
| 같은 키·다른 내용 | 409 `IDEMPOTENCY_KEY_REUSED` |
| 선행 진행 중, 대기 상한 초과 | 409 `IDEMPOTENCY_KEY_IN_USE` |
| 헤더 형식 오류 | 400 `INVALID_REQUEST` |
| 업무 실패 (취소 금액 초과 등) | 지금과 같음. 키는 저장되지 않는다 |
| 키 INSERT 를 포함한 1213 | **500** (현재 규약, 번역하지 않음) |

**V5 는 데드락을 없애지 않는다.** unique + insert-first 는 중복 실행을 막는 장치다. unique 의 중복 검사도 락을 잡는다. 선점자가 키를 INSERT 한 채 대기자가 둘 이상일 때 선점자가 롤백하면, 대기자들은 중복 검사로 얻은 S 락을 서로 가진 채 각자 INSERT 의 X 를 기다려 순환 대기가 될 수 있다 ([MySQL 8.0 — Locks Set by Different SQL Statements](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html) 의 세 세션 사례). 8번 커밋에서 이 모양을 관측한다 (6.2 관측, 정합성은 6절 회귀 10).

- 1213 이 나면 피해 트랜잭션은 **전체 롤백**된다. 키도 사라지므로 같은 키 재전송은 안전하다 — 살아남은 쪽이 커밋했으면 저장된 응답을 받는다
- 응답은 현재 규약대로 500 이다. "키 INSERT 의 1213 을 재시도 가능한 409 로 번역" 은 계약 변경이므로 이번엔 하지 않고, 관측 결과와 함께 기록에 후보로 남긴다
- **모든 동시 요청이 성공 응답을 받는다는 보장은 이번 범위 밖이다.** S5 가 보장하는 것은 "같은 키로 **커밋되는 취소는 최대 한 건**이고, 그 성공 응답이 재생된다" 이다. 업무 실패나 롤백 뒤의 재전송은 다시 실행되므로 **실행 횟수**는 보장 대상이 아니다. CARD 의 외부 효과는 S8/S9 에서 다룬다

### 4.7 2차-② 에서 예상하는 순환

```
T1  SELECT ... WHERE key = k FOR UPDATE      없음 → 갭 X
T2  SELECT ... WHERE key = k FOR UPDATE      없음 → 갭 X  (갭 락끼리 공존)
    ── KEY_LOOKED_UP barrier ──
T1  payment FOR UPDATE                        획득
T2  payment FOR UPDATE                        T1 에 막힘
T1  취소 … INSERT key                         insert intention → T2 의 갭 X 에 막힘  → 순환
```

최소 실험(2차-①)의 순환에 payment 행이 한 고리로 끼는 모양이다. 누가 피해자가 될지는 정하지 않는다 — 단언은 "성공 1, 1213 1, 취소 이력 1건" 이다. **중복은 막혔지만 데드락 덕분이다.** 이 대비를 기록에 남긴다.

## 5. 과거 컨텍스트

```
support
├── MySqlTestContainer
├── PastSchemaDatabase        (신규) 등록 헬퍼: register(registry, database, flywayTarget)
├── AbstractV2SchemaTest      얇게: PastSchemaDatabase.register(registry, "payment_v2", "2")
└── AbstractV4SchemaTest      (신규) 얇게: "payment_v4", "4"
```

- 버전 인자를 **공유 static 상태로 두지 않는다.** 각 베이스가 자기 `@DynamicPropertySource` 에서 헬퍼에 값을 넘긴다. 프로퍼티가 달라 Spring 컨텍스트 캐시 키가 버전별로 갈린다
- `ddl-auto: validate` 는 과거 컨텍스트에서도 **유지한다.** 키 저장소가 JDBC 라 V2 에 없는 테이블을 매핑하는 엔티티가 생기지 않는다. 과거 엔티티 매핑이 그 스키마와 맞는지를 계속 검증하는 쪽이 낫다. 엔티티가 새 테이블을 매핑하는 시나리오가 오면 그때 끈다 (S4 가 S5 로 넘긴 결정)
- 컨텍스트 전제 테스트: 각 컨텍스트에서 **DB 이름, Flyway 적용 버전, `idempotency_key` 인덱스 유일성**(V4 비유일 / 최신 unique)과 키 컬럼 collation 을 확인한다. `V2SchemaContextTest` 와 같은 역할이다
- V2 컨텍스트에도 조율자 빈은 뜬다. 쓰지 않으므로 무해하다

## 6. 동기화 지점과 회귀

키 저장소는 인터페이스(`IdempotencyKeyStore`)로 두어 기존 방식(`ConcurrencyGateConfig` 의 인터페이스 프록시)으로 게이트를 건다.

| 지점 | 종류 | 대상 | 용도 |
|---|---|---|---|
| `KEY_LOOKED_UP` (신규) | barrier, 반환 직후 | 1·2차 배선의 키 조회 | 두 요청이 "없음" 을 본 뒤 진행. 2차는 갭 X 를 잡은 뒤지만 갭 락끼리 공존하므로 모인다 (S4 `LEDGER_INSERTED` 와 같은 예외) |
| `KEY_CLAIMED` (신규) | hold, 반환 직후 | 본선 `claim` | 선행이 키를 쥔 채 머문다. 후속의 대기는 `LockWaitProbe` 로 확인한 뒤 선행을 풀어 준다 |

**후속의 대기 확인 — `LockWaitProbe` (신규, test support).** 지금까지 락 관측은 수동·로컬 root 였고, 테스트 코드가 `performance_schema` 를 조회하는 것은 이번이 처음이다.

- 테스트 사용자는 자기 데이터베이스 권한만 받는다 (`MySqlTestContainer.createDatabase` 의 GRANT). `data_lock_waits` 조회에는 그 테이블의 SELECT 권한이 필요하다 ([MySQL 8.0 — data_lock_waits](https://dev.mysql.com/doc/mysql-perfschema-excerpt/8.0/en/performance-schema-data-lock-waits-table.html)). `createDatabase` 가 이미 쓰는 root 연결 방식을 재사용한다. 테스트 사용자의 조회가 실제로 거부되는지는 착수 시 확인해 기록한다
- `data_lock_waits` 에는 스키마·테이블 컬럼이 없다. `data_locks` 와 락 id 로 조인해 **현재 테스트의 DB 와 `idempotency_key` 테이블**로 좁힌다. 같은 컨테이너에 데이터베이스가 셋(컨테이너 기본 DB, `payment_v2`, `payment_v4`)이다
- 기대한 대기자 수가 될 때까지 폴링하고, 상한(게이트와 같은 10초) 안에 나타나지 않으면 테스트를 실패시킨다

**선행만 실패시키는 장치 (회귀 8·10).** 예외 주입 대신 **업무 실패**를 쓴다. 게이트에 새 기능을 더하지 않는다.

- 선행은 같은 키로 20,000 취소를 보낸다. 입력 검증은 통과하고 업무 검증에서 `CANCEL_AMOUNT_EXCEEDED` 로 실패해 tx1 이 롤백된다. 후속은 같은 키로 3,000 취소다
- 선행을 `KEY_CLAIMED` 에서 붙잡고, 후속 INSERT 가 **실제로 대기 중인 것**을 `LockWaitProbe` 로 확인한 뒤 풀어 준다. 이 확인이 없으면 "대기하던 INSERT 가 그대로 성공했다" 가 아니라 "선행이 끝난 뒤에 INSERT 했다" 를 본 것일 수 있다

**회귀** (최신 컨텍스트, MONEY. 공통 준비는 3절)

| # | 사례 | 기대 |

| 2 | 같은 키·다른 금액 / 다른 사유 / 다른 결제 | 409 `IDEMPOTENCY_KEY_REUSED`, 부작용 없음 |

| 5 | 다른 가맹점이 같은 키 문자열 사용 | 둘 다 각자 처리 |

| 12 | 키 INSERT 뒤 canceller 가 업무 실패 | 키 행 없음 (같은 트랜잭션 확인, 4.3 조건 2) |
| 13 | 업무 실패 뒤 같은 키·같은 내용 재전송. 준비는 READY 결제: 취소 → 승인 → 같은 취소 재전송 | 첫 응답 409 `INVALID_PAYMENT_STATUS`. 재전송은 **재생이 아니라 재실행**되어 200, 취소 1건 |
| 14 | 트랜잭션 밖에서 `claim` / `complete` 호출 | 즉시 실패, 키 행 없음 (4.3 조건 5) |

모든 사례에서 공통 불변식(잔액 == 원장 합계, `balance_amount = amount − 취소 합계`)과 "예상 밖 오류 0건" 을 확인한다. 10번의 1213 은 이 시나리오가 예측한 것이므로 예상 밖으로 세지 않고 따로 센다.

**대기 상한은 테스트에서도 기본 3초다.** 베이스 전체에 짧은 값을 주지 않는다. 회귀 7·8·10 은 후속이 대기하는 동안 테스트가 폴링하고 선행을 풀어 줘야 하므로, 상한이 짧으면 느린 환경에서 후속이 먼저 1205 로 끝난다. 회귀 9 만 상한을 넘겨 기다리며, hold 의 상한 10초 안이다.

### 6.1 락 관측 (수동, 로컬 root)

- 2차-①: barrier 시점 `data_locks` 에 `uk` 아닌 `idx_idempotency_key_lookup` 의 `X,GAP` 두 개 GRANTED, INSERT 시점 `X,GAP,INSERT_INTENTION` WAITING. `LATEST DETECTED DEADLOCK`
- 3차 동시: 후속 INSERT 가 무엇을 기다리는지(중복 검사 락의 모드) 관측으로 확정해 기록한다. 계획에서 모드를 미리 단정하지 않는다
- 회귀 10: 대기자 두 명의 락 모드와 순환

### 6.2 관측 실험 — 대기자 둘의 데드락 (자동)

회귀 10 과 분리한다. "1213 이면 …" 같은 조건부 단언으로는 데드락을 재현했다고 할 수 없고, 정합성 회귀가 데드락 발생 여부에 기대서도 안 된다.

- 회귀 10 과 같은 배치를 관측 테스트로 5회 돌려 1213 발생 여부와 피해자 수를 기록한다. S4 의 `LockWaitTimeoutObservationTest` 와 같은 역할이다
- 결과가 매번 같으면 그 결과를 **무조건 단언**으로 관측 테스트에 고정하고 `phase1/S5.md` 에 남긴다. 매번 같지 않으면 단언 없이 분포만 기록한다
- 회귀 10 의 단언은 관측 결과와 무관하게 바꾸지 않는다
