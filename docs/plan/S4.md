# S4 — FK 락 승격 데드락 계획

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 선행 계획: [plan/S3.md](S3.md) · 선행 기록: [phase1/S3.md](../phase1/S3.md) · 이슈: #27

## 1. 배경

S1~S3 의 스키마에는 FK 가 없다. 원장 INSERT 의 FK 검사 락이 차감 유실 관찰에 섞이지 않게 하려고 일부러 뺐다 (SCENARIO 83행). S4 는 `wallet_ledger.wallet_id → wallet.id` FK 를 처음 추가하고, **FK 검사도 부모 행을 잠근다**는 사실이 만드는 데드락을 본다.

```
T1  INSERT wallet_ledger (wallet_id = 1)   FK 검사 → wallet#1 에 S 락
T2  INSERT wallet_ledger (wallet_id = 1)   FK 검사 → wallet#1 에 S 락   (S 끼리는 공존)
T1  UPDATE wallet WHERE id = 1             X 락 필요 → T2 의 S 에 막힘
T2  UPDATE wallet WHERE id = 1             X 락 필요 → T1 의 S 에 막힘  → 순환 대기
```

본선(`PessimisticLockWalletBalanceUpdater`)은 원장 INSERT 전에 wallet 을 `FOR UPDATE` 로 잡으므로 이 모양이 생기지 않는다. S2 가 "선행 잠금이 S4 의 데드락을 예방한다" 고 남긴 가정이다. S4 는 그 선행 잠금을 **뺀** 구현으로 데드락을 재현하고, 본선이 막는다는 것을 확인한다.

### 1.1 착수 전 확인 — FK 하나로 과거 재현 5개가 깨진다

계획 전에 임시 worktree 에서 FK 만 추가하고 전체 테스트를 돌렸다 (정리 규약의 TRUNCATE 는 FK 검사를 끄도록 임시 수정). **142개 중 6개 실패.**

| 실패 | 예외 |
|---|---|
| `WalletLostUpdateReproductionTest` 2건 (S2 naive 차감, 충전 경쟁) | `update wallet` 에서 `Deadlock found` |
| `DuplicateConfirmReproductionTest` MONEY (S1) | `update payment` 에서 `Deadlock found` |
| `OptimisticLockConcurrencyTest`, `LockContentionObservationTest` (S2-a) | `Deadlock found` — 버전 충돌 대신 |
| `SchemaConstraintTest.noForeignKeys` | 예상된 실패 |

원인은 모두 1절의 모양이다. naive 와 낙관적 락 전략은 `WalletLedger` 를 IDENTITY 로 **즉시 INSERT** 하고, 지갑 변경은 **커밋 시점 flush 의 UPDATE** 로 나간다. 코드에 쓴 순서(읽기 → 계산 → 원장)가 아니라 SQL 순서가 "자식 INSERT → 부모 UPDATE" 다. FK 를 넣는 순간 S2 의 Lost Update 재현이 **데드락 재현으로 바뀐다.**

반대로 원자적 감산·조건부 감산(`WalletDecrementComparisonTest`)은 green 이었다. `UPDATE wallet` 이 원장 INSERT 보다 **먼저** 나가서 X 락을 선점하기 때문이다. 같은 문장이고 순서만 다르다 — 이것이 S4 의 대조군이 된다 (5절).

두 가지가 따라 나온다.

- V3 는 SCENARIO 94행 "좁은 예외"(additive·DEFAULT·미매핑 컬럼)에 해당하지 않는다. **과거 재현은 V2 전용 DB 에서 돌려야 한다** — 원칙을 이번에 처음 구현한다 (3절)
- 데드락(1213)은 JPA 경로에서 `CannotAcquireLockException` 으로 올라왔다. 락 대기 타임아웃(1205)도 같은 `PessimisticLockingFailureException` 계열로 번역될 수 있어 **예외 타입으로는 둘을 구분할 수 없다고 보고**, SCENARIO 169행의 "둘의 역할 구분" 은 벤더 에러 코드로 한다. 1205 의 실제 타입은 6절 측정에서 기록한다

## 3. 과거 재현을 V2 DB 에서 돌린다

### 3.1 옮기는 것과 남기는 것

기준은 **"어느 스키마를 전제로 쓴 실험인가"** 다. 결과가 우연히 같아도 V2 전제 실험은 V2 에서 돌린다 — 이후 S5·S6 마이그레이션에서 또 깨지지 않게 한다.

| 테스트 | 스키마 | 이유 |
|---|---|---|
| `DuplicateConfirmReproductionTest` (S1) | **V2** | MONEY 재현이 V3 에서 데드락으로 바뀐다 |
| `WalletLostUpdateReproductionTest` (S2) | **V2** | 동일 |
| `WalletDecrementComparisonTest` (S2 비교 1·2) | **V2** | V3 에서도 green 이지만 V2 전제 실험이다 |
| `OptimisticLockConcurrencyTest`, `LockContentionObservationTest` (S2-a) | **V2** | V3 에서 버전 충돌 대신 데드락 |
| `OverRefundReproductionTest` (S3) | **V2** | V3 에서도 green 이지만 V2 전제 실험이다 |
| S1·S2·S3 회귀 (`*RegressionTest`) | V3 (최신) | 본선 회귀는 최신 스키마에서 계속 green 이어야 한다 |
| API·서비스·스키마 계약 테스트 | V3 (최신) | 본선 |

`SchemaConstraintTest` 는 둘로 나눈다. V2 쪽은 "FK 0건" 을 과거 전제로 계속 지키고, V3 쪽은 "FK 는 `wallet_ledger → wallet` 하나뿐" 과 기존 인덱스 전제(S6·S10)를 지킨다.

**V3 에서 과거 재현이 데드락으로 바뀐다는 사실 자체**는 버리지 않는다. 1.1 의 관찰로 `phase1/S4.md` 에 기록한다.

### 3.2 장치

```
support
├── AbstractIntegrationTest          최신 스키마 (기존). DB = test
└── AbstractV2SchemaTest             (신규) 같은 컨테이너의 두 번째 DB, Flyway target=2
```

- 컨테이너는 **하나를 공유**한다. 두 번째 DB(`payment_v2`)를 root 로 만들고 테스트 사용자에게 권한을 준다
- 두 베이스는 **Spring 컨텍스트가 따로** 뜬다 (datasource URL·Flyway target 이 다르므로 캐시 키가 다르다). 게이트·Fake 카드사도 컨텍스트마다 따로다
- 정리 규약(TRUNCATE → 시드 → Fake 리셋 → 게이트 해제)은 같다. 시드는 V1 테이블만 쓰므로 V2 DB 에서도 그대로 돈다 (seed_local.sql 머리말이 R__ 를 쓰지 않은 이유가 이것이었다)

**구현 시 확인할 것**

- `@ServiceConnection` 은 연결 정보를 프로퍼티보다 우선한다. V2 베이스는 `@ServiceConnection` 을 상속하지 않고 `@DynamicPropertySource` 로 URL 을 준다 — 컨테이너 소유를 공용 홀더로 빼야 할 수 있다
- 컨텍스트가 둘이면 커넥션 풀도 둘이다. 풀 크기 10 × 2 가 컨테이너 `max_connections` 안인지 확인한다
- `ddl-auto: validate` 는 **엔티티가 V2 에 없는 테이블·컬럼을 매핑하는 순간** V2 컨텍스트 기동을 막는다. V3 는 FK 만 더하므로 이번엔 통과한다. S5 에서 멱등키 엔티티가 생기면 다시 다룬다 (10절)

### 3.3 DatabaseCleaner

FK 가 생기면 부모 테이블 TRUNCATE 가 실패한다 (자식이 비어 있어도). `FOREIGN_KEY_CHECKS = 0` 은 **세션 변수**이므로 풀에서 매번 다른 커넥션을 받는 `JdbcTemplate.execute` 연속 호출로는 안 된다. 한 커넥션(`ConnectionCallback`) 안에서 원래 값을 읽고 → 끄고 → TRUNCATE → **`finally` 에서 원래 값으로 복원**한다. 이 클래스의 javadoc 이 "S4 에서 FK 가 생기면 먼저 깨진다" 고 예고한 항목이다.

복원을 `finally` 에 두는 이유: HikariCP 는 커넥션을 풀에 돌려줄 때 `SET` 으로 바꾼 세션 변수를 되돌리지 않는다. TRUNCATE 가 중간에 실패해 FK 검사가 꺼진 커넥션이 풀에 남으면, 그 커넥션을 받은 후속 테스트에서 제약 검사가 무력화된다. S4 재현이 그 커넥션을 받으면 FK 락이 없어 데드락이 나지 않고, 원인을 추적하기 어려운 실패가 된다.

## 4. 동기화 지점

| 지점 | 종류 | 대상 | 그 시점 보유 락 |
|---|---|---|---|
| `LEDGER_INSERTED` (신규) | barrier, **반환 직후** | `WalletLedgerRepository.save` | 자기 payment X (CAS), 자기 원장 행, **wallet S (FK 검사)** |
| `WALLET_LOCK_ATTEMPT` (기존) | barrier, 호출 직전 | `WalletRepository.findByIdForUpdate` | 자기 payment X (CAS) |

- `LEDGER_INSERTED` 는 **S 락을 잡은 뒤** 모으는 barrier 다. plan/S2.md 4.1 의 "락을 잡은 뒤에는 모으지 않는다" 규칙의 예외인데, S 락끼리는 공존하므로 두 참가자가 모두 도착할 수 있다. 개선 구현에는 이 barrier 를 쓰지 않는다 (SCENARIO 170행) — 본선은 wallet X 를 먼저 잡으므로 두 번째 참가자가 도착하지 못한다
- naive·낙관적 전략도 `save` 를 지나지만 무장 전에는 no-op 이다. V2 컨텍스트에서 무장하지 않는다

## 5. 재현과 회귀

전부 V3(최신) 컨텍스트. 준비: 충전 100,000 → 같은 지갑의 MONEY 결제 P1(3,000), P2(3,000) READY. 잔액이 충분하므로 잔액 부족이 섞이지 않는다.

| # | 배선 | 동기화 | 기대 결과 |
|---|---|---|---|
| 재현 1 | `ledgerFirstDebitConfirmer` | `LEDGER_INSERTED` ×2 | 성공 1, `CannotAcquireLockException`(1213) 1. 피해 결제는 READY·원장 0건 (전체 롤백). 잔액 97,000 == 원장 합계 |
| 재현 2 | `retryingLedgerFirstDebitConfirmer` | `LEDGER_INSERTED` ×2 | 성공 2, 데드락 1회 → 재시도 1회. 잔액 94,000 == 원장 합계, PAY 원장 2건 |
| 대조 | `atomicDebitConfirmer` (S2 비교 1) | `WALLET_READ` ×2 | 성공 2, 데드락 0. **같은 두 문장을 UPDATE → INSERT 순서로** 보낸다 |
| 회귀 1 | 본선 승인 × 2 | `WALLET_LOCK_ATTEMPT` ×2 | 성공 2, 데드락 0, 잔액 == 원장 합계 |
| 회귀 2 | 본선 승인(P1) + 충전 + 본선 취소(P3 환불), 같은 지갑 | `WALLET_LOCK_ATTEMPT` ×3 | 데드락 0, 잔액 == 원장 합계. **원장을 쓰는 모든 경로**(차감·충전·환불)가 wallet 을 먼저 잠근다 |

**재현 1 이 결정적인 이유.** barrier 뒤 두 UPDATE 중 먼저 나간 쪽은 상대의 S 에 막혀 대기하고, 나중 쪽이 대기 그래프를 닫는 순간 InnoDB 가 즉시 순환을 감지해 한쪽을 롤백한다. 누가 피해자가 되는지는 정하지 않는다 (InnoDB 는 변경 행 수 등으로 가벼운 트랜잭션을 고른다) — 단언은 "정확히 한 건" 이다.

**재시도가 barrier 에 다시 걸리지 않는 이유.** 게이트는 스레드당 1회 통과다. 재시도는 같은 워커 스레드에서 돌므로 `LEDGER_INSERTED` 를 그냥 지나간다.

**피해자의 롤백 범위.** 데드락은 문장이 아니라 **트랜잭션 전체**를 롤백한다. 피해 결제의 CAS(`IN_PROGRESS`)와 원장 INSERT 가 함께 사라지므로 재시도는 READY 를 보고 CAS 를 다시 통과한다 — S1 이 단일 트랜잭션을 고른 효과가 S2-a 에 이어 여기서도 나타난다.

**회귀 2 의 점검 범위.** "모든 MONEY 변경 경로를 점검한다" (SCENARIO 168행) 를 테스트 하나로 끝내지 않는다. `WalletLedgerRepository.save` 호출처를 전수 확인해 `phase1/S4.md` 에 표로 남긴다 — 본선에서는 세 경로 모두 `lock(walletId)` 뒤에 원장을 쓴다.

### 5.1 공통 단언

- 불변식 1(잔액 == 원장 합계, 음수 아님)을 모든 행에서 확인한다. 재현 1 도 **정합성은 깨지지 않는다** — 데드락은 가용성 문제다. S1~S3 의 재현과 성격이 다르다는 점을 기록에서 짚는다
- 예상 밖 오류: 재현 1 의 1213 한 건 외에는 0건
- 데드락 판정은 `CannotAcquireLockException` 타입이 아니라 원인 `SQLException.getErrorCode() == 1213` 으로 한다

### 5.2 락 관측

S3 와 같이 로컬 docker-compose MySQL 에 `root` 로 붙어 SQL 을 재연한다. `docker/mysql/conf.d` 에 `innodb_print_all_deadlocks = ON` 을 넣는다.

- barrier 시점: `data_locks` 에 wallet PRIMARY 의 `S,REC_NOT_GAP` 두 개가 **둘 다 GRANTED**
- 첫 UPDATE 시점: `data_lock_waits` 에 `X,REC_NOT_GAP` WAITING ← 상대 `S,REC_NOT_GAP`
- `SHOW ENGINE INNODB STATUS` 의 `LATEST DETECTED DEADLOCK` 과 에러 로그
- 개선 후: 두 번째 트랜잭션이 wallet `X,REC_NOT_GAP` 에서만 기다리고, 원장 테이블엔 `IX` 만

## 6. 데드락 감지와 락 대기 타임아웃

SCENARIO 169행: "기본 데드락 감지는 타임아웃까지 기다리지 않으며, 단순 락 대기의 타임아웃은 별도 실험으로 측정한다."

| | 데드락 (1213) | 락 대기 타임아웃 (1205) |
|---|---|---|
| 판단 | 대기 그래프에 순환이 생기는 즉시 | `innodb_lock_wait_timeout`(기본 50초) 경과 |
| 롤백 범위 | 피해 트랜잭션 **전체** | 기본(`innodb_rollback_on_timeout=OFF`)은 **마지막 문장만** — 트랜잭션은 열린 채 호출자에게 돌아온다 |
| 재시도 | 이번 두 트랜잭션 재현에서는 피해자 롤백으로 순환 대기가 해소되므로, 새 트랜잭션으로 재시도하면 성공할 수 있다 | 상대가 락을 오래 보유하고 있다는 신호다. 보유자가 끝나면 재시도가 성공할 수도 있지만 대기열을 늘릴 수도 있다 |

그래서 이번 실험의 재시도 조건은 1213 만으로 정한다. 1205 를 재시도하지 않는 것은 사실 주장이 아니라 정책 선택이다 — 락 보유 시간 자체를 다루는 것은 S8 의 주제다.

### 6.1 관찰 경로 — DB 동작과 프레임워크 처리를 나눈다

DB 가 하는 일(문장/트랜잭션 롤백)과 프레임워크가 하는 일(예외 변환, `@Transactional` 경계의 롤백)을 섞어 관찰하지 않는다.

| 관찰 대상 | 경로 | 이유 |
|---|---|---|
| 1205 뒤 **문장 단위 롤백**과 트랜잭션 생존 | 직접 관리하는 JDBC 트랜잭션 (`autoCommit = false`) | 예외가 `@Transactional` 경계 밖으로 전파된 뒤에는 Spring 이 트랜잭션 전체를 롤백하므로, DB 의 문장 단위 롤백 상태를 관찰할 수 없다. 1205 를 받은 **같은 커넥션에서** 앞 문장의 변경이 남아 있는지 확인한다 |
| 1213·1205 의 **예외 타입** | JPA 경로 (`@Transactional` 서비스 호출) | 호출자가 실제로 받는 타입과 원인 체인을 기록한다 |

두 관찰을 반드시 별도 테스트로 나눌 필요는 없다. 어느 경로에서 무엇을 봤는지를 기록에 구분해 남기면 된다.

### 6.2 측정

**데드락 감지 (재현 1)**

- 구간: **barrier 해제 → 피해자 워커의 예외 수신.** 현재 테스트 장치로는 두 번째 UPDATE 발행 시각을 직접 측정하지 않는다 (어느 쪽이 두 번째인지도 정해져 있지 않다)
- 이 값은 스레드 스케줄링·SQL 실행·예외 전달을 포함한 **전체 관측 시간**이며, 순수 데드락 감지 시간이 아니다. 기록에 측정 시작·종료 지점과 방법을 함께 적는다
- 판정: 이 상한값이 `innodb_lock_wait_timeout`(기본 50초)보다 충분히 짧으면 "타임아웃까지 기다리지 않는다" 를 보인 것으로 본다

**락 대기 타임아웃**

- 한 트랜잭션이 wallet 을 `FOR UPDATE` 로 잡은 채 hold, 다른 JDBC 트랜잭션이 `SET SESSION innodb_lock_wait_timeout = 1` 후 같은 행을 잠그려다 약 1초 뒤 1205
- 구간: 잠금 문장 발행 직전 → 1205 수신. 이 경우엔 발행 시각을 테스트가 직접 안다
- **세션 설정 복원.** 풀에서 받은 커넥션이면 커넥션을 반환하기 전에 `finally` 에서 `innodb_lock_wait_timeout` 을 원래 값으로 되돌린다 (3.3 과 같은 이유 — 1초 설정이 남으면 후속 회귀의 정상 락 대기가 1205 로 끝난다). 전용 커넥션을 열고 닫는 방식이면 복원이 필요 없지만, 어느 방식을 썼는지 기록한다

**관측 (수동, 로컬 root)**
- `innodb_deadlock_detect = OFF` 에서 재현 1 을 돌리면 순환이 감지되지 않고 **타임아웃으로** 끝난다. 전역 변수라 공유 테스트 컨테이너에서 바꾸지 않는다

## 11. 다음 단계에 남기는 것

- **FK 와 wallet 선행 잠금은 본선에 유지**한다. 원장을 쓰는 새 경로는 반드시 wallet 을 먼저 잠근다
- **롤백된 트랜잭션의 재시도 ≠ 커밋 후 재전송.** 데드락 재시도는 DB 가 이미 전부 되돌린 요청을 다시 하는 것이다. S5 는 커밋까지 끝났는데 응답만 잃은 요청의 재전송이라 같은 재시도가 **중복**을 만든다 (SCENARIO 171행)
- **V2 컨텍스트의 수명.** S5 에서 멱등키 엔티티가 생기면 `ddl-auto: validate` 가 V2 기동을 막는다. 과거 컨텍스트는 `validate` 를 끄거나, 과거 재현이 쓰는 엔티티만 스캔하도록 좁혀야 한다 — S5 계획에서 정한다. S6·S7 도 "인덱스 없는 스키마" 를 같은 장치로 복원한다
- **1205 는 (기본 설정에서) DB 수준으로는 문장만 롤백한다.** S8 에서 커넥션·락 보유 시간이 길어지면 이 타임아웃을 실제로 만난다
