# 결제 모듈 학습 시나리오

> "처음부터 잘 만들지 않는다. 문제를 만들고, 원인을 찾고, 고친다."
> 이 문서는 그 반복을 어떤 순서로 할지 정한 계획서다. 각 단계의 상세 기록(원인 분석, 개선 전후 비교)은 나중에 별도 문서로 남긴다.

## 1. 도메인 스케치 (Phase 0에서 만들 것)

의도적으로 **상태 전이 보호, 잔액 동시성 제어, 요청 멱등성 장치를 넣지 않는다.** 식별자 검색에 필요한 unique 인덱스는 Phase 0부터 두되, FK는 만들지 않는다. 서비스 코드는 "읽고 → 검사하고 → 계산한 값을 저장한다" 패턴으로 통일한다. 아래 의사코드의 실행 순서와 실제 SQL 순서는 별도로 확인한다.

### 엔티티

- `merchant` : 가맹점. `id`, `name`, `api_key`
- `payment` : 결제 1건
  - `id` (PK), `payment_key` (우리가 발급), `order_id` (가맹점이 발급), `merchant_id`
  - `wallet_id` : MONEY 결제의 차감 대상 지갑. CARD는 null
  - `method` : CARD | MONEY
  - `amount`, `balance_amount` (취소 후 남은 금액)
  - `status` : READY → IN_PROGRESS → DONE → PARTIAL_CANCELED / CANCELED, 실패 시 ABORTED, 만료 시 EXPIRED
  - S9에서 `UNKNOWN` 추가: 외부 처리 결과를 확인하지 못한 상태. 조회/대사 후 최종 상태 확정. 처리 기한 초과로 실패 정책을 확정한 경우는 새 상태를 만들지 않고 `ABORTED`에 사유 컬럼(`abort_reason`, S9에서 추가)으로 구분한다
  - `approved_at`, `card_approval_no` (카드일 때)
- `payment_cancel` : 취소 이력. `payment_id`, `cancel_amount`, `reason`, `canceled_at`
- `wallet` : 머니 지갑. `id` (PK), `member_id`, `balance`
- `wallet_ledger` : 지갑 원장(append only). `wallet_id`, `type`(CHARGE/PAY/REFUND), `amount`, `payment_id`
- `settlement` : 가맹점별 일 정산. `merchant_id`, `settlement_date`, `total_amount`, `fee`, `status`. `total_amount`는 **수수료 차감 전** 금액으로, 해당 회차에 배정된 확정 승인 합계 − 확정 취소 합계다. 지급액은 컬럼으로 두지 않고 `total_amount - fee`로 계산한다

금액은 원 단위 정수, 결제·충전·취소 요청 금액은 양수로 검증한다. 원장의 `amount`는 CHARGE/REFUND가 양수, PAY가 음수이며, 초기 잔액도 CHARGE 원장으로 기록한다. 따라서 잔액은 해당 지갑 원장 금액의 합과 같아야 한다. 각 이력 테이블은 별도 PK를 갖는다.

### API (v1)

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/v1/payments` | 결제 생성 (READY). orderId, amount, method. MONEY는 memberId로 지갑을 찾아 wallet_id 저장 |
| POST | `/v1/payments/confirm` | 승인. paymentKey, orderId, amount 세 값 일치 검증 후 승인 |
| POST | `/v1/payments/{paymentKey}/cancel` | 취소/부분취소. cancelAmount |
| GET | `/v1/payments/{paymentKey}` | 조회 |
| POST | `/v1/wallets/{memberId}/charge` | 머니 충전 |
| GET | `/v1/wallets/{memberId}` | 잔액 조회 |

### 승인 처리 흐름 (naive 버전)

```
confirm(paymentKey, orderId, amount)
  @Transactional
  1. payment 조회 → status == READY 인지, orderId/amount 일치하는지 검사
  2. method == CARD  : 카드사 승인 호출 (트랜잭션 안에서)
     method == MONEY : wallet 조회 → balance >= amount 검사 → balance - amount 저장, ledger 기록
  3. payment.status = DONE, approved_at 기록
```

```
cancel(paymentKey, cancelAmount)
  @Transactional
  1. payment 조회 → DONE/PARTIAL_CANCELED 상태와 balance_amount >= cancelAmount 검사
  2. payment_cancel insert
  3. payment.balance_amount -= cancelAmount, 0이면 CANCELED 아니면 PARTIAL_CANCELED
  4. method == MONEY : wallet 에 cancelAmount 환불, ledger 기록
     method == CARD  : 카드사 취소 호출
```

## 2. Phase 0 : 기반 구축

목표: 위 도메인이 "정상 케이스에서는" 동작하는 상태.

- docker-compose: MySQL 8.0의 패치 버전 고정 (데이터 볼륨, `my.cnf` 마운트 자리 미리 확보)
- Flyway 마이그레이션 V1: 위 테이블과 다음 인덱스만 명시적으로 생성. Hibernate 자동 DDL은 사용하지 않는다. 로컬 시드는 Flyway 이력에 넣지 않고 프로파일 한정 초기화 러너로 넣는다 (상세: `docs/plan/PHASE0.md` 4.2)
  - 각 테이블 PK, `payment(payment_key)` unique, `wallet(member_id)` unique, `merchant(api_key)` unique
  - **FK는 생성하지 않는다.** 원장 INSERT의 FK 검사 락이 S1/S2의 차감 유실 실험에 섞이는 것을 막는다. `wallet_ledger.wallet_id → wallet.id` FK는 S4에서 처음 추가
  - **payment의 `merchant_id`, `order_id`, `(merchant_id, order_id)` 인덱스는 S6 이전에 만들지 않는다.** 가맹점별 주문 유일성은 도메인상 필요하지만, 제약 도입은 S6의 개선 단계로 미룬다
- Spring Data JPA + 엔티티 + 레이어드 패키지 (`api` / `application` / `domain` / `infrastructure`) — 이후 #21 에서 업무별 패키지(`com.sunm2n.pay.<업무>.<계층>`)로 재배치했다. 현재 구조는 [STRUCTURE.md](STRUCTURE.md)
- `CardApprovalClient` 인터페이스 + `FakeCardApprovalClient` (항상 성공, 승인번호 발급)
- 정상 흐름 통합 테스트 (Testcontainers MySQL): 생성 → 승인 → 부분취소 → 조회
- k6 스크립트 뼈대 (`load/`): 결제 생성 + 승인 반복

Phase 0 완료 기준: 정상 케이스 통합 테스트 통과, 서로 다른 CARD 결제를 생성·승인하는 k6 100 VU 1분 테스트에서 예상 밖 에러 0. MONEY의 공유 지갑 경쟁은 S2에서 다룬다. 정상 흐름에서는 승인 횟수, 잔액·원장 합계, 취소 합계·잔여 금액도 함께 검증한다.

### 실험 실행 시 주의사항

- 재현 테스트와 개선 후 회귀 테스트를 구분한다. 각 실험에 **마이그레이션 버전, 서비스 구현, 격리 수준, 인덱스/FK, 유지·제거할 잠금, 동기화 지점**을 기록한다. 과거 실패 재현은 전용 DB를 해당 버전으로 초기화하고, 최신 스키마를 공유하지 않는다.
  - **좁은 예외**: additive 하고 `DEFAULT`가 있으며 **재현 경로의 엔티티에 매핑되지 않는** 컬럼 추가는 최신 스키마를 공유해도 된다. 재현이 그 컬럼을 읽지도 쓰지도 않으므로 같은 결과를 낸다. 예외를 적용하면 그 마이그레이션 이후에도 과거 재현이 green인지 확인해 근거를 남긴다 (S2의 V2 `wallet.version`: `docs/phase1/S2.md` 7.1).
- 동시에 시작시키는 것만으로 결과를 보장하지 않는다. 두 요청의 조회 완료, 두 INSERT 완료 등 필요한 시점을 latch/barrier로 맞춘다. 개선된 코드에서는 먼저 락을 잡은 요청만 진행할 수 있으므로, 실패 재현용 barrier를 그대로 적용해 테스트 자체가 멈추지 않게 한다.
- 이 교재의 동시성 테스트 메서드에는 `@Transactional`을 붙이지 않는다. 초기 데이터를 먼저 커밋하고 작업 스레드별로 독립 트랜잭션을 시작한다. 테스트 스레드의 트랜잭션은 작업 스레드로 전파되지 않는다.
- 낙관적 락 예외는 API 호출·flush·commit에서 발생할 수 있다. 실패한 트랜잭션 안에서 반복하지 않고, 바깥 계층에서 새 트랜잭션으로 재시도한다. Spring Retry를 쓰면 retry advice가 transaction advice를 감싸는지 확인한다.
- JPA의 코드 순서와 SQL 순서는 다를 수 있다. Hibernate의 INSERT/UPDATE flush 순서와 식별자 생성 전략을 확인한다. 잠금 실험은 명시적 SQL 또는 flush 제어로 실제 순서를 고정한다.
- JPA 1차 캐시가 DB 재조회를 생략할 수 있다. S7의 반복 읽기는 JdbcTemplate 스칼라 조회를 기본으로 사용한다. 엔티티로 관찰할 때는 별도 읽기 실험에서 clear 후 재조회하고 SQL 로그로 확인한다.
- 조건부 UPDATE와 JPA 엔티티를 혼용하면 영속성 컨텍스트의 상태가 DB와 달라질 수 있다. 갱신 전 flush와 갱신 후 clear/재조회 범위를 정해 오래된 엔티티가 상태를 덮어쓰지 않게 한다.
- Spring 기본 프록시 방식의 자기 호출은 트랜잭션 경계를 만들지 않는다. 또한 기존 트랜잭션에 참여하면 내부 메서드의 isolation 설정이 기본적으로 무시된다. 경계 분리와 격리 수준 변경은 새 트랜잭션이 실제 시작되는지 확인한다.
- `spring.jpa.open-in-view=false`를 Phase 0부터 고정한다. 풀 크기, 커넥션 획득 타임아웃, 외부 호출 타임아웃을 명시하고 실제 세션의 격리 수준도 확인한다.
- 공통 불변식: 지갑 잔액은 원장 합계와 일치하고 음수가 아니어야 한다. 승인된 결제의 취소 합계는 승인금액 이하이며 `balance_amount = amount - 취소 합계`여야 한다. 실패·재시도 후에도 이 조건을 검증한다.

## 3. Phase 1 : 단일 서버에서 겪는 문제들

각 시나리오는 아래 형식을 따른다.

- **전제**: 스키마 버전·구현·격리 수준. 누적 개선 상태인지 독립 비교 실험인지
- **재현**: 어떤 요청을 어떤 동기화 지점에 맞춰 동시에 보내면 문제가 나는가
- **관찰**: 무엇을 보고 문제라고 판단하는가 (DB 상태, 로그, INNODB STATUS 등)
- **원인**: 왜 생기는가
- **개선**: 어떻게 고치는가. 여러 선택지가 있으면 나열하고 하나를 고른 이유를 남긴다
- **완료 기준**: 깨졌던 불변식이 유지되는지, 예상한 실패 응답과 예상 밖 오류를 구분했는지
- **다음 단계에 남기는 것**: 이 해결책 때문에 뒤에서 어떤 문제가 새로 생기거나, 어떤 문제가 더 이상 안 생기는지

### S1. 중복 승인 — 같은 결제가 두 번 승인된다

- **재현**: 같은 `paymentKey`로 confirm을 N개 보낸다. naive 코드에서 모두 READY를 읽은 뒤 승인하도록 동기화한다. MONEY는 wallet 잔액 조회까지 완료한 시점을 맞춘다
- **관찰**: CARD는 Fake 승인 호출·승인번호가 여러 개. MONEY는 모두 같은 잔액을 읽었다면 잔액에는 한 번의 차감만 반영되지만 PAY 원장은 N건 쌓인다
- **원인**: READY 검사와 DONE 갱신이 원자적이지 않다. RR과 RC 모두에서 발생하며 RC 전환만으로 해결되지 않는다
- **개선 후보**
  1. 조건부 UPDATE: `UPDATE payment SET status='IN_PROGRESS' WHERE payment_key=? AND status='READY'`. affected rows가 1인 요청만 승인 진행
  2. `SELECT ... FOR UPDATE`로 payment를 잠근 뒤 검사
  3. 애플리케이션 락 / 분산 락 (적용 범위와 필요성 비교)
- **선택**: 1번. 검사와 상태 전이를 한 문장으로 원자화한다. UPDATE도 payment의 X락을 잡고 트랜잭션 종료까지 유지한다. 첫 요청이 성공 커밋하면 대기한 요청은 조건 재평가 후 0건 갱신으로 탈락한다
- **트랜잭션 경계**: S8 전까지 승인 전체는 단일 트랜잭션. 전체 롤백되면 IN_PROGRESS 변경도 취소된다. 이 단계에서 DB에 커밋된 IN_PROGRESS가 남는 것으로 설명하지 않는다
- **완료 기준**: 정상 성공 경쟁에서 외부 승인 또는 PAY 원장은 한 건. 잔액과 원장이 일치하며 후속 요청은 정해진 중복/상태 응답을 받는다
- **남기는 것**: 승인도 `payment → wallet` 순서로 잠근다. 외부 호출 동안 락과 커넥션을 보유하는 문제는 S8에서 다룬다
- **선택 확장**: READY 만료 배치와 confirm을 경쟁시킨다. `READY → EXPIRED`와 `READY → IN_PROGRESS` 중 한 전이만 성공해야 한다. 만료 기준 시각/컬럼은 확장 시 추가한다

### S2. 머니 잔액 동시 차감 — 차감이 유실된다

- **전제**: S1 적용, wallet FK·버전·선행 잠금 없음. 각각 다른 payment를 사용해 S1의 동일 결제 잠금과 분리한다
- **재현**: 잔액 10,000인 한 지갑에 각 3,000인 결제 N개를 동시에 승인한다. 모두 같은 잔액을 읽은 뒤 계산값을 저장하도록 동기화한다. 충전과 결제의 경쟁도 비교한다
- **관찰**: 결제 N건과 PAY 원장 N건이 생기지만 잔액은 7,000. 충전 갱신이 사라질 수도 있다. `wallet.balance != SUM(wallet_ledger.amount)`
- **원인**: read-modify-write의 Lost Update. 동일한 잔액에서 계산한 값을 서로 덮어쓴다
- **원자적 감산 비교 실험** (동일 시작 데이터에서 독립 실행)
  1. 검사 후 `UPDATE wallet SET balance=balance-? WHERE id=?`: 차감 유실은 사라지지만, 잔액 검사를 모두 통과한 4건이 실행되면 -2,000. 원인은 검사와 감산 사이의 비원자성
  2. `UPDATE wallet SET balance=balance-? WHERE id=? AND balance>=?`: 양수 금액에 대해 검사와 차감을 함께 원자화. affected rows가 1일 때만 성공 처리하고 payment·ledger 변경을 같은 트랜잭션에 묶는다. 이 역시 유효한 해결책
- **락 비교 실험** (naive 구현에서 각각 시작)
  - **S2-a 낙관적 락**: `wallet.version`과 `@Version`. 충돌하면 전체 트랜잭션을 롤백하고 새 트랜잭션에서 재조회·재시도
  - **S2-b 경합 관찰**: 충분한 잔액 또는 통제된 충전 조건에서 한 지갑에 요청을 몰아, 잔액 부족과 락 충돌을 구분한다. 재시도 횟수·지연·상한 초과를 측정
  - **S2-b 비관적 락**: `SELECT ... FOR UPDATE`로 잠근 뒤 잔액을 검사·변경한다. 낙관적 락과 처리량·대기·실패율 비교
- **선택**: 이후 본선은 비관적 락. 조건부 UPDATE도 해결 후보로 인정하고, 낙관적/비관적 방식의 선택 기준은 관측 결과로 설명한다
- **완료 기준**: 10,000에서 3,000 결제 4건이면 성공 3건, 잔액 1,000, PAY 원장 3건. 나머지는 잔액 부족으로 종료하며 충돌 재시도로 중복 원장이 생기지 않는다
- **남기는 것**: wallet을 먼저 잠그는 방식은 S4의 FK 락 승격 데드락도 예방한다. S4 실패 재현에서는 이 선행 잠금을 명시적으로 제거한다

### S3. 부분취소 초과 환불 — 취소 합계가 결제금액을 넘는다

- **재현**: `amount = 10,000`인 DONE CARD 결제에 7,000 부분취소를 동시에 2개. 둘 다 잔여 금액 조회를 마친 뒤 진행한다. S2의 지갑 잠금과 분리해 관찰하고, 개선 후 MONEY도 회귀 검증한다
- **관찰**: 두 취소 모두 성공, `SUM(payment_cancel.cancel_amount) = 14,000`, `balance_amount` 는 3,000 (한쪽만 반영)
- **원인**: S2 와 같은 Lost Update. 이번엔 `payment.balance_amount`
- **개선**: `SELECT ... FOR UPDATE`로 payment를 잠근 뒤 상태·잔여 금액 검사 (S2-b 결론 적용). 이 결제의 모든 취소 경로가 같은 규칙을 따르게 한다. 취소 이력 합계와 잔여 금액의 일치는 완료 후 별도 대사로 검증한다
- **완료 기준**: 7,000 취소는 한 건만 성공, 잔여 금액 3,000. CARD Fake 취소 호출은 한 번, MONEY 회귀 검증에서는 취소 합계와 환불 원장이 일치
- **남기는 것**: 취소도 `payment → wallet` 순서. S1 이후 승인과 순서가 같으며, 서로 다른 결제 A/B와 공유 지갑만으로 순환 대기가 생긴다고 가정하지 않는다

### S4. FK 락 승격 데드락 — 원장 INSERT도 지갑을 잠근다

- **전제**: S2-b의 지갑 선행 잠금을 제거한 **독립 비교 실험**. 본선의 비관적 락 구현과 분리한다. S4 마이그레이션에서 `wallet_ledger.wallet_id → wallet.id` FK를 처음 추가하고, 기존 원장에 고아 참조가 없는지 확인한다. 다른 FK는 이 단계에서 추가하지 않는다
- **재현**: 같은 지갑을 사용하는 서로 다른 MONEY 결제 두 건을 승인한다. 각 payment의 S1 CAS는 유지한다
  1. wallet은 일반 조회로 읽고, `FOR UPDATE`나 wallet UPDATE를 먼저 실행하지 않는다
  2. 각 트랜잭션이 ledger를 INSERT한다. FK 검사로 동일 부모 wallet 행의 S락을 획득한다
  3. 두 INSERT 완료를 barrier로 맞춘 뒤 각각 wallet UPDATE를 실행한다. 충분한 잔액을 두고 명시적 SQL로 실행 순서를 고정한다
- **관찰**: 두 S락은 공존하지만, X락으로 승격하려는 두 UPDATE는 상대 S락 때문에 순환 대기한다. `SHOW ENGINE INNODB STATUS`, `performance_schema.data_locks`와 `data_lock_waits`로 부모 행·락 모드 확인. `innodb_print_all_deadlocks=ON`으로 기록
- **원인**: FK 검사도 락을 잡는다. 자식 INSERT 뒤 부모 UPDATE는 S→X 승격 경쟁을 만들 수 있다. 코드 순서가 아닌 실제 SQL과 락 획득 순서로 분석한다
- **개선**: ledger INSERT 전에 wallet을 `FOR UPDATE`로 잠근다. S2-b 본선 구현으로 복귀해 `payment → wallet → ledger` 순서를 적용하고 모든 MONEY 변경 경로를 점검한다
- **재시도**: 데드락 피해 트랜잭션 전체를 새 트랜잭션에서 제한적으로 재시도한다. `innodb_deadlock_detect`와 `innodb_lock_wait_timeout`의 역할을 구분한다. 기본 데드락 감지는 타임아웃까지 기다리지 않으며, 단순 락 대기의 타임아웃은 별도 실험으로 측정한다
- **완료 기준**: 실패 실험의 실제 대기 관계 확인, 개선 후 두 결제의 잔액·원장 일치. 실패 재현용 INSERT barrier는 개선 코드에 그대로 적용하지 않는다
- **남기는 것**: FK와 지갑 선행 잠금은 이후 본선에 유지한다. 롤백된 DB 트랜잭션의 재시도와 S5의 커밋 후 클라이언트 재전송을 구분한다

### S5. 취소 재시도 중복 — 멱등키를 넣었더니 갭락 데드락

- **재현**: 10,000 결제의 3,000 취소가 커밋됐지만 응답을 받지 못해 가맹점이 같은 요청을 재전송한다. 같은 내용의 취소가 두 번 실행된다
- **관찰**: 취소 이력 두 건, 잔여 금액 4,000. 금액 상한을 지켰어도 같은 요청을 두 번 처리한 것이다
- **원인**: 요청 단위 식별자가 없다. 전체 롤백된 데드락 트랜잭션의 재시도를 이 중복의 원인으로 삼지 않는다
- **개선 1차**: `Idempotency-Key`와 `idempotency_key` 테이블. "키 조회 → 없으면 처리 → 키 저장" (check-then-insert)
- **관찰 2**: 두 요청이 키 조회를 모두 마친 뒤 처리하도록 동기화하면 중복 가능. RR과 RC 모두에서 발생하는 check-then-act 경쟁
- **개선 2차**: 키 조회에 `FOR UPDATE` 추가. 멱등 테이블만 사용하는 최소 실험에서 동일한 없는 키를 조회한다. 검색용 비유일 인덱스와 양옆의 기준 행을 두어 같은 갭을 찾도록 하고, 두 조회 완료 후 INSERT를 진행한다
- **관찰 3**: 두 트랜잭션의 X 갭락은 공존한다. 이후 각 INSERT의 insert intention 락이 상대 갭락에 막혀 데드락. 최소 실험으로 원인을 확인한 뒤 서비스에 적용했을 때 payment 잠금과의 상호작용도 기록한다
- **개선 3차 후보**
  1. `(merchant_id, operation, idempotency_key)` unique + insert-first. 먼저 키를 선점한 요청만 처리
  2. RC 전환: 해당 검색의 갭락 데드락은 줄지만, unique가 없으면 중복 처리가 다시 가능하므로 멱등성 해결책이 아니다
- **선택**: 1번. RC 전환은 S7에서 비교한다. 키 레코드에 요청 내용 식별값, 처리 상태, HTTP 상태 코드와 응답 본문을 저장한다. 같은 키에 다른 요청 내용이면 거절한다
- **트랜잭션·응답 정책**: MONEY 취소는 키 INSERT·취소·결과 저장을 한 트랜잭션으로 묶는다. 후속 INSERT는 선행 트랜잭션 종료까지 대기할 수 있다. 성공 커밋 뒤에는 저장된 응답을 반환하고, 전체 롤백 뒤에는 다시 선점할 수 있다. 대기 상한 초과는 재시도 가능한 충돌 응답으로 처리한다. unique 위반 후 기존 결과 읽기는 실패 트랜잭션 밖의 새 트랜잭션에서 수행한다
- **범위**: 이 단계의 최종 정합성 검증은 MONEY로 수행한다. CARD의 외부 취소 성공은 DB 롤백으로 취소되지 않으므로, 분리 커밋된 처리 중 상태와 복구는 S8/S9에서 다룬다
- **완료 기준**: 같은 키의 순차·동시 재요청에서 취소 한 건, MONEY 환불 한 건, 완료 응답 동일. 다른 요청 내용은 거절. 롤백/대기 상한 초과도 검증
- **남기는 것**: S7에서 과거 갭락 실험을 재실행할 때는 unique 도입 전 스키마를 별도로 복원한다

### S6. 인덱스 없는 조건의 락 — 전혀 다른 결제끼리 서로 막힌다

- **전제**: payment의 merchant_id/order_id 검색 인덱스와 merchant FK는 아직 없다. S4에서 추가한 wallet_ledger FK와 구분한다
- **재현**: `WHERE merchant_id=? AND order_id=? FOR UPDATE`로 조회/취소하는 API를 추가한다. 서로 다른 가맹점·결제를 준비하고 각 요청에는 다른 멱등키를 사용한다. CARD Fake로 공유 지갑 경합도 제외한다
- **관찰**: 풀스캔 여부는 `EXPLAIN`, 스캔에 따른 행·갭 잠금과 대기는 `data_locks`/`data_lock_waits`로 확인한다. 지연과 잠금 개수를 기록하며 완전 직렬화 여부를 측정한다
- **원인**: 적절한 인덱스가 없으면 RR의 locking read가 넓은 범위를 스캔하고 잠근다. 최종 결과 행 수만으로 잠금 범위를 판단하지 않는다
- **개선 비교**: 인덱스 없음 → `merchant_id` 단일 인덱스 → `(merchant_id, order_id)` 복합 unique. 각 실행 계획과 잠금 범위를 비교한다. unique 추가 전 중복 주문 데이터를 정리한다. slow query log와 `long_query_time`도 사용한다
- **완료 기준**: 서로 다른 결제의 경합 감소 확인, 주문 유일성 검증. 단일 인덱스는 가맹점 범위로 좁힐 수 있지만 최종 선택은 복합 unique
- **남기는 것**: S7에서 인덱스 없는 실험 스키마를 복원해 UPDATE와 SELECT FOR UPDATE를 RR/RC로 비교한다. RC에서도 locking read가 스캔 중 이미 잠긴 행을 만나면 대기할 수 있다

### S7. 격리레벨 조정 — READ COMMITTED로 내리고 무엇이 달라지는지 본다

- **동기**: 갭락·범위 잠금과 읽기 일관성의 차이를 직접 확인한다. 일반 집계 SELECT가 범위 조건이라는 이유만으로 넥스트키 락을 잡는다고 가정하지 않는다
- **작업**: `my.cnf`의 `transaction_isolation = READ-COMMITTED` 적용 후 연결을 갱신하고 실제 세션 값을 확인한다. 바이너리 로그는 ROW인지 확인한다. MySQL 8.0 기본값이 ROW이며 `binlog_format`은 8.0.34부터 deprecated이므로 필수 변경 항목으로 취급하지 않는다
- **관찰**
  - S5의 unique 도입 전 독립 실험: 없는 키 조회의 갭락 데드락은 사라지지만 중복 INSERT는 가능. RC에서도 FK·중복키 검사에 필요한 갭락까지 모두 사라지는 것은 아니다
  - S6의 인덱스 없는 독립 실험: UPDATE는 RC의 semi-consistent read와 불일치 행 락 해제 효과를 관찰한다. SELECT FOR UPDATE는 이미 잠긴 행을 스캔할 때 여전히 기다릴 수 있다. 동일 데이터와 선행 잠금에서 둘을 비교한다
  - 비잠금 스칼라 조회 사이에 다른 트랜잭션의 커밋을 넣어 non-repeatable read를 관찰한다. `payment_cancel` 건수 조회에서도 같은 방식으로 팬텀을 확인한다
- **개선**: RC 전환 자체를 정합성 해결책으로 삼지 않는다. 검증과 변경은 조건부 UPDATE 또는 필요한 행 잠금으로 보호하고, 여러 조회의 일관된 시점이 필요하면 별도 RR 집계 트랜잭션을 사용한다
- **완료 기준**: 조회별 결과·잠금 차이를 설명하고, S1~S6 개선 구현의 불변식이 RC에서도 유지됨을 확인
- **남기는 것**: 이후 본선은 RC. S10에서 특정 집계만 RR로 실행해 대비한다

### S8. 커넥션 풀 고갈 — 외부 호출을 트랜잭션 안에서 하면 생기는 일

- **재현 1 (대기 증가)**: 풀 크기 10, Fake 카드사 지연 2초를 명시하고 서로 다른 카드 결제를 동시 50개 승인한다. 외부 호출 외 비용을 무시하면 처리율은 약 5건/초이고 한 번의 50건은 약 10초에 처리되므로, 이것만으로 30초 획득 타임아웃을 예상하지 않는다
- **재현 2 (획득 실패)**: k6의 도착률 제어로 처리율을 지속 초과시키거나, 충분히 큰 일시적 요청 폭주/짧은 획득 타임아웃을 설정한다. 사용한 부하 모델과 실제 도착률·대기 시간을 기록한다
- **관찰**: Hikari active/pending, 커넥션 획득 시간·실패, 카드·머니·조회 API 지연. `SHOW PROCESSLIST`와 활성 트랜잭션을 함께 확인한다. Sleep 표시만으로 커넥션 점유 원인을 확정하지 않는다
- **원인**: 외부 응답 대기 동안 열린 트랜잭션이 커넥션과 락을 보유한다. 카드 승인뿐 아니라 같은 풀의 다른 요청에도 대기가 전파된다
- **개선**
  1. CARD 승인: `READY → IN_PROGRESS` 커밋(tx1) → 외부 호출(tx 없음) → 결과 반영(tx2)
  2. 풀 크기, DB `max_connections`, 서버 자원과 실제 점유 시간을 함께 측정한다. 획득 타임아웃과 외부 connect/read timeout을 명시한다
  3. MONEY 승인은 외부 호출이 없으므로 단일 트랜잭션을 유지한다
- **CARD 취소에도 적용**: 취소 작업의 금액·거래번호·처리 중 상태를 tx1에 기록하고 외부 취소 후 tx2에서 결과를 확정한다. 결제별 미완료 카드 취소는 한 건만 허용하는 방식으로 시작한다. 처리 중/상태 불명 작업이 있으면 다른 취소를 거절하고, 같은 키 재요청은 진행 중 충돌 응답 또는 저장된 완료 응답을 반환한다. 스키마·커밋 경계는 이 단계의 상세 문서에 정의한다
- **완료 기준**: 외부 지연 중 커넥션 점유 시간 감소와 다른 API의 지연 개선 확인. 승인/취소 중복 실행·초과 취소 방지가 경계 분리 후에도 유지
- **남기는 것**: 커밋된 IN_PROGRESS/취소 작업이 남은 채 서버가 죽거나 결과 저장이 실패할 수 있다. 외부 호출은 분리 전에도 DB와 원자적이지 않았지만, 이제 복구할 중간 상태를 명시적으로 보관한다

### S9. 외부 타임아웃 후 상태 불명 — 승인은 됐는데 우리는 실패로 안다

- **준비**: Fake를 WireMock 컨테이너로 교체한다. 지연·5xx·응답 유실을 정의하고, 거래번호별 승인/취소 완료 상태와 조회 응답을 모델링한다. 단순 요청 수신 로그를 승인 완료 증거로 삼지 않는다
- **재현**: 외부 승인은 완료됐지만 응답이 read timeout 뒤에 도착한다. naive 오류 처리에서는 ABORTED로 기록한다. 추가로 외부 성공 직후 DB 결과 저장 실패와 서버 종료도 주입한다
- **관찰**: 외부 상태 조회는 승인 완료인데 우리 DB는 ABORTED 또는 IN_PROGRESS. 고객·가맹점이 확인하는 결과가 어긋난다
- **원인**: 타임아웃은 실패 확정이 아닌 결과 불명이다. DB 롤백으로 외부 승인을 되돌릴 수 없다
- **개선**
  1. 불명 결과는 UNKNOWN으로 기록하고 외부 거래 조회 후 확정한다. 동기 재조회 실패 시 스케줄러 대사. 오래된 IN_PROGRESS도 복구 대상에 포함
  2. 외부 요청은 동일 작업에 동일 거래번호를 사용하고 상대 시스템의 멱등 계약을 확인한다. 재시도 횟수·backoff·조회 주기를 정한다
  3. 요청이 전송되지 않았음이 확인된 연결 실패는 재시도 후보. read timeout이나 전송 여부가 불명확한 실패는 재조회부터 수행한다
  4. **실패 확정과 외부 결과 확인을 분리한다.** 타임아웃은 UNKNOWN으로만 기록한다. 서버가 정한 처리 기한이 지나도 외부 결과를 확정하지 못한 작업은 조건부 UPDATE로 `ABORTED`(사유: 기한 초과)를 DB에 확정한다. 가맹점에 응답이 전달됐는지는 기준으로 쓰지 않는다. HTTP 응답은 유실될 수 있어 서버가 알 수 없기 때문이다
  5. **정책**: 기한 안에 승인 성공이 확인되면 DONE으로 수렴한다. DB에 실패를 확정한 뒤 승인 성공이 확인되면 DONE으로 되돌리지 않고 보상 취소한다. 보상 취소는 S8의 카드 취소 작업 레코드로 만들어 완료까지 추적하며, 취소 자체의 실패·상태 불명도 재조회한다. 로컬에서 실패를 확정했다고 복구 대상에서 빠지는 것이 아니다
  6. **복구 경쟁의 조건부 전이**: 성공 반영은 `IN_PROGRESS`(원래 요청의 tx2)와 `UNKNOWN`(재조회 결과)에서 올 수 있다. 각 경로의 허용 상태와 작업 식별자(payment id, 거래번호)를 UPDATE 조건에 넣는다. `WHERE status='UNKNOWN'` 하나로 통일하면 정상 승인이 막힌다. 동기 HTTP 클라이언트는 read timeout 뒤에 도착한 응답을 버리므로, 실제 경쟁은 원래 요청의 tx2와 오래된 IN_PROGRESS를 집은 복구 작업, 그리고 복구 작업끼리의 중복 실행이다. 갱신 0건으로 탈락한 승인 성공은 버리지 않고 보상 취소의 증거로 넘긴다. 이미 완료된 취소를 DONE으로 되돌리지 않는다
- **CARD 취소에도 적용**: 외부 취소 성공 후 응답 유실/DB 커밋 실패를 재현한다. 미확정 작업을 실패로 지워 재취소하지 않고, 동일 작업 조회로 결과를 확정한다. 미확정 중에는 다른 취소를 허용하지 않는다
- **완료 기준**: 외부 상태와 로컬 상태가 정책에 맞게 수렴한다. 대사 재실행과 클라이언트 재전송이 추가 승인·취소를 만들지 않으며, 상태 불명은 별도 모니터링 대상에 남는다. 원래 요청의 tx2와 복구 작업이 경쟁해도 조건부 전이는 한쪽만 성공한다. 실패 확정 후 확인된 승인은 보상 취소가 완료 상태까지 도달한다
- **남기는 것**: 상태 조회·복구 스케줄러가 생긴다. S10의 금액 대사와 구분해 연결한다

### S10. 정산 배치 — 집계가 안 맞고, 배치가 온라인 결제를 막는다

- **준비**: naive 배치는 매일 새벽 가맹점별 전날 DONE/PARTIAL_CANCELED 결제를 집계해 `settlement`를 생성하고 대상 payment에 `settled = true`를 표시한다. 이 컬럼은 S10에서 추가하며, 이후 개선에서 승인·취소별 반영 이력으로 보완한다
- **재현 1 (집계 불일치)**: 대상 결제 ID를 고정한다. RC에서 취소 합계를 읽은 뒤 다른 트랜잭션이 부분취소를 커밋하고, 그 다음 잔여 금액 합계를 읽도록 동기화한다. `승인금액 합계 = 취소 합계 + 잔여 금액 합계`가 깨지는 것을 관찰한다. 같은 순서를 RR의 비잠금 집계로 비교한다
- **재현 2 (배치가 온라인을 막음)**: 대상 10만 건을 한 트랜잭션에서 `UPDATE payment SET settled=true WHERE ...`. 그동안 취소 요청이 lock wait. undo 로그 증가, 배치 실패 시 롤백 시간
- **재현 3 (이중 실행)**: 배치를 두 번 돌리면 정산이 두 번 생긴다
- **관찰**: 아래 세 식으로 불일치를 판정한다. '정산 총액 vs 원장 합계' 한 식은 쓰지 않는다. 지갑 원장에는 충전이 섞이고, CARD 결제에는 지갑 원장이 없으며, 정산에는 수수료와 반영 회차 차이가 있기 때문이다
  - 지갑 잔액 = 해당 지갑 원장 합계
  - 결제 잔여 금액 = 승인금액 − 확정 취소 합계
  - 정산 `total_amount` = 해당 회차에 배정된 확정 승인 합계 − 해당 회차에 배정된 확정 취소 합계. 지급액 = `total_amount − fee`
  - 잠금·purge: `Innodb_row_lock_waits`와 `information_schema.innodb_metrics`의 `trx_rseg_history_len`을 관찰한다. 긴 읽기 트랜잭션을 추가한 비교에서 purge 지연도 확인한다. 취소 API p99 급증
- **개선**
  1. 집계는 **마감 시각(cut-off)** 기준으로, 마감 이후 취소는 다음 정산에 반영 (차감 정산)
  2. 집계용 **새 트랜잭션**을 RR로 시작한다. Spring은 `@Transactional(isolation = Isolation.REPEATABLE_READ)`이 새 트랜잭션을 시작하도록 경계를 구성한다. 기존 RC 트랜잭션 참여로 대체하지 않는다. 직접 SQL 실험에서는 `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` 후 `START TRANSACTION WITH CONSISTENT SNAPSHOT`. 후자는 RR 설정을 대신하지 않으며 스냅샷을 시작 시점에 만든다. Spring 관리 트랜잭션 안에서 START TRANSACTION을 중첩 실행하지 않는다
  3. 집계 대상 승인·취소 이력과 정산 반영 이력을 연결한다. 과거 정산한 결제가 오늘 취소된 경우도 차감 대상으로 잡아야 하므로 payment의 `settled` 하나로 완료 여부를 판단하지 않는다. 마감 대상 확정 후 처리 표시는 청크(1,000건) 단위 트랜잭션으로, PK 커서와 재시작 지점을 기록한다
  4. `settlement (merchant_id, settlement_date)` unique 제약 + 배치 실행 이력 테이블로 멱등 실행
  5. 원장(`wallet_ledger`, `payment_cancel`) 합계와 스냅샷 컬럼(`balance`, `balance_amount`) 을 비교하는 **일일 대사 잡**. 불일치가 나오면 S2~S9 중 어디서 샜는지 추적하는 연습
- **완료 기준**: 마감 전후 취소, 과거 정산 결제의 후속 취소, 청크 중단 후 재시작, 이중 실행에서도 누락·이중 반영 없음. 일관된 스냅샷은 읽기 시점을 맞추는 수단이며 업무상 마감 대상 확정·늦게 커밋된 거래의 처리 규칙은 별도로 정의한다
- **남기는 것**: Phase 2에서 배치가 여러 서버에 뜨더라도 S10의 멱등성은 유지돼야 한다. 실행 잠금은 불필요한 중복 작업을 줄이는 별도 장치다

### S11. (선택) 서버 파라미터 종합 점검

시나리오라기보다 S4~S10 에서 건드린 파라미터를 한 번에 정리하고 부하 테스트로 전후를 비교하는 단계.

- `transaction_isolation`, 바이너리 로그 ROW 설정 확인 (S7)
- `innodb_lock_wait_timeout`, `innodb_deadlock_detect`, `innodb_print_all_deadlocks` (S4)
- `long_query_time`, `slow_query_log`, `performance_schema` 활성화 (S6)
- `max_connections` vs HikariCP `maximum-pool-size` (S8)
- `innodb_buffer_pool_size`: 접근하는 데이터·인덱스의 작업 집합이 버퍼 풀을 초과하는 조건에서 디스크 읽기와 배치 시간을 비교. 전체 DB 크기만으로 판단하지 않는다

### Phase 1 종료 점검: API별 멱등성 범위

S5는 취소 재전송만 다룬다. 같은 문제가 충전과 결제 생성, 승인 완료 후 재요청에도 남는다. 충전은 락을 정확히 잡아도 같은 요청을 순차 재전송하면 두 번 충전된다. 모든 API에 같은 멱등키 구현을 강제하지 않고, API마다 아래 세 가지를 정한다.

| API | 식별 기준 | 같은 요청 재전송 응답 | 같은 식별자, 다른 내용 |
|---|---|---|---|
| 생성 | 주문 유일성 `(merchant_id, order_id)` unique (S6) | 기존 결제 정보로 응답 | 409 거절 |
| 승인 | 결제 상태 (S1 CAS) + paymentKey/orderId/amount 세 값 | DONE 이후 같은 세 값이면 저장된 승인 결과로 응답 | 409 거절 |
| 취소 | 요청 키 `Idempotency-Key` (S5) | 저장된 완료 응답 | 409 거절 |
| 충전 | 요청 키 `Idempotency-Key` (S5 구현 재사용, operation=CHARGE) | 저장된 완료 응답 | 409 거절 |

- **재현**: 충전 재전송, 생성 응답 유실 후 재생성, 승인 완료 후 재조회·재요청. 각각 순차와 동시 재전송을 모두 본다
- **완료 범위**: 충전은 문제를 발견하고 끝내지 않는다. 요청 식별자와 중복 방지 구현까지 이 점검에서 끝낸다. 생성·승인은 기존 장치(S1, S6)로 막히는지 확인하고 응답 규약만 추가한다
- **완료 기준**: 네 API 모두 같은 요청의 재전송이 두 번 반영되지 않고, 표의 응답을 반환하며, 공통 불변식이 유지된다

## 4. 시나리오 순서 제약 (왜 이 순서인가)

| 제약 | 이유 |
|---|---|
| Phase 0에 식별자 unique만 두고 FK는 만들지 않는다 | S1/S2에서 검색 범위 잠금과 FK 승격 데드락이 차감 유실 관찰에 섞이지 않게 한다 |
| S1 CAS는 단일 승인 트랜잭션 안에서 시작한다 | X락과 롤백 범위를 먼저 배우고, S8에서 커밋 경계를 분리한다 |
| S2는 S3보다 먼저 | 지갑에서 비교한 낙관적/비관적 방식을 결제 취소에 적용한다 |
| S4는 독립 비교 실험 | S2-b 본선의 wallet 선행 X락은 FK 승격 데드락을 막는다. 제거한 실패 구현과 복구한 개선 구현을 비교한다 |
| payment의 merchant_id/order_id 검색 인덱스는 S6에서 추가 | 초기부터 복합 unique를 두면 인덱스 부재 실험이 사라진다 |
| S5 최종 해결은 unique + insert-first | RC는 중복 방지책이 아니다. 갭락 변화는 S7에서 별도로 확인한다 |
| S6은 S7보다 먼저 | RR의 스캔·잠금을 기준으로 잡고, RC의 UPDATE와 SELECT FOR UPDATE 차이를 비교한다 |
| S8은 S9보다 먼저 | 커밋된 중간 상태와 외부 호출 경계를 만든 후 조회·복구 정책을 실습한다 |
| S7은 S10보다 먼저 | RC 집계와 별도 RR 집계 트랜잭션의 읽기 일관성을 대비한다 |
| WireMock은 S9에서 도입 | S8의 점유 시간은 지연 Fake로 측정하고, S9에서 네트워크 실패와 외부 상태를 모델링한다 |

## 5. Phase 2 : 멀티 서버 (개요만)

Phase 1이 끝나면 아래 실패 시나리오를 순서대로 다룬다. 상세 시나리오는 그때 Phase 1과 같은 형식(전제·재현·관찰·원인·개선·완료 기준)으로 다시 작성한다. 기술은 각 실패의 해결책으로만 도입한다.

1. **호출자 입장의 응답 유실**: 가맹점 서버(별도 Spring Boot 앱)가 주문 생성 → 우리 API 호출 → 응답 유실을 겪는다. Phase 1의 타임아웃·재시도·멱등성이 **호출자 입장**으로 반복된다
2. **웹훅 유실**: 승인 커밋 뒤 가맹점 통보가 실패하면 통보만 사라진다. 개선: 트랜잭셔널 아웃박스
3. **웹훅 중복 전달·순서 역전**: 아웃박스 재전송으로 같은 이벤트가 두 번 가고, 승인·취소 통보 순서가 뒤집힌다. 개선: 이벤트 ID 기반 소비자 멱등성과 결제 상태 기반 순서 판정
4. **가맹점 처리 후 응답 유실**: 가맹점이 웹훅을 처리했지만 우리가 ACK를 받지 못해 재전송한다. 3의 소비자 멱등성이 흡수해야 한다
5. **배치 이중 실행**: PG 서버 2대 + 로드밸런서에서 정산 배치가 동시에 뜬다. S10의 멱등성 재검증, DB 락 기반 스케줄러 잠금 또는 ShedLock으로 중복 작업 억제. 인메모리 상태에 의존한 보호도 검증
6. **분산 락이 정말 필요한 지점**: Redis는 필요성을 검증하는 선택 단계로 둔다. 대부분 DB 락으로 충분하다는 것을 확인하는 게 목적. 캐시와 정합성
7. **메시지 브로커**: Kafka는 아웃박스 릴레이에서 무엇을 얻으려는지(전달 보장, 소비자 분리, 재처리)를 먼저 정한 뒤 도입 여부를 결정한다

**별도 이정표** (멀티서버 실습 진척과 분리해 관리한다)

- **멀티모듈 + 헥사고널 리팩터링**: `payment-api`, `payment-domain`, `payment-infra`. 포트/어댑터로 카드사, DB 분리. Phase 1 개선 후 회귀 테스트가 그대로 통과해야 한다. 과거 결함 재현 테스트는 해당 스키마·구현을 가진 독립 환경에서 유지한다
- **CI 확장**: Testcontainers 통합 테스트는 이미 GitHub Actions(`.github/workflows/ci.yml`)에서 PR·main 푸시마다 실행된다. Phase 1 회귀 테스트를 여기에 유지하고, k6 부하 테스트를 nightly로 추가한다

## 6. 확정된 갈림길

| 갈림길 | 결정 | 이유 |
|---|---|---|
| 초기 제약 | 식별자 unique는 유지, FK는 S4에서 대상 하나만 추가 | 조회 실험을 안정시키고 FK 락은 따로 관찰 |
| S2 해결 방식 | 계산값 저장·무조건 감산·조건부 감산 비교 후 낙관적/비관적 락 비교. 이후 본선은 비관적 락 | 서로 다른 실패 원인과 대안의 선택 기준 학습 |
| S4 구성 | FK S→X 승격의 독립 실험 | 누적 개선 코드에서 자연 발생한다고 가정하지 않음 |
| S5 최종 해결 | unique + insert-first. RC 전환은 S7 | 멱등성과 격리 수준의 역할 구분 |
| 머니 결제 외부 의존 | 두지 않음 | DB 내부 정합성 실험 분리 |
| S8/S9 범위 | CARD 승인과 취소 모두 포함, MONEY는 단일 트랜잭션 유지 | 취소에도 같은 외부 상태 불일치가 발생 |
| S11 서버 파라미터 종합 점검 | 별도 단계로 유지 | 부하와 환경을 고정해 전후 비교 |
| S9 실패 확정 | 처리 기한 기준으로 ABORTED를 DB에 확정. 확정 후 확인된 승인은 보상 취소 | 응답 전달 여부는 서버가 알 수 없다 |
| 멱등성 적용 범위 | API별 식별 기준·응답 규약을 Phase 1 종료 점검에서 정리. 충전은 구현까지 | 모든 API에 같은 멱등키를 강제하지 않는다 |
| 로컬 시드 | Flyway 이력 밖 일반 SQL + 프로파일 한정 러너 | `outOfOrder=false`에서 V900 뒤의 V2가 적용되지 않는다 |

## 7. 상세 실습 문서에 남길 것

- 각 시나리오의 스키마 버전·실제 SQL·동기화 지점·부하 설정·불변식·관측 결과. 실패 재현과 개선 후 회귀 검증을 구분한다
- S5 멱등키 보존 기간, 요청 내용 비교 규칙, 저장 응답 스키마와 대기 상한. S8 이후 분리 커밋된 작업의 진행 중 응답·복구 정책
- S8/S9 카드 취소 작업 상태와 외부 거래 조회 모델, 외부 성공 후 로컬 저장 실패·복구 경쟁에 대한 조건부 상태 전이(경로별 허용 상태와 작업 식별자), 처리 기한 값과 보상 취소 추적
- Phase 1 종료 점검의 API별 멱등성 표(식별 기준, 재전송 응답, 내용 불일치 응답)와 충전 중복 방지 구현
- S10 승인·취소별 정산 반영 이력, 마감 대상 확정, 청크 재시작, 수수료·차감 정산 규칙
- READY 만료 배치와 confirm 경쟁은 S1 선택 확장으로 기록
