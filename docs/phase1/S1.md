# S1 — 중복 승인: 같은 결제가 두 번 승인된다

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 계획: [plan/S1.md](../plan/S1.md) · 선행 기록: [phase0/README.md](../phase0/README.md)

Phase 1 의 첫 실습이다. Phase 0 이 만든 naive 승인을 처음으로 무너뜨리고 조건부 UPDATE 로 고친다.

## 1. 전제

| 항목 | 상태 |
|---|---|
| 스키마 | V1 그대로. **마이그레이션을 추가하지 않았다** — CAS 는 기존 컬럼만 쓴다 |
| 제약 | FK 0건, `payment` 의 `merchant_id`/`order_id` 인덱스 없음 (유지) |
| 격리 수준 | REPEATABLE READ |
| 구현 | Phase 0 naive 누적. S1 이 첫 개선 |
| 트랜잭션 경계 | 승인 전체가 단일 트랜잭션 |
| 커넥션 풀 | `maximum-pool-size: 10` — 테스트도 같은 `application.yml` 을 쓴다 |
| 워커 수 | 5 (게이트 대기 중 커넥션을 점유하므로 풀 크기보다 작아야 한다) |

버전은 [phase0/README.md 1절](../phase0/README.md)과 같다 — MySQL 8.0.44, Spring Boot 3.5.16, Hibernate ORM 6.6.53.Final.

마이그레이션이 없으므로 과거 스키마 전용 컨테이너(`plan/PHASE0.md` 2절)는 쓰지 않았다. 재현 테스트도 공유 컨테이너에서 돌고, 실패 버전은 스키마가 아니라 **빈**으로 보존된다.

## 2. 재현

같은 `paymentKey` 로 승인 5건을 동시에 보낸다. 동기화 지점은 리포지터리 조회 **반환 직후**다.

| 결제수단 | 게이트 |
|---|---|
| CARD | `PaymentRepository.findByPaymentKey` — 모두 READY 를 읽은 시점 |
| MONEY | 위 + `WalletRepository.findById` — 모두 같은 잔액을 읽은 시점 |

동기화 장치는 테스트가 소유한다. `BeanPostProcessor` 가 리포지터리 빈을 JDK 동적 프록시로 감싼다. 프로덕션 코드에 관측 훅을 심으면 실습 대상인 naive 구현이 원래 모습을 잃기 때문이다.

`@MockitoSpyBean` 대신 직접 만든 프록시를 쓴 것은 **동기화 지점을 명시적으로 관리하기 위해서**다. 어느 메서드의 어느 시점이 지점인지가 이름 하나로 한곳에 모여 있어야 S2~S10 이 지점을 늘려 갈 때 흩어지지 않는다. 덧붙여 스파이 빈은 테스트 클래스마다 빈을 재정의해 Spring 컨텍스트를 따로 만들지만, 이 설정은 무장 전에 no-op 이라 전체 테스트가 컨텍스트 하나를 계속 공유한다. (Mockito 자체는 스텁을 미리 걸어 두고 여러 스레드가 호출하는 방식을 지원한다. 안전하지 않은 것은 호출 중에 스텁을 다시 걸거나 검증하는 쪽이다.)

게이트는 **스레드당 한 번만** 통과시킨다. 개선된 구현이 CAS 성공 후 엔티티를 재조회하면서 같은 메서드를 두 번 호출하는데, 두 번째로 barrier 에 걸리면 나머지 참가자가 오지 않아 테스트가 멈춘다.

`DuplicateConfirmReproductionTest` 는 깨진 결과를 그대로 assert 하므로 **결함이 재현될 때 green** 이다. FK 0건이나 인덱스 부재를 테스트로 고정하는 것과 같은 성격이다.

## 3. 관찰

### 3.1 CARD — 승인이 5번 일어나고 4번은 추적할 수 없다

| 항목 | 값 |
|---|---|
| 요청 5건의 결과 | **전부 성공** (아무도 거절되지 않는다) |
| `FakeCardApprovalClient` 승인 호출 | **5회** |
| 발급된 승인번호 | **5개** (전부 다름) |
| `payment.card_approval_no` | **1개** — 마지막 커밋이 이긴다 |
| 최종 `status` | DONE |

실물 카드사였다면 승인 4건이 카드사에는 남고 우리 DB 에는 없는 상태다. 대사할 근거조차 없다.

### 3.2 MONEY — 차감은 한 번, 원장은 다섯 건

잔액 10,000 인 지갑에 3,000 짜리 결제 하나를 5번 승인시켰다.

| 항목 | 값 |
|---|---|
| 요청 5건의 결과 | 전부 성공 |
| `wallet.balance` | **7,000** — 모두 같은 잔액을 읽고 계산값을 저장했으므로 차감은 한 번만 반영된다 |
| PAY 원장 | **5건** (각 −3,000) |
| 원장 합계 | 10,000 − 15,000 = **−5,000** |

`wallet.balance(7,000) ≠ SUM(ledger)(−5,000)` — **불변식 1 이 깨진다.** 이것이 S1 이 무너뜨리는 것이다.

여기서 잔액이 한 번만 줄어드는 것은 S2(차감 유실)와 같은 원인이지만, S1 이 관찰하는 것은 **결제 한 건이 여러 번 승인되어 원장이 여러 건 남는 것**이다. S2 는 서로 다른 결제들이 같은 지갑을 놓고 경쟁한다.

### 3.3 SQL 순서 — 직렬화는 UPDATE 에서만 일어난다

`org.hibernate.SQL` 로그다. 코드 순서가 아니라 실제 SQL 순서로 본다 (SCENARIO 98행).

```
pool-3-thread-1  select ... from payment where payment_key=?     ┐
pool-3-thread-5  select ... from payment where payment_key=?     │ 5건이 모두
pool-3-thread-2  select ... from payment where payment_key=?     │ 막힘 없이
pool-3-thread-4  select ... from payment where payment_key=?     │ 통과한다
pool-3-thread-3  select ... from payment where payment_key=?     ┘
pool-3-thread-1  select ... from wallet where id=?               ┐ 잔액도
pool-3-thread-5  select ... from wallet where id=?               │ 5건 모두
...                                                              ┘ 같은 값을 읽는다
pool-3-thread-5  insert into wallet_ledger ...                   ┐
pool-3-thread-2  insert into wallet_ledger ...                   │ 원장 5건
...                                                              ┘
pool-3-thread-5  update payment set ... where id=?               ┐ 여기서만
pool-3-thread-2  update payment set ... where id=?               │ 직렬화된다
...                                                              ┘
pool-3-thread-5  update wallet set balance=? where id=?
pool-3-thread-1  update wallet set balance=? where id=?
```

두 가지가 보인다.

1. **`SELECT` 는 아무도 막지 않는다.** REPEATABLE READ 의 일반 SELECT 는 consistent non-locking read 라 락을 잡지 않는다. 그래서 5개가 모두 READY 를 읽는다
2. **flush 순서는 원장 INSERT → `update payment` → `update wallet`** 이고 모든 스레드에서 같다. 승인이 `payment → wallet` 순서로 잠근다는 것이 여기서 확인되고, 이 순서가 S2·S4 의 전제가 된다

**데드락에 대해서는 이 실험이 말할 수 있는 범위를 넘지 않는다.** FK 가 없고 모든 워커가 같은 코드 경로를 타는 이번 조건에서는 데드락이 **관측되지 않았다**. 다만 이것은 Hibernate 가 정한 flush 순서에 기댄 관측이지 보장이 아니다. SCENARIO 98행이 경고하듯 코드 순서와 SQL 순서는 다를 수 있고, 잠금 순서를 실제로 고정하려면 명시적 SQL 이나 flush 제어가 필요하다. 원장 INSERT 가 지갑을 잠그기 시작하는 S4(FK 승격)에서 이 조건이 달라진다

## 4. 원인

READY 검사와 DONE 갱신이 원자적이지 않다.

- 검사: 잠금 없는 `SELECT`. 다른 트랜잭션의 진행을 막지도, 알아채지도 못한다
- 갱신: flush 시점의 `UPDATE ... WHERE id=?`. X 락을 잡으므로 서로 **직렬화되지만**, 이미 다섯 요청 모두 "나는 READY 를 봤다"는 판단을 끝낸 뒤다. 마지막에 커밋한 값이 남는다

읽기가 잠금을 잡지 않으므로 RR 과 RC 모두에서 동일하게 발생한다. **격리 수준 전환은 해결책이 아니다.**

## 5. 개선

### 5.1 후보 비교

| 후보 | 내용 | 평가 |
|---|---|---|
| **1. 조건부 UPDATE** | `UPDATE payment SET status='IN_PROGRESS' WHERE payment_key=? AND status='READY'` 로 검사와 전이를 한 문장으로 묶고, 갱신 건수 1 인 요청만 진행 | **선택.** 허용 상태와 전이가 **한 SQL 문장 안에** 있다. 무엇을 보장하는지가 코드의 실행 순서가 아니라 문장 자체에 드러나고, 추가 인프라도 없다 |
| 2. `SELECT ... FOR UPDATE` | 첫 조회에 잠금을 결합하고 메모리에서 검사 | 보장 수준은 같고 **SQL 문장은 오히려 적다**(5.2 참고). 다만 잠금과 검사가 나뉘어 있어 보장이 문장이 아니라 코드의 순서에 의존한다 — "잠갔는데 검사를 빠뜨린" 구현이 문법적으로 가능하다. 검사할 것이 많아 한 문장으로 표현하기 어려운 경우에 어울리며, 여기서는 그렇지 않다 |
| 3. 애플리케이션 락 / 분산 락 | 승인 진입을 키 단위로 직렬화 | 단일 서버에서는 DB 가 이미 해 주는 일을 밖에서 다시 하는 것이다. 락 서버라는 장애 지점과 TTL·소유권 문제가 새로 생긴다. 분산 락이 정말 필요한 지점은 Phase 2 에서 따로 검증한다 |

1번은 SCENARIO 124행에서 이미 확정된 선택이고, 위는 그 근거를 남긴 것이다. 2번을 실제로 구현해 비교하지는 않았다.

### 5.2 구현

승인 구현을 `PaymentConfirmer` 로 뽑아 **실패 버전과 개선 버전을 코드에 공존**시켰다. 과거 실습 기록을 언제든 다시 실행할 수 있어야 하므로 결함을 품은 구현을 지우지 않는다 (`plan/PHASE0.md` 2절). 두 구현의 차이는 **상태 전이를 어떻게 확정하느냐** 하나뿐이고, 조회·검증·승인 본문은 `PaymentSupport` 가 공유한다.

```
소유권 조회 → 상태 사전 검사 → orderId/amount 검사 → [상태 전이] → 승인 본문 → DONE
                                                      naive: 없음
                                                      CAS  : 조건부 UPDATE
```

**상태 사전 검사를 CAS 앞에 남긴 이유.** 조건부 UPDATE 만으로도 경쟁은 막힌다. 그런데 사전 검사를 없애면 *이미 DONE 인데 요청 값도 틀린* 경우의 응답이 `INVALID_PAYMENT_STATUS` 에서 `PAYMENT_MISMATCH` 로 바뀐다. 기존 오류 우선순위를 보존하려고 남겨 둔 것이고, 경쟁의 최종 판정은 어디까지나 CAS 가 한다.

**조건부 UPDATE 는 네이티브 SQL 로 적었다.** 이 문장 자체가 실습 대상이라 어떤 SQL 이 나가는지 JPQL 번역에 가려지면 안 된다. `status` 는 `VARCHAR` 이고 엔티티도 `@Enumerated(STRING)` 이라 문자열 리터럴과 표현이 일치한다.

갱신 건수는 matched 든 changed 든 같다. WHERE 가 `READY` 이고 SET 이 `IN_PROGRESS` 라 조건에 걸린 행은 반드시 값이 바뀌므로, 드라이버의 `useAffectedRows` 설정에 결과가 좌우되지 않는다.

**이 선택에는 비용이 있다.** CAS 경로는 사전 조회 `SELECT` → 조건부 `UPDATE` → 재조회 `SELECT` 로 문장이 셋이다. `FOR UPDATE` 였다면 첫 조회가 잠금을 겸해 둘로 끝난다. 왕복 수로는 CAS 가 불리하며, 위에서 1번을 고른 근거는 왕복이 아니라 **조건과 전이를 한 문장으로 표현한다는 것**이다.

`@Modifying(flushAutomatically = true, clearAutomatically = true)` 를 붙였다. 이 UPDATE 는 영속성 컨텍스트를 거치지 않으므로 비우지 않으면 이미 로드한 엔티티가 옛 상태를 들고 있게 된다. flush 쪽은 반대로 아직 반영되지 않은 변경이 이 UPDATE 뒤로 밀려 순서가 뒤집히는 것을 막는다.

### 5.3 락 관측

로컬 MySQL 에서 조건부 UPDATE 가 잡는 락을 직접 봤다. `performance_schema.data_locks` (다른 세션이 같은 문장을 실행 중):

```
index_name                lock_type  lock_mode        lock_status  lock_data
NULL                      TABLE      IX               GRANTED      NULL
PRIMARY                   RECORD     X,REC_NOT_GAP    GRANTED      55889
uk_payment_payment_key    RECORD     X,REC_NOT_GAP    GRANTED      's1-lock-probe', 55889
uk_payment_payment_key    RECORD     X,REC_NOT_GAP    WAITING      's1-lock-probe', 55889
```

- `REC_NOT_GAP` — **갭 락이 없다.** unique 인덱스에 대한 동등 조건이고 대상 행이 실제로 존재하기 때문이다. 갭 락은 S5 의 주제다
- 잠기는 것은 **두 곳**이다. 조건을 평가한 secondary unique index (`uk_payment_payment_key`) 와 실제로 갱신할 clustered index (`PRIMARY`)
- 두 번째 세션은 secondary index 에서 **WAITING** 이다

승자가 커밋한 뒤 탈락자가 어떻게 되는지도 확인했다.

```
winner_affected_rows = 1
loser_affected_rows  = 0     (2,005 ms 대기 후)
```

탈락자는 락을 기다렸다가, 풀린 뒤 **조건을 다시 평가해서** 0 건이 된다. 이것이 "첫 요청이 성공 커밋하면 대기한 요청은 조건 재평가 후 0건 갱신으로 탈락한다"(SCENARIO 124행)의 실물이다.

### 5.4 탈락 판정은 갱신 건수로만 내린다

탈락한 요청에게 "현재 상태가 무엇인지" 알려 주고 싶어진다. **그럴 수 없다.**

탈락한 요청은 아무 행도 바꾸지 않았고, REPEATABLE READ 의 스냅샷은 첫 조회 시점에 고정돼 있다. 그래서 승자가 이미 커밋한 뒤에도 **평범한 재조회는 여전히 `READY` 를 돌려준다.** 그 값으로 "READY 라서 승인할 수 없습니다" 같은 메시지를 만들면 거짓말이 된다.

`DuplicateConfirmRegressionTest.loserCannotLearnTheWinnerStatusByReading` 이 이 순서를 테스트로 고정한다.

| 순서 | 관측 |
|---|---|
| 1. 트랜잭션 안에서 첫 조회 | `READY` — 여기서 스냅샷이 확정된다 |
| 2. 다른 트랜잭션이 승인하고 커밋 | — |
| 3. 조건부 UPDATE | **0 건** — 현재 읽기(current read)라 최신 커밋 값을 다시 평가한다 |
| 4. 평범한 재조회 | **`READY`** — 스냅샷은 1번 시점 그대로다 |
| 5. 트랜잭션 밖에서 조회 | `DONE` |

3번과 4번이 같은 트랜잭션 안에서 서로 다른 것을 본다. 잠금 읽기/DML 은 최신 커밋 값을 보고, 일반 SELECT 는 스냅샷을 본다. **탈락을 확정하는 근거는 갱신 건수 0 하나뿐이다.**

`clearAutomatically` 도 스냅샷과 무관하다. 영속성 컨텍스트를 비울 뿐 DB 의 읽기 시점을 갱신하지 않는다. **재조회는 CAS 성공 경로 전용**이며, 자기 트랜잭션의 변경은 자기에게 보이므로 `IN_PROGRESS` 상태의 결제를 얻는다.

### 5.5 응답

탈락은 **409 `INVALID_PAYMENT_STATUS`** 다. 새 에러 코드를 만들지 않았고, 메시지에 상태를 싣지 않는다 (5.4).

"DONE 이후 같은 세 값이면 저장된 승인 결과로 응답"하는 멱등 규약(SCENARIO 278행)은 **Phase 1 종료 점검**의 범위다. S1 은 두 번 승인되지 않는 것까지만 책임진다.
