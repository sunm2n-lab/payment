# S5 — 취소 재전송 중복: 멱등키를 넣었더니 갭락 데드락

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 계획: [plan/S5.md](../plan/S5.md) · 선행 기록: [phase1/S4.md](S4.md) · 이슈: #29

S4 는 **롤백된** 트랜잭션을 새 트랜잭션에서 다시 하는 재시도였다. DB 가 이미 전부 되돌린 요청이라 다시 해도 안전했다. S5 는 반대다. 취소가 **커밋까지** 끝났는데 가맹점이 응답을 받지 못해 같은 요청을 다시 보낸다. 서버에는 두 요청을 같은 요청으로 알아볼 식별자가 없다.

S3 의 잠금은 금액 상한을 지킨다. 두 번째 요청도 상한 안이라 정당한 요청처럼 통과한다. 막아야 할 것은 초과가 아니라 **같은 요청의 두 번째 실행**이다. 키를 넣고(1차) → 동시 요청에서 뚫리고 → 조회를 잠그고(2차) → 갭락 데드락을 만나고 → unique + insert-first 로 갔다(3차).

## 1. 전제

| 항목 | 상태 |
|---|---|
| 스키마 | **V4** `idempotency_key` — 최종 컬럼 + 비유일 검색 인덱스 `idx_idempotency_key_lookup`. **V5** 그 인덱스를 `uk_idempotency_key (merchant_id, operation, idempotency_key)` 로 교체 (ALTER 한 문장) |
| 과거 재현 | 1·2차는 처음부터 **V4 DB**(`payment_v4`) 에서 돈다. S1~S3 은 계속 V2, 0단계는 최신 (1.1) |
| 격리 수준 | REPEATABLE READ |
| 구현 | 취소는 S3 본선(`PessimisticLockPaymentCanceller`). 1·2차 실패 배선도 이 canceller 를 그대로 쓴다 |
| 트랜잭션 경계 | 키 INSERT·취소·결과 저장이 한 트랜잭션 (분리는 S8) |
| 결제수단 | 최종 정합성은 **MONEY** 로 본다. CARD 외부 취소는 DB 롤백으로 되돌아가지 않는다 (S8/S9) |
| 서버 설정 | 기본값 — `innodb_deadlock_detect=ON`, `innodb_lock_wait_timeout=50`, `innodb_rollback_on_timeout=OFF` |

버전은 [phase0/README.md 1절](../phase0/README.md)과 같다 (MySQL 8.0.44, Hibernate 6.6.53, Spring Boot 3.5.16).

### 1.1 과거 컨텍스트가 둘이 됐다

S4 의 V2 베이스에서 등록 방식을 떼어 `PastSchemaDatabase.register(registry, database, flywayTarget)` 로 옮겼다. 각 베이스는 자기 `@DynamicPropertySource` 에서 값을 넘긴다. 버전을 공유 static 상태로 두지 않으므로 Spring 컨텍스트 캐시 키가 버전별로 갈린다.

```
support
├── MySqlTestContainer
├── PastSchemaDatabase        등록 헬퍼
├── AbstractV2SchemaTest      payment_v2, target=2   S1~S3 재현
└── AbstractV4SchemaTest      payment_v4, target=4   S5 1·2차 재현 (S7 도 쓴다)
```

- **1·2차 재현은 처음부터 V4 에 뒀다.** V5 를 넣는 커밋에서 빨개지지 않았다 (S4 의 교훈)
- `ddl-auto: validate` 는 과거 컨텍스트에서도 유지했다. 키 저장소가 JDBC 전용이라 V2 에 없는 테이블을 매핑하는 엔티티가 생기지 않았다. S4 가 넘긴 "과거 컨텍스트에서 validate 를 끌지" 는 이번엔 필요 없었다
- 컨텍스트 전제 테스트가 셋이다. `V2SchemaContextTest`, `V4SchemaContextTest`(DB 이름, V4, 검색 인덱스 비유일, `ascii_bin`), `LatestSchemaContextTest`(컨테이너 기본 DB, 마지막 마이그레이션, `uk_idempotency_key` 만, `ascii_bin`)

## 2. 재현

준비: 충전 100,000 → MONEY 결제 10,000 승인 (DONE, 잔여 10,000).

| 단계 | 배선 | 동기화 | 스키마 | 테스트 |
|---|---|---|---|---|
| 0 | 본선, 키 없음. 3,000 취소를 **순차로** 두 번 (HTTP) | — | 최신 | `CancelResendReproductionTest` |
| 1차 | `CheckThenInsertIdempotentCanceller` — 키 조회(잠금 없음) → 취소 → 키 저장 | `KEY_LOOKED_UP` ×2 | V4 | `CheckThenInsertReproductionTest` |
| 2차-① | 멱등 테이블만, JDBC 세션 둘. 기준 행 `k10`·`k30` 사이의 없는 `k20` 을 둘 다 `FOR UPDATE` → 둘 다 INSERT | 두 조회 뒤 동시 INSERT | V4 | `GapLockDeadlockReproductionTest` |
| 2차-② | `LockingLookupIdempotentCanceller` — 키 `FOR UPDATE` 조회 → 취소 → 키 저장 | `KEY_LOOKED_UP` ×2 | V4 | 같은 클래스 |

1·2차 실패 배선은 **응답을 저장하지 않는다.** 키 행은 hash·`COMPLETED` 만 남기고 `response_status`·`response_body` 는 NULL 이다. 키가 이미 있으면 재생하지 않고 현재 결제를 조회해 돌려준다. 1·2차의 관심은 중복 실행과 데드락이고, 응답 스냅샷 타입은 이 배선보다 나중(응답 경계 refactor)에 생겼다 (plan 2절).

## 3. 관찰

### 3.1 0단계 — 키 없이 다시 보내면 두 번 처리된다

취소 이력 2건, 잔여 4,000, REFUND 원장 2건. 두 응답 모두 200 이다. **불변식은 깨지지 않는다.** 잔액 == 원장 합계, `balance_amount = amount − 취소 합계` 모두 성립한다. 깨진 것은 "같은 요청은 한 번만 실행된다" 는 기대다.

헤더가 선택이므로 이 동작은 본선에서도 계속 성립한다. V5 이후에도 이 테스트는 green 이다.

### 3.2 1차 — check-then-insert 는 동시 요청에서 뚫린다

```
T1  SELECT key            없음
T2  SELECT key            없음          ── KEY_LOOKED_UP barrier
T1  payment FOR UPDATE → 취소 → INSERT key → 커밋
T2  payment FOR UPDATE (T1 커밋까지 대기) → 잔여 7,000 을 보고 취소 → INSERT key → 커밋
```

성공 2, 취소 2건, 잔여 4,000, 키 행 2건. T2 는 T1 의 키가 커밋된 뒤에도 다시 보지 않는다 — 조회는 이미 끝났다. 잠금 읽기가 최신 값을 읽으므로 금액 상한은 지켜진다. 비유일 인덱스라 키 행 중복도 막히지 않는다. 대조로 **순차** 재전송은 키를 보고 다시 처리하지 않는다 (취소 1건). 조회와 저장 사이의 틈이 원인이라 RR 이든 RC 든 같다.

### 3.3 2차-① 최소 실험 — 갭락은 공존하고 insert intention 이 서로를 기다린다

수동 관측 (MySQL 8.0.44 컨테이너, root, 두 세션을 `SLEEP` 으로 벌려 `data_locks` 를 사이사이 조회).

두 `FOR UPDATE` 뒤:

```
trx   INDEX_NAME                  LOCK_MODE  LOCK_STATUS  LOCK_DATA
1821  idx_idempotency_key_lookup  X,GAP      GRANTED      1, 'CANCEL', 'k30', 2
1822  idx_idempotency_key_lookup  X,GAP      GRANTED      1, 'CANCEL', 'k30', 2
```

T1 의 INSERT 뒤:

```
1821  idx_idempotency_key_lookup  X,GAP                   GRANTED  1, 'CANCEL', 'k30', 2
1821  idx_idempotency_key_lookup  X,GAP,INSERT_INTENTION  WAITING  1, 'CANCEL', 'k30', 2
1822  idx_idempotency_key_lookup  X,GAP                   GRANTED  1, 'CANCEL', 'k30', 2
```

T2 가 INSERT 하자 순환이 완성됐다. `LATEST DETECTED DEADLOCK` 요약:

```
(1) TRANSACTION 1821 inserting
    HOLDS    idx_idempotency_key_lookup  lock_mode X locks gap before rec           (k30)
    WAITING  idx_idempotency_key_lookup  lock_mode X locks gap before rec insert intention waiting (k30)
(2) TRANSACTION 1822 inserting
    HOLDS    같은 갭 X
    WAITING  같은 갭의 insert intention
WE ROLL BACK TRANSACTION (2)
```

- 없는 `k20` 을 잠그며 찾으면 **다음 레코드 `k30` 앞의 갭**에 X 갭락이 걸린다. 없는 행은 잠글 수 없으므로 행이 아니라 갭을 잠근다
- 갭락끼리는 모드와 무관하게 공존한다. 둘 다 "없음" 을 보고 진행한다
- INSERT 의 insert intention 은 갭락과 충돌한다. 각자 상대의 갭락을 기다려 순환이 된다
- 자동 테스트는 두 INSERT 를 동시에 보낸다. 어느 쪽이 먼저 대기에 들어가든 나중 쪽이 순환을 완성한다. 5회 반복에서 매번 성공 1, 1213 1, `k20` 행 1건

### 3.4 2차-② 서비스 적용 — payment 락이 순환의 한 고리로 낀다

성공 1, 1213 1, 취소 1건, 잔여 7,000, 키 행 1건. **중복은 막혔지만 데드락 덕분이다.**

`LATEST DETECTED DEADLOCK` (테스트 컨테이너, `payment_v4`):

```
(1) TRANSACTION 2367  starting index read
    select ... from payment p1_0 where p1_0.id=? for update
    HOLDS    idempotency_key  idx_idempotency_key_lookup  lock_mode X   (supremum)
    WAITING  payment          PRIMARY                     lock_mode X locks rec but not gap waiting
(2) TRANSACTION 2366  inserting
    INSERT INTO idempotency_key ...
    HOLDS    payment          PRIMARY                     lock_mode X locks rec but not gap
    WAITING  idempotency_key  idx_idempotency_key_lookup  lock_mode X insert intention waiting (supremum)
WE ROLL BACK TRANSACTION (1)
```

- 계획(4.7)이 예상한 순환 그대로다. T2 가 payment 행을 쥐고 키 INSERT 에서 T1 의 갭락을 기다리고, T1 은 키 갭락을 쥔 채 payment 에서 T2 를 기다린다
- 계획과 다른 점 하나: 테이블이 비어 있어 잠긴 것은 기준 행 앞의 갭이 아니라 **supremum** 의 next-key(`X`) 다. supremum 은 실제 레코드가 없으므로 사실상 "마지막 레코드 뒤의 갭" 이다
- 피해자는 payment 에서 기다리던 쪽이었다(변경이 없는 트랜잭션). 단언은 "누가" 가 아니라 "성공 1, 1213 1" 이다

## 4. 원인

- **요청 단위 식별자가 없었다.** 같은 요청의 두 번째 실행을 막는 장치가 금액 상한밖에 없었다. 전체 롤백된 데드락 트랜잭션의 재시도는 이 중복의 원인이 아니다 (SCENARIO 177행)
- **1차: 조회와 저장 사이의 틈.** 둘 다 "없음" 을 본 뒤에는 막을 것이 없다. 비유일 인덱스라 저장도 막히지 않는다
- **2차: 없는 행의 잠금은 갭락이다.** `FOR UPDATE` 는 존재하는 행을 직렬화하지만, 없는 키에 대해서는 서로 공존하는 갭락만 잡는다. 결과적으로 INSERT 가 데드락으로 직렬화된다

## 5. 개선 — unique + insert-first

```
IdempotentCancelCoordinator.cancel(merchantId, key, paymentKey, amount, reason)   트랜잭션 없음
  key == null → PaymentService.cancel, 저장 없음 (기존 경로)
  tx1  claim         키 INSERT (IN_PROGRESS)       JdbcTemplate, 즉시 나간다
       cancel        PaymentService.cancel → 본선 canceller 가 tx1 에 참여
       complete      스냅샷 JSON 저장 (COMPLETED, 200)
  commit 성공 → 스냅샷
  uk_idempotency_key 1062 → tx2(readOnly) 에서 find → hash 비교 → 저장된 (status, body)
```

- **SQL 순서로 보장한다.** 키 INSERT 가 JPA flush 를 기다리지 않고 실제로 먼저 나간다. 엔티티를 만들지 않은 이유다
- **같은 트랜잭션.** `JpaTransactionManager` 는 자기 커넥션을 `JdbcTemplate` 에 노출한다. 취소가 업무 실패하면 키 행도 함께 사라진다 (회귀 12)
- **선점 충돌은 `uk_idempotency_key` 의 1062 로만 판정한다** (`MySqlLockErrors.isDuplicateKey`). MySQL 메시지는 `... for key 'idempotency_key.uk_idempotency_key'` 로 끝나고, 앞쪽의 중복 값에는 사용자 입력이 들어가므로 끝부분만 본다
- **쓰기는 활성 트랜잭션 필수.** `claim`·`complete`·`record`·`findForUpdate` 는 `TransactionSynchronizationManager.isActualTransactionActive()` 로 SQL 을 보내기 전에 검사한다 (회귀 14)
- `PaymentService.cancel` 은 시그니처도 반환 타입도 바꾸지 않았다. 컨트롤러가 조율자를 부르고, 조율자가 두 경로 모두에서 이 메서드에 위임한다

### 5.1 후속 INSERT 는 무엇을 기다리는가

수동 관측 (V5 를 적용한 같은 관측 컨테이너).

선행이 키를 INSERT 한 채 진행 중일 때 후속 INSERT:

```
trx   INDEX_NAME          LOCK_MODE      LOCK_STATUS  LOCK_DATA
1841  uk_idempotency_key  X,REC_NOT_GAP  GRANTED      1, 'CANCEL', 'k20', 5
1842  uk_idempotency_key  S              WAITING      1, 'CANCEL', 'k20', 5
```

- 선행의 새 레코드는 암묵 락이다. 후속의 중복 검사가 그것을 **명시적 `X,REC_NOT_GAP`** 으로 바꾸고, 자기는 그 레코드에 **`S`(next-key)** 를 요청해 기다린다
- 선행이 커밋하면 후속은 1062, 롤백하면 위반 없이 그대로 INSERT 한다. 그래서 "선행 롤백 → 후속 1062 → tx2 에서 행 없음" 은 일반 흐름이 아니고, 조율자는 tx2 의 행 없음을 재선점으로 흡수하지 않고 `IllegalStateException` 으로 드러낸다

### 5.2 대기 상한은 키 INSERT 한 문장에만

```
tx1 의 커넥션에서
  SELECT @@SESSION.innodb_lock_wait_timeout      기존 값 (50)
  SET SESSION innodb_lock_wait_timeout = 3       payment.idempotency.claim-lock-wait-timeout-seconds
  INSERT INTO idempotency_key ...
  finally: SET SESSION innodb_lock_wait_timeout = 50      INSERT 직후, 취소 전
```

- 이 INSERT 의 1205 만 409 `IDEMPOTENCY_KEY_IN_USE` 로 번역한다. 1205 는 문장만 롤백하고 트랜잭션은 열어 두므로, 예외를 tx1 밖으로 던져 전체를 롤백시킨다
- 선점 뒤 세션 값은 원래대로 돌아와 있다. 1062 로 실패해도 복원된다 (`JdbcIdempotencyKeyStoreTest`)
- **payment 잠금 대기에는 짧은 상한이 새지 않는다.** 다른 트랜잭션이 결제 행을 상한+1초(4초) 쥐고 있어도 키 있는 취소는 기다렸다가 성공한다 (회귀 9 별도 사례)
- 커넥션 일치와 트랜잭션 원자성은 다른 조건이다. `ConnectionCallback` 으로 한 커넥션에 묶기만 해서는 자동 커밋을 막지 못한다. 활성 트랜잭션 강제가 둘을 함께 보장한다

### 5.3 응답 스냅샷

재생 때는 `Payment` 가 아니라 **그때의 응답**이 있어야 한다. 응답 경계를 먼저 옮겼다 (refactor 커밋, 기존 테스트 수정 없이 green).

- application 계층의 `PaymentSnapshot`(`PaymentResponse` 와 같은 필드)과 `CancelOutcome(status, body)`. 상태는 정수로 둬 application 이 `HttpStatus` 를 모른다
- 스냅샷은 tx1 **안에서** 만들어 저장한다. 커밋된 결과와 저장된 응답이 같은 시점의 값이다
- 직렬화는 조율자가 MVC 와 같은 `ObjectMapper` 빈으로 한다. 저장소는 본문을 문자열로만 다룬다
- 동일 응답의 기준은 HTTP 상태와 JSON 필드·값이다. 바이트 동일성은 계약이 아니다
- "키 A 3,000 → 키 B 2,000 → A 재전송" 에서 A 재전송은 잔여 **7,000**(당시)을 받고, 현재 잔여는 5,000 이다 (회귀 4)

### 5.4 키와 요청 내용의 정의

| 입력 | 처리 |
|---|---|
| 헤더 없음 | 기존 경로 (키 행 없음) |
| 빈 값, 공백뿐, 65자 이상, `0x21`~`0x7E` 밖(비ASCII·탭 포함), 쉼표 | 400 `INVALID_REQUEST`, 부작용 없음 |
| 같은 헤더 두 번 | 쉼표로 합쳐져 400 |
| 대소문자만 다른 키 | 다른 키 (컬럼 `ascii_bin`) |
| 다른 가맹점의 같은 키 문자열 | 서로 무관 (`(merchant_id, operation)` 범위) |
| 같은 키, 다른 금액·사유·결제 | 409 `IDEMPOTENCY_KEY_REUSED`, 저장된 응답을 주지 않는다 |
| `reason` 의 `null` 뒤 `""` | 다른 요청 → 409 |

fingerprint 입력은 고정 순서 JSON `{"paymentKey","cancelAmount","reason"}` 의 SHA-256 이다. 비교 대상은 **성공해 저장된 요청뿐**이다. 업무 실패로 롤백된 요청은 키 행이 없으므로 같은 키로 다른 내용을 보내도 새 요청으로 실행된다 (회귀 8·13).

### 5.5 헤더 전달 — 내장 Tomcat 실측

MockMvc 는 컨테이너를 거치지 않아 값을 준 그대로 넘긴다. JDK `HttpClient` 는 보내기 전에 헤더를 검사할 수 있다. 그래서 `IdempotencyKeyHeaderServerTest` 는 RANDOM_PORT 서버에 **소켓으로 요청 바이트를 직접** 쓴다.

| 보낸 헤더 | Tomcat 이 넘긴 값 | 결과 |
|---|---|---|
| `Idempotency-Key:   ws-key \t ` | `ws-key` (앞뒤 공백·탭 제거) | 200. 이어서 `Idempotency-Key: ws-key` 는 재생 — 취소 1건, 저장된 키 `ws-key` |
| `Idempotency-Key: key-x` + `Idempotency-Key: key-y` | 두 값 → `String` 바인딩에서 `key-x,key-y` | 400 |
| `Idempotency-Key:` | `""` | 400. 헤더를 아예 안 보내면 200 — 빈 값과 없음이 구분된다 |

- 앞뒤 공백은 HTTP 의 OWS 라 컨테이너가 자른다. 그래서 코드는 값을 다듬지 않는다. MockMvc 로 `"   "` 를 보내면 그대로 들어와 400 이 된다 (회귀 11)
- 복수 값의 합침은 Spring 변환 서비스가 한다. `@RequestHeader` 는 값이 둘 이상이면 `String[]` 을 만들고 선언 타입으로 변환한다 — `String` 이면 쉼표로 이어 붙이고, `String[]` 이면 따로 온다 (`IdempotencyKeysTest`). 컨트롤러는 `String` 으로 받고 값을 쉼표로 나누지 않는다. 쉼표 금지 규칙 하나로 "복수 헤더" 와 "쉼표가 든 단일 값" 이 모두 400 이다

### 5.6 unique 는 데드락을 없애지 않는다 — 대기자 둘

선행이 키를 쥔 채 대기자가 둘일 때 선행이 롤백하면:

```
trx   INDEX_NAME          LOCK_MODE      LOCK_STATUS  LOCK_DATA           (롤백 전)
1845  uk_idempotency_key  X,REC_NOT_GAP  GRANTED      ..., 'k20', 7       선행
1846  uk_idempotency_key  S              WAITING      ..., 'k20', 7       대기자 1
1847  uk_idempotency_key  S              WAITING      ..., 'k20', 7       대기자 2
```

선행이 롤백하면 대기자들의 `S` 는 레코드가 사라진 자리의 **`S,GAP`** 으로 남아 둘 다 GRANTED 가 되고, 각자의 INSERT 가 insert intention 으로 상대의 `S,GAP` 을 기다린다:

```
(1) HOLDS  lock mode S locks gap before rec    WAITING  lock_mode X locks gap before rec insert intention waiting
(2) HOLDS  lock mode S locks gap before rec    WAITING  lock_mode X locks gap before rec insert intention waiting
WE ROLL BACK TRANSACTION (2)
```

MySQL 문서의 세 세션 사례([Locks Set by Different SQL Statements](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)) 그대로다.

**자동 관측** (`UniqueKeyWaiterDeadlockObservationTest`, 6.2): 회귀 10 과 같은 배치 — 선행 20,000 취소(업무 실패)를 `KEY_CLAIMED` 에 붙잡고, 같은 키·같은 내용(3,000) 대기자 둘의 대기를 `LockWaitProbe` 로 확인한 뒤 풀어 준다. **5회 모두 성공 1, 1213 1.** 결정적이라 관측 테스트에 무조건 단언으로 고정했다. 회귀 10 의 단언은 바꾸지 않았다.

- 1213 피해 트랜잭션은 전체 롤백된다. 키도 사라지므로 같은 키 재전송은 안전하다 — 살아남은 쪽이 커밋했으면 저장된 응답을 받는다 (회귀 10 의 마지막 단언)
- 응답은 현재 규약대로 **500** 이다. "키 INSERT 의 1213 을 재시도 가능한 409 로 번역" 은 계약 변경이라 이번엔 하지 않았다. 대기자 둘이 모두 대기 중일 때 선행이 롤백하면 매번 한 명이 500 을 받는다는 것이 관측 결과다 — 번역 후보의 근거로 남긴다

## 8. 다음 단계에 남기는 것

- **"같은 키로 커밋되는 취소는 최대 한 건" 과 "모두 성공 응답" 은 다르다.** 선행 롤백 + 대기자 둘에서 매번 한 명이 1213(500)을 받는다(5.6). 키 INSERT 의 1213 을 재시도 가능한 409 로 번역할지는 계약 변경으로 따로 정한다. 업무 실패나 롤백 뒤의 재전송은 다시 실행되므로 **실행 횟수**도 보장 대상이 아니다
- **`status` 컬럼은 S8 에서 의미가 생긴다.** CARD 취소를 분리 커밋하면 `IN_PROGRESS` 가 커밋된 채 보인다. 지금 조율자는 그 상태를 `IllegalStateException` 으로 드러낸다. 그때 진행 중 응답(409 등)과 복구 정책을 정한다
- **tx2 의 "행이 반드시 있다" 는 정리 경로가 없다는 전제에 기댄다.** 보존 기간 정리를 만들면 다시 본다
- **S7 은 `payment_v4`(`AbstractV4SchemaTest`)에서 2차 갭락 실험을 RC 로 다시 돌린다.** 갭락은 줄지만 unique 없이 중복은 다시 가능하다는 것을 확인한다. 3.3 의 락 모드가 비교 기준이다
- **충전은 이 구현을 `operation=CHARGE` 로 재사용한다** (Phase 1 종료 점검). `idempotency` 는 최상위 패키지이고 결제 타입을 모르므로 `wallet` 에서도 쓸 수 있다. 요청 fingerprint 구성(`CancelFingerprint` 에 해당)과 스냅샷은 충전 쪽이 따로 갖는다
- **`LockWaitProbe` 는 이후 시나리오의 대기 확인에 재사용한다.** hold + 대기 확인 + 해제는 "대기 중인 쪽이 어떻게 끝나는가" 를 보는 표준 배치가 됐다
