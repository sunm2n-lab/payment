# S3 — 부분취소 초과 환불: 취소 합계가 결제금액을 넘는다

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 계획: [plan/S3.md](../plan/S3.md) · 선행 기록: [phase1/S2.md](S2.md) · 이슈: #25

S1 은 **같은 결제의 승인** 경쟁을, S2 는 **서로 다른 결제가 같은 지갑**을 건드리는 경쟁을 막았다. 취소 경로는 어느 쪽도 적용받지 않았다. 이번 실습은 결함 두 개를 재현하고 한 번에 고친다.

1. 같은 결제의 부분취소가 서로의 잔여 금액 차감을 덮어쓴다 — 대상만 바뀐 S2 의 Lost Update
2. 잠그지 않는 환불이 같은 지갑의 **잠근** 차감을 덮어쓴다 — 락 규칙은 행 단위로 지켜져야 한다

## 1. 전제

| 항목 | 상태 |
|---|---|
| 스키마 | V2 그대로. **마이그레이션을 추가하지 않았다** |
| 제약 | FK 0건, `balance_amount` 에 `UNSIGNED`/`CHECK` 없음 |
| 격리 수준 | REPEATABLE READ |
| 구현 | **S1·S2 적용 누적** — 승인은 CAS + 비관적 락 차감. 취소만 Phase 0 naive |
| 트랜잭션 경계 | 취소 전체가 단일 트랜잭션. 카드 취소 호출도 안 (S8 전까지) |
| 결제 삭제 | 물리 삭제 경로 없음 |

버전은 [phase0/README.md 1절](../phase0/README.md)과 같다.

### 1.1 이음매 두 개와 조회 하나

취소가 naive / 비관적 락 둘로 갈라지므로 S1 의 `PaymentConfirmer` 와 같은 방식으로 이음매를 뽑았다.

```java
public interface PaymentCanceller {
  Payment cancel(Long merchantId, String paymentKey, long cancelAmount, String reason);
}
```

공통 본문(상태 → 금액 검사, 취소 이력, 잔여 금액·상태, 환불 또는 카드 취소)은 `PaymentSupport.cancel` 한곳에 있다. 두 구현의 차이는 **결제를 어떻게 읽느냐**와 **어떤 updater 를 쓰느냐**뿐이다.

환불은 결제 코드에서 꺼내 `WalletBalanceUpdater.refund` 로 옮겼다. 별도 환불 이음매를 두지 않은 이유가 이번 실습의 두 번째 결함이다 — 환불 전략을 따로 고를 수 있으면 "차감은 비관적, 환불은 naive" 같은 조합이 가능해지고, 그 조합이 3.2 의 유실을 만든다. 차감·충전·환불이 한 전략으로 묶이면 그 조합은 표현할 수 없다.

결제 생성이 지갑 id 를 찾던 `WalletRepository.findByMemberId` 호출도 `WalletService.findIdByMemberId` 로 옮겼다. 그 결과 `payment` 는 `wallet.infrastructure` / `wallet.domain` 을 import 하지 않는다. RESTRUCTURE 에서 S3 로 미뤄 둔 의존성이 여기서 정리됐다 ([STRUCTURE.md 4절](../STRUCTURE.md)).

## 2. 재현

| # | 배선 | 동기화 | 워커 |
|---|---|---|---|
| 재현 1 | `naivePaymentCanceller`, CARD 10,000 결제에 7,000 × 2 | `PAYMENT_READ` barrier | 2 |
| 재현 2 | `naivePaymentCanceller` 취소(P1) + 본선 승인(P2), **같은 지갑·다른 결제** | `WALLET_READ` **hold** | 2 |

재현 2 는 barrier 로 만들 수 없다. 필요한 것은 동시 출발이 아니라 **"환불이 잔액을 읽음 → 승인이 커밋 → 환불이 씀"** 이라는 순서다. 그래서 `ConcurrencyGate` 에 순서 게이트 hold 를 더했다. 무장한 지점에 처음 도착한 스레드 하나를 붙잡고, 상대가 `awaitArrival` → 자기 작업 → `release` 한다.

같은 결제를 쓰지 않은 것도 조건이다. 같은 결제면 payment 행에서 먼저 직렬화되어 지갑 경쟁이 가려진다.

`OverRefundReproductionTest` 는 깨진 결과를 그대로 assert 하므로 **결함이 재현될 때 green** 이다.

## 3. 관찰

### 3.1 재현 1 — 14,000 이 환불된다

| 항목 | 값 |
|---|---|
| 요청 2건의 결과 | **둘 다 성공** (둘 다 잔여 10,000 을 보고 검사) |
| `payment_cancel` | 2건, 합계 **14,000** |
| `payment.balance_amount` | **3,000** — 차감이 한 번만 반영된다 |
| `payment.status` | PARTIAL_CANCELED |
| 카드사 취소 호출 | **2회** |

`3,000 ≠ 10,000 − 14,000` — **불변식 2** 가, `14,000 > 10,000` — **불변식 3** 이 깨진다. DB 의 잔여 금액은 3,000 으로 멀쩡해 보이지만 카드사에는 이미 14,000 이 환불 요청됐다. 실제 피해는 외부에 있다.

SQL 로그(`org.hibernate.SQL` + `orm.jdbc.bind`)도 S2 와 같은 모양이다.

```
pool-3-thread-2  select ... from payment where payment_key=?        ┐ 둘 다 잠그지 않고
pool-3-thread-1  select ... from payment where payment_key=?        ┘ 10,000 을 읽는다
pool-3-thread-1  insert into payment_cancel ... <- [7000]           ┐ 취소 이력은
pool-3-thread-2  insert into payment_cancel ... <- [7000]           ┘ 둘 다 남는다
pool-3-thread-2  update payment set ... balance_amount=? <- [3000]  ┐ 행 락으로 직렬화되지만
pool-3-thread-1  update payment set ... balance_amount=? <- [3000]  ┘ 둘 다 3000 을 쓴다
```

### 3.2 재현 2 — 잠근 차감이 잠그지 않은 환불에 덮어써진다

충전 10,000 → P1(5,000) 승인 → 잔액 5,000. P1 2,000 부분취소와 P2(3,000) 승인을 경쟁시켰다.

| 항목 | 값 |
|---|---|
| 요청 2건의 결과 | 둘 다 성공, P2 는 DONE |
| 원장 합계 | 10,000 − 5,000 − 3,000 + 2,000 = **4,000** |
| `wallet.balance` | **7,000** |

환불이 승인 전에 읽은 5,000 에 2,000 을 더해 **덮어썼다.** 승인의 차감 3,000 이 통째로 사라졌다 — **불변식 1 위반.**

승인은 본선이다. 지갑을 `FOR UPDATE` 로 잠그고 검사·차감했다. 그런데도 유실된다. 로그가 이유를 보여 준다.

```
thread-2(환불)  select ... from payment where payment_key=?
thread-2(환불)  insert into payment_cancel ... <- [2000]
thread-2(환불)  select ... from wallet where id=?                    ← 잠그지 않는다. 5000 을 읽는다
                ─── hold ───
thread-1(승인)  UPDATE payment SET status='IN_PROGRESS' WHERE payment_key=? AND status='READY'
thread-1(승인)  select ... from wallet where id=? for update         ← 기다릴 락이 없다
thread-1(승인)  insert into wallet_ledger ... <- [-3000, PAY]
thread-1(승인)  update payment set ... status=? <- [DONE]
thread-1(승인)  update wallet set balance=? <- [2000]                커밋
                ─── release ───
thread-2(환불)  insert into wallet_ledger ... <- [2000, REFUND]
thread-2(환불)  update payment set ... balance_amount=? <- [3000]
thread-2(환불)  update wallet set balance=? <- [7000]                ← 5000 + 2000
```

`FOR UPDATE` 는 **다른 `FOR UPDATE` 와 UPDATE** 를 기다리게 할 뿐, 잠그지 않는 SELECT 를 막지 않는다. 환불은 락 없이 읽었으므로 승인과 겹칠 일이 없었고, 나중에 옛 값으로 계산한 절대값을 썼다. 한 행을 바꾸는 경로 **전부**가 같은 규칙을 따라야 잠금이 의미를 갖는다.

### 3.3 hold 가 교착을 만들지 않는 이유

hold 는 붙잡힌 쪽의 락이 상대 경로와 겹치면 교착이 된다 (상대가 DB 락에 막혀 `release` 에 도달하지 못한다). 위 로그에서 hold 시점까지 환불이 보낸 문장은 SELECT 둘과 `payment_cancel` INSERT 하나다. payment UPDATE 는 아직 나가지 않았다 — 지갑 조회가 `em.find` 라 auto-flush 를 일으키지 않고, 결제 변경은 커밋 시점에 flush 된다.

로컬 MySQL 에서 같은 문장을 재연해 hold 시점의 락을 봤다.

```
object_name     index_name  lock_type  lock_mode  lock_status  lock_data
payment_cancel  NULL        TABLE      IX         GRANTED      NULL
```

새로 INSERT 한 행의 락은 암묵적이라 `data_locks` 에 나오지 않는다. 승인은 P2 행·wallet·`wallet_ledger` 만 건드리므로 어느 것과도 겹치지 않는다. 재연에서 승인은 시작부터 커밋까지 **2ms** 였다.

## 4. 원인

두 결함 모두 read-modify-write 의 Lost Update 다.

- **재현 1**: 잠그지 않은 `balance_amount` 를 읽고, 검사하고, 계산한 절대값을 쓴다. S2 와 같고 대상만 결제다
- **재현 2**: 지갑 행을 바꾸는 세 경로(차감·충전·환불) 중 환불만 잠그지 않았다. 락은 **그 락을 요청하는 쪽**끼리만 순서를 정한다

S2 와 마찬가지로 RC 에서도 같다. 격리 수준 전환은 해결책이 아니다.

## 5. 개선

SCENARIO 155행대로 S2-b 결론(비관적 락)을 취소에 적용했다. `PessimisticLockPaymentCanceller` 가 본선(`@Primary`)이다.

```
1. findOwnershipByPaymentKey      잠그지 않는 스칼라 조회 (id, merchantId). 없으면 404
2. merchantId 불일치 → 404        불변 값이라 락 없이 검사해도 안전하다
3. findByIdForUpdate(id)          PK 레코드 X 락. 엔티티는 여기서 처음 로드한다
4. 상태 → 금액 검사                잠근 뒤의 현재 값으로
5. payment_cancel, balance_amount·status
6. MONEY → updater.refund (wallet FOR UPDATE) / CARD → cardApprovalClient.cancel
```

**바뀌지 않는 사실(존재, 소유 가맹점)은 잠그기 전에, 바뀌는 사실(상태, 잔여 금액)은 잠근 뒤에** 검사한다. 환불은 승인 본선과 같은 `PessimisticLockWalletBalanceUpdater` 를 쓴다. 잠금 순서는 승인과 같은 `payment → wallet` 이다.

### 5.1 락 관측 — 두 번째 취소는 PK 레코드 락에서 기다린다

로컬 docker-compose MySQL(임시 DB 에 V1+V2 적용)에 `root` 로 붙어 본선 취소 두 건의 SQL 을 재연했다. 첫 취소가 커밋 전에 머무는 동안이다.

```
object_name     index_name  lock_type  lock_mode      lock_status  lock_data  thread
payment         NULL        TABLE      IX             GRANTED      NULL       T1
payment         PRIMARY     RECORD     X,REC_NOT_GAP  GRANTED      1          T1
payment_cancel  NULL        TABLE      IX             GRANTED      NULL       T1
wallet          NULL        TABLE      IX             GRANTED      NULL       T1
wallet          PRIMARY     RECORD     X,REC_NOT_GAP  GRANTED      1          T1
wallet_ledger   NULL        TABLE      IX             GRANTED      NULL       T1
payment         NULL        TABLE      IX             GRANTED      NULL       T2
payment         PRIMARY     RECORD     X,REC_NOT_GAP  WAITING      1          T2

waiting_on       waiting_mode   waiting_data  blocking_mode
payment.PRIMARY  X,REC_NOT_GAP  1             X,REC_NOT_GAP
```

- **취소도 `payment → wallet` 순서다.** T1 이 두 행의 X 락을 함께 보유한다
- **두 번째 취소는 payment PK 레코드 락에서만 기다린다.** 소유 조회(1단계)는 잠그지 않으므로 T2 는 그 전까지 아무 락도 없다
- `REC_NOT_GAP` — PK 등치이고 행이 있으므로 갭 락이 없다
- `payment_key` 의 secondary index 에는 락이 없다. S1 의 CAS 는 `payment_key` 조건으로 갱신하므로 uk 인덱스와 PK 양쪽을 잠갔다 (phase1/S2.md 6.6). 취소는 PK 로만 잠근다

### 5.2 잠금 읽기는 스냅샷이 아니라 최신 값을 읽는다

같은 재연에서 T2 가 락을 얻은 뒤 읽은 값은 `PARTIAL_CANCELED / 2000` 이었다 — T1 이 커밋한 값이다. 같은 트랜잭션에서 잠그지 않고 다시 읽으면 다르다.

```
at_           status            balance_amount
plain before  DONE              5000      ← 첫 SELECT 에서 RR 스냅샷이 고정된다
for update    PARTIAL_CANCELED  2000      ← 잠금 읽기는 최신 커밋 값 (current read)
plain after   DONE              5000      ← 다시 스냅샷
```

그래서 두 가지가 따라 나온다.

- **검사는 반드시 잠금 읽기의 결과로 해야 한다.** 소유 조회(1단계)에서 스냅샷이 고정되지만, 그 조회는 불변 값만 읽으므로 스냅샷이 낡아도 상관없다
- **탈락자의 예외 메시지가 사실을 말한다.** 회귀 1 의 탈락자는 `balanceAmount=3000` 을 담는다. S2 조건부 감산의 탈락자가 스냅샷 때문에 잔액을 주장할 수 없었던 것(`notEnough`)과 다르다

### 5.3 엔티티를 먼저 읽고 잠그면 개선이 무효가 된다

DB 는 최신 값을 돌려주지만 JPA 는 그 값을 버릴 수 있다. 영속성 컨텍스트에 같은 id 의 엔티티가 이미 있으면 `FOR UPDATE` 조회 결과로 **갱신하지 않고** 기존 엔티티를 돌려준다. 락은 잡혔는데 값은 잠그기 전의 것이다.

변이로 확인했다. 1단계를 `findOwnedPayment(...).getId()`(엔티티 로드)로 바꾸면 회귀 1·2·4 가 **"성공 2건"** 으로 실패한다 — 결제 잠금을 아예 뺀 변이와 똑같은 결과다. 그래서 1단계는 엔티티가 아니라 스칼라(`PaymentOwnership(id, merchantId)`)를 돌려준다. S2 의 비관적 충전이 `findIdByMemberId` 로 id 만 찾은 것과 같은 이유다.

### 5.4 `payment_key` 로 바로 잠그지 않는 이유 — 갭 락

없는 키 `k2` 를 `payment_key` 로 `FOR UPDATE` 했다 (있는 키는 `k1`, `k3`).

```
object_name  index_name              lock_type  lock_mode  lock_data
payment      uk_payment_payment_key  RECORD     X,GAP      'k3', 2
```

`k3` 앞의 갭, 즉 `('k1', 'k3')` 에 갭 락이 걸린다. 트랜잭션이 끝날 때까지

- `k20` INSERT — 그 갭에 들어가므로 **대기 후 `Lock wait timeout`**
- `k5` INSERT — 갭 밖이라 **즉시 성공**

막히는 것은 모든 결제 INSERT 가 아니라 **그 갭에 들어오는** INSERT 다. `payment_key` 는 UUID 라 어느 갭에 떨어질지 정해져 있지 않다. 같은 없는 키를 잠그지 않는 소유 조회(1단계)로 찾으면 `data_locks` 는 **0건**이고 바로 404 로 끝난다.

PK 등치 잠금이 레코드 락 하나로 끝나는 전제는 **결제를 물리 삭제하지 않는다**는 것이다. 1단계에서 확인한 행이 3단계에서 없다면 데이터 불일치로 보고 예상 밖 오류(5xx)로 둔다.

### 5.5 오류 우선순위 — 탈락자의 예외는 승자가 정한다

검사 순서는 Phase 0 그대로 **상태 → 금액** 이다.

| 승자 | 탈락자가 읽는 상태 | 탈락자의 예외 |
|---|---|---|
| 7,000 부분취소 (10,000 결제) | PARTIAL_CANCELED, 잔여 3,000 | `CANCEL_AMOUNT_EXCEEDED` |
| 10,000 전액취소 | CANCELED | `INVALID_PAYMENT_STATUS` |

"초과 요청은 `CANCEL_AMOUNT_EXCEEDED`" 는 부분취소끼리의 경쟁에만 맞는 말이다. 회귀 4 가 전액·부분 경쟁에서 탈락자의 예외가 승자와 짝이 맞는지 확인한다.

### 5.6 승인과의 경쟁

같은 결제에서 승인과 취소가 겹치면 **payment 락을 먼저 잡은 쪽**이 결과를 정한다.

- 승인이 CAS 로 먼저 잡고 정상 커밋 → 취소는 대기 후 DONE 을 읽는다 (5.2 의 잠금 읽기)
- 취소가 먼저 잡음 → READY 를 읽고 `INVALID_PAYMENT_STATUS`. 정상이다
- 승인이 롤백 → 취소는 READY 를 읽는다

이 경쟁의 테스트는 이번 범위가 아니다.

### 5.7 비교하지 않은 후보

| 후보 | 판단 |
|---|---|
| 조건부 UPDATE (`... SET balance_amount = balance_amount - ? WHERE id = ? AND balance_amount >= ?`) | 유효하다. 다만 상태 전이(`PARTIAL_CANCELED`/`CANCELED`)와 상태 검사를 같은 문장에 넣어야 하고, 탈락 판정이 갱신 건수 0 뿐이라 탈락자가 상태 오류인지 금액 초과인지 구분하려면 다시 읽어야 한다 — 그 재조회는 스냅샷이다 (5.2). 검사 규칙이 늘수록 SQL 이 커진다 |
| 낙관적 락 | S2 에서 비교를 마쳤다. 한 결제에 동시 취소가 몰리는 경우는 드물어 충돌 비용은 작겠지만, `payment` 에 `@Version` 을 붙이면 naive 경로까지 보호되어 재현이 사라진다 (S2 가 `VersionedWallet` 을 따로 둔 이유와 같다) |

## 8. 다음 단계에 남기는 것

- **취소도 `payment → wallet` 순서다.** 승인과 순서가 같으므로 서로 다른 결제 A/B 와 공유 지갑만으로 순환 대기가 생긴다고 가정하지 않는다 (SCENARIO 157행). S4 의 FK 락 승격 실험은 이 순서 위에서 한다
- **S5 — 취소 재시도.** 잠금은 동시 요청을 줄 세울 뿐이다. 같은 취소가 재전송되면 두 번째도 정당한 새 취소로 보인다 (잔여 금액이 남아 있다면 통과한다). 멱등키가 필요하다. 5.4 의 갭 락은 멱등키 테이블의 insert-first 에서 다시 만난다
- **S8 — 락 보유 시간.** 카드 취소는 payment X 락을 붙든 채 외부 응답을 기다리고, MONEY 취소는 payment 와 wallet 을 함께 잠근다
- **S9 — 카드 취소 실패.** 지금은 카드 취소가 트랜잭션 안에 있어 실패하면 전체가 롤백되지만, 카드사 쪽은 이미 취소됐을 수 있다
- **hold 게이트**는 "A 읽음 → B 커밋 → A 씀" 순서가 필요한 이후 재현(S4·S7)에서 쓸 수 있다. 붙잡힌 쪽이 보유한 락이 상대와 겹치지 않는지는 쓸 때마다 확인한다
