# S6 — 인덱스 없는 조건의 락: 전혀 다른 결제끼리 서로 막힌다

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 계획: [plan/S6.md](../plan/S6.md) · 선행 기록: [phase1/S5.md](S5.md) · 이슈: #31

S5 까지의 잠금은 모두 unique 인덱스나 PK 의 등치로 행을 찾았다. 그래서 "잠근 것" 과 "찾은 것" 이 같았고, 서로 다른 결제는 서로 다른 행을 잠가 만나지 않았다. S6 은 **인덱스가 없는 조건**(`merchant_id = ? AND order_id = ?`)으로 잠그며 읽는다. 결과는 1행인데 InnoDB 는 찾느라 스캔한 인덱스 레코드를 잠근다.

세 단계의 **SQL 과 서비스 코드는 하나다.** 인덱스 없음(V5) → `merchant_id` 단일 인덱스(V6) → `(merchant_id, order_id)` 복합 unique(V7) 로 스키마만 바꿨다. 잠금 범위의 차이는 실행 계획 하나로 설명된다.

## 1. 전제

| 항목 | 상태 |
|---|---|
| 스키마 | **V6** `idx_payment_merchant_id (merchant_id)`. **V7** 그 인덱스를 `uk_payment_merchant_order (merchant_id, order_id)` 로 교체 + `order_id` 를 `ascii` / `ascii_bin` 으로 (ALTER 한 문장) |
| 과거 재현 | 0·0'·1 단계는 처음부터 **V5 DB**(`payment_v5`), 2 단계는 **V6 DB**(`payment_v6`) 에서 돈다. 3 단계는 최신 (1.1) |
| 격리 수준 | REPEATABLE READ (RC 비교는 S7) |
| 결제수단 | CARD (Fake). 공유 지갑 경합을 제외한다 |
| 멱등키 | 행렬의 모든 취소가 요청마다 다른 키를 쓴다. 같은 키의 선점 대기(S5)가 섞이지 않는다 |
| FK | 추가하지 않는다. `payment → merchant` FK 없음 |
| 트랜잭션 경계 | 취소 전체가 단일 트랜잭션 (분리는 S8) |
| 서버 설정 | 기본값 — `innodb_lock_wait_timeout=50`, `innodb_autoinc_lock_mode=2` |

버전은 [phase0/README.md 1절](../phase0/README.md)과 같다 (MySQL 8.0.44, Hibernate 6.6.53, Spring Boot 3.5.16).

## 2. 재현 배치

### 2.1 대상 SQL

`PaymentRepository.findByMerchantIdAndOrderIdForUpdate` 가 실제로 내보내는 문장(Hibernate SQL 로그):

```sql
select p1_0.id,p1_0.amount,p1_0.approved_at,p1_0.balance_amount,p1_0.card_approval_no,p1_0.created_at,
       p1_0.merchant_id,p1_0.method,p1_0.order_id,p1_0.payment_key,p1_0.status,p1_0.wallet_id
from payment p1_0 where p1_0.merchant_id=? and p1_0.order_id=? for update
```

`EXPLAIN` 은 이 문장 그대로에 건다 (`OrderLockMatrix.LOCKING_READ_SQL`). 대기 결과를 보기 전에 `type`/`key` 를 먼저 단언하고, 다르면 해석하지 않고 실패한다.

### 2.2 대량 픽스처 — 실행 계획을 결정적으로

`BulkPaymentFixture`: 가맹점 100 × CARD DONE 결제 100건 = 10,000건. JDBC 여러 행 INSERT, 끝에 `ANALYZE TABLE payment`.

- **가맹점·결제 id 를 명시해 넣는다.** 가맹점 `m` 의 결제는 id `(m−1)×100+1 .. m×100`, 주문 id `order-m-seq`, 결제 키 `pk-m-seq`. 단일 인덱스의 엔트리 순서 `(merchant_id, id)` 가 가맹점 순서와 같다. 이후 만드는 결제의 id 는 10,001 이상이다
- `merchant_id` 선택도 1%. 시드 가맹점 둘에 반씩 넣으면 50% 라 옵티마이저가 인덱스를 버릴 수 있다
- 테스트 간 정리가 TRUNCATE 라 시드 가맹점 id 가 1·2 로 되돌아간다. 픽스처가 먼저 확인한다
- 행렬의 한 행마다 새로 넣는다. 한 번에 1초 안쪽이라 행별 격리를 택했다

### 2.3 대기 행렬 — `OrderLockMatrix`

선행은 가맹점 **A = 50** 의 `order-50-1` 을 주문 기반으로 취소하다가 잠금 읽기 **반환 직후**(`ORDER_LOCKED` hold)에 붙잡힌다. 앞뒤 이웃 A−1 = 49, A+1 = 51, 떨어진 가맹점 **B = 80**. 세 스키마가 같은 시나리오 코드를 쓰고 기대만 넘긴다.

- **대기**: 후속을 보낸 뒤 `LockWaitProbe.awaitWaiters(payment, n)` 가 대기자를 확인하고, 그때까지 끝난 후속이 0이며, 선행을 풀면 후속이 성공한다
- **통과**: 선행이 붙잡힌 채로 후속이 10초 안에 모두 성공한다

## 3. 관찰

### 3.1 0 단계 — 주문 유일성이 없다 (V5)

같은 가맹점이 `order-s6-0` 으로 결제를 순차로 두 번 만든다. **둘 다 200.** 주문 기반 조회·취소는 결과가 2행이라 Spring Data 가 `IncorrectResultSizeDataAccessException` 을 던지고 **500** 이다. 하나를 골라 취소하지 않는다 — 상태 스냅샷이 그대로다 (`DuplicateOrderReproductionTest`).

### 3.2 0' 단계 — 비교가 대소문자를 무시한다 (V5)

`order-s6-1` 로 만든 결제가 `ORDER-S6-1` 조회에 **200 으로 잡힌다.** `ORDER-S6-1` 도 만들면 두 주문이 각자 생성되고(unique 가 없으므로), 조회·취소는 2행이라 500 이다. 컬럼 collation 이 `utf8mb4_0900_ai_ci` 라서다. 승인의 `orderId` 검사(`String.equals`)는 대소문자를 구분하므로 조회와 승인의 판정도 어긋나 있다.

### 3.3 1 단계 — 인덱스 없음 (V5)

`EXPLAIN`: `type=ALL`, `key=NULL`.

선행이 붙잡힌 시점의 락 (`LockWaitProbe.locksOf`, 선행 트랜잭션 하나로 필터):

```
RECORD PRIMARY X GRANTED x10076
TABLE  -       IX GRANTED x1
```

- **10,076 = 레코드 10,001 + 페이지 supremum 75.** 결과는 1행인데 클러스터 인덱스의 모든 레코드(픽스처 10,000 + B 의 READY 1)와 모든 페이지의 끝 갭을 next-key `X` 로 잠갔다
- REPEATABLE READ 는 조건에 맞지 않은 행의 락을 풀지 않는다. 풀스캔이 곧 전체 잠금이다

| # | 후속 | 결과 |
|---|---|---|
| 1 | B 의 주문 기반 취소 | 대기 |
| 2 | A 의 다른 주문 취소 | 대기 |
| 3 | B 의 결제 `paymentKey` 취소 (PK 잠금) | 대기 |
| 4 | A 의 다른 결제 `paymentKey` 취소 | 대기 |
| 5 | B 의 READY 결제 승인 (S1 CAS `UPDATE`) | 대기 |
| 6 | B 의 새 결제 생성 | 대기 — 새 id 는 끝에 들어가고 supremum 이 잠겨 있다 |
| 7 | A−1 의 새 결제 생성 | 대기 |
| 8 | A+1 의 새 결제 생성 | 대기 |
| 9 | A 의 새 결제 생성 | 대기 |
| 10 | A 의 주문 **비잠금** 조회 | **통과** — 스냅샷을 읽는다 |
| 11 | 선행 + 다른 가맹점 주문 기반 취소 7건 | **대기자 7** — 완전 직렬화 |

가맹점도, 결제도, 멱등키도 다른 요청 **전부**가 한 요청의 커밋을 기다린다. 막히지 않는 것은 비잠금 읽기뿐이다.

### 3.4 2 단계 — `merchant_id` 단일 인덱스 (V6)

`EXPLAIN`: `type=ref`, `key=idx_payment_merchant_id`, `rows=100`, `filtered=10.0`, `Extra=Using where`.

```
RECORD idx_payment_merchant_id X          GRANTED x101   A 의 엔트리 100 + 페이지 supremum 1
RECORD idx_payment_merchant_id X,GAP      GRANTED x1     (51, 5001) — A+1 의 첫 엔트리
RECORD PRIMARY                 X,REC_NOT_GAP GRANTED x100 A 의 행
TABLE  -                       IX         GRANTED x1
```

- 스캔이 가맹점 하나로 좁혀졌다. 그러나 `order_id` 는 인덱스에 없어 A 의 100행을 모두 읽어 비교하고, 비교에 진 99행의 락도 남는다
- PRIMARY 는 레코드만(`REC_NOT_GAP`) 잠갔다. 보조 인덱스로 찾은 행의 클러스터 레코드다
- 스캔 끝의 첫 불일치 엔트리 `(51, 5001)` 에는 레코드 없이 갭만(`X,GAP`) 걸렸다

| # | 후속 | 결과 | 이유 |
|---|---|---|---|
| 1 | B 의 주문 기반 취소 | 통과 | B 의 엔트리를 스캔한다. 잠긴 곳과 겹치지 않는다 |
| 2 | A 의 다른 주문 취소 | **대기** | 같은 A 의 엔트리를 스캔하다 첫 엔트리에서 막힌다 |
| 3 | B 의 결제 `paymentKey` 취소 | 통과 | B 의 PRIMARY 레코드는 잠기지 않았다 |
| 4 | A 의 다른 결제 `paymentKey` 취소 | **대기** | 그 행의 PRIMARY 레코드가 잠겼다 |
| 5 | B 의 READY 결제 승인 | 통과 | |
| 6 | B 의 새 결제 생성 | 통과 | 새 엔트리 `(80, 새 id)` 는 잠긴 갭 밖. PRIMARY 의 supremum 은 잠기지 않았다 |
| 7 | A−1 의 새 결제 생성 | **대기** | 3.5 |
| 8 | A+1 의 새 결제 생성 | 통과 | 3.5 |
| 9 | A 의 새 결제 생성 | **대기** | 3.5 |
| 10 | A 의 주문 비잠금 조회 | 통과 | |
| 11 | 다른 가맹점 주문 기반 취소 7건 | 통과, 대기자 0 | |

### 3.5 이웃 가맹점의 INSERT — 잠긴 갭을 확인한 뒤 단언했다 (6.2)

계획은 7·8·9번을 키 배치에서 끌어낸 **예상**(†)으로 두고, 잠긴 갭을 `data_locks` 로 확인한 뒤에만 단언으로 올리기로 했다. 확인 도중 **페이지 경계**가 설명에 끼어든다는 것을 알았다.

`ENGINE_LOCK_ID` 의 페이지 번호로 본 선행의 락 (`MerchantIndexGapObservationTest`):

| 엔트리 | 모드 | 페이지 |
|---|---|---|
| `(50, 4901)` — A 의 첫 엔트리 | `X` (next-key) | 55 |
| supremum | `X` | 55 |
| `(50, 5000)` — A 의 마지막 엔트리 | `X` | 58 |
| `(51, 5001)` — A+1 의 첫 엔트리 | `X,GAP` | 58 |
| `(49, 4900)` — A−1 의 마지막 엔트리 (별도 트랜잭션의 `FOR SHARE` 로 위치만 확인) | — | 55 |

- **7번 대기.** A−1 의 새 엔트리 `(49, 새 id)` 는 `(49, 4900)` 과 `(50, 4901)` 사이에 들어간다. 둘이 **같은 55번 페이지**라서, `(50, 4901)` 의 next-key 가 덮는 갭이다. 두 엔트리가 페이지 경계를 사이에 뒀다면 새 엔트리는 앞 페이지의 끝(그 페이지 supremum 앞)에 들어가 이 락과 만나지 않았을 것이다. 그래서 "같은 페이지" 를 관측 테스트의 단언으로 둔다 — 픽스처가 바뀌어 전제가 깨지면 이 테스트가 먼저 알린다
- **9번 대기.** A 의 새 엔트리 `(50, 새 id)` 는 `(50, 5000)` 과 `(51, 5001)` 사이, 58번 페이지의 `X,GAP` 이 덮는 갭이다
- **8번 통과.** A+1 의 새 엔트리 `(51, 새 id)` 는 A+1 의 기존 엔트리 100개 **뒤**라 잠긴 갭 밖이다. A+1 의 엔트리 중 잠긴 것은 첫 엔트리의 갭 하나뿐이다
- 55번 페이지의 supremum 락은 A 의 범위 **안쪽**(A 의 엔트리가 55·58 두 페이지에 걸쳐 있다)이라 새 엔트리의 위치와 무관하다

`ENGINE_LOCK_ID` 는 MySQL 8.0.44 에서 `<trx>:<?>:<?>:<page>:<heap_no>:<lock>` 6필드로 나왔다. 끝에서 세 번째가 페이지, supremum 의 heap_no 는 1 이다 (`LockWaitProbe.pageOf`).

### 3.6 3 단계 — 복합 unique (V7, 본선)

`EXPLAIN`: `type=const`, `key=uk_payment_merchant_order`.

```
RECORD uk_payment_merchant_order X,REC_NOT_GAP GRANTED x1
RECORD PRIMARY                   X,REC_NOT_GAP GRANTED x1
TABLE  -                         IX            GRANTED x1
```

대상 결제 한 행이다. 락 엔트리는 둘이다 — 보조 인덱스로 찾아 배타적으로 잠그면 클러스터 레코드도 함께 잠긴다. **대기 행렬 11행 모두 통과**(회귀 7). 같은 가맹점의 다른 주문(2번), 같은 가맹점의 새 결제(9번), 앞 이웃(7번)도 막히지 않는다.

### 3.7 없는 주문을 잠그며 찾으면 (V7, 4.7 관측)

`order-50-none` 을 주문 기반으로 취소하다 `ORDER_LOCKED` 에 붙잡힌 선행의 락:

```
uk_payment_merchant_order  X,GAP  51, 'order-51-1', 5001
```

- 잠글 레코드가 없으므로 그 값이 들어갈 자리의 **다음 엔트리**에 갭락 하나. `ascii_bin` 순서로 `order-50-none` 은 A 의 숫자 주문들 뒤다(`n` 0x6E > `9` 0x39). `LOCK_DATA` 에 PK(5001)가 붙는다 — 보조 인덱스 엔트리가 PK 를 담는다
- 같은 갭에 들어가는 A 의 새 주문 `order-50-new` 생성은 선행이 끝날 때까지 **대기**, B 의 생성은 **통과**
- 404 로 끝나는 요청이라 곧 롤백되어 수명은 짧다. 고치지 않았다 — 비잠금 조회 → PK 잠금으로 바꾸면 세 단계의 SQL 이 달라진다. RC 에서 사라지는지는 S7 이 본다

### 3.8 수동 관측 — 100,000건과 slow query log (6.1)

일회용 MySQL 8.0.44 컨테이너에 `docker/mysql/conf.d/s6.cnf` 를 붙이고 V5·V6·V7 스키마를 각각 만들었다. 가맹점 1,000 × 100건 = 100,000건 (자동 테스트의 10배, 가맹점당 행 수는 같다). 대상은 `merchant_id=500 AND order_id='order-500-1'`. 로컬 docker compose DB 는 쓰지 않았다.

**경합 없는 단건 잠금 읽기** — 트랜잭션 안에서 `NOW(6)` 차이로 5회 (µs, 최소 / 중앙 / 최대):

| 스키마 | `EXPLAIN` | `rows` | 레코드 락 | 지연 |
|---|---|---|---|---|
| V5 | `ALL` | 96,917 | 100,698 | 34,345 / 36,028 / 36,770 |
| V6 | `ref` | 100 | 201 | 382 / 398 / 406 |
| V7 | `const` | 1 | 2 | 306 / 316 / 335 |

- V5 의 락 개수는 **테이블 크기**를, V6 은 **가맹점의 행 수**를 따른다. 10,000건 때 10,076 → 100,000건 때 100,698 이고, V6 은 두 크기에서 모두 가맹점당 100행 + 갭·supremum 이다. V7 은 크기와 무관하게 2 다
- 지연은 환경의 영향을 받으므로 단언하지 않는다. 경합이 없어도 V5 는 100배 느리다

**slow query log** (`long_query_time=1`, `log_queries_not_using_indexes=ON`). 선행이 3초 쥐는 동안 후속을 보냈다:

| 스키마 | 문장 | `Query_time` | `Lock_time` | `Rows_examined` |
|---|---|---|---|---|
| V5 | 선행 (A) | 0.039512 | 0.000002 | 100,000 |
| V5 | 후속 (가맹점 800) | 2.542214 | 2.489273 | 100,000 |
| V6 | 후속 (A 의 다른 주문) | 2.442316 | 2.441701 | 100 |
| V7 | — | 기록 없음 | | |

- V5 의 선행은 0.04초로 빨랐는데도 기록됐다 — `log_queries_not_using_indexes` 가 인덱스를 쓰지 않은 조회를 시간과 무관하게 남긴다. 풀스캔 잠금 읽기를 찾는 단서가 된다
- **행 락 대기 시간이 `Lock_time` 에 들어간다.** 후속의 `Query_time` 대부분이 `Lock_time` 이다. slow log 만 보고 "느린 쿼리" 로 오해하기 쉬운데, 실제로는 다른 트랜잭션을 기다린 시간이다
- V6 의 선행은 인덱스를 쓰고 1초 미만이라 기록되지 않았다. 기다린 후속만 남는다

## 4. 원인

InnoDB 의 잠금 읽기는 **조건에 맞은 행이 아니라 찾느라 스캔한 인덱스 레코드**를 잠근다. 쓸 인덱스가 없으면 클러스터 인덱스 전체가 스캔 대상이고, REPEATABLE READ 는 조건에 맞지 않은 행의 락도 트랜잭션 끝까지 들고 있다. 최종 결과 행 수(1행)로 잠금 범위를 판단하면 안 된다.

단일 인덱스는 스캔 범위를 가맹점 하나로 줄이지만, 인덱스에 없는 `order_id` 를 비교하느라 가맹점의 모든 행을 읽는다. 잠금 범위는 **인덱스가 좁혀 준 데까지**다. 등치 unique 가 되어야 찾은 것과 잠근 것이 같아진다.

## 5. 개선 — `(merchant_id, order_id)` 복합 unique

```sql
ALTER TABLE payment
    MODIFY order_id VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    DROP INDEX idx_payment_merchant_id,
    ADD UNIQUE KEY uk_payment_merchant_order (merchant_id, order_id);
```

- **ALTER 한 문장.** unique 추가나 문자 집합 변환이 실패하면 단일 인덱스와 collation 이 그대로 남는다 (리허설 1·2, 5.4)
- **단일 인덱스를 남기지 않는다.** 복합 unique 의 선두 컬럼이 `merchant_id` 라 가맹점 검색도 이 인덱스가 받는다
- 잠금 범위와 함께 **주문 유일성**이 생긴다 (5.2)

### 5.1 주문 id 형식

`OrderIds`: `[A-Za-z0-9_-]`, 6~64자. 생성 요청의 `orderId`(Bean Validation `@Pattern`)와 새 API 의 경로 변수(`OrderIds.validate`)가 같은 규칙을 쓴다. 위반은 400 `INVALID_REQUEST`. 토스페이먼츠의 주문번호 규칙과 같다.

- 주문 id 가 **경로 변수와 unique 키**가 되면서 제한했다. `/`, 공백, 악센트가 경로·collation·정규화 문제를 만든다
- 대소문자는 구분한다. `order_id` 를 `ascii_bin` 으로 바꿔 `Order-1` 과 `order-1` 이 다른 주문이다 (회귀 10). S5 멱등키 컬럼과 같은 선택이다
- **최소 6자.** 공개 규칙은 넓히기는 쉽고 좁히기는 어렵다. 보안 장치가 아니다 — 접근 권한은 가맹점 인증과 `merchant_id` 조건이 지킨다

**계획 1.2 가 놓친 테스트가 하나 있었다.** `ErrorResponseContractTest` 의 "amount 0 은 400, 첫 필드 오류가 메시지" 도 준비 데이터의 주문 id 가 `zero`(4자)였다. 형식 규칙이 들어가면 한 요청이 두 필드를 함께 어기고, Bean Validation 의 필드 오류 순서는 정해져 있지 않다. 계획 단계의 사전 확인 두 번과 형식 제한 커밋 직후의 전체 실행에서는 우연히 `amount` 가 먼저 나와 통과했고, 몇 커밋 뒤의 전체 실행에서 `orderId` 가 먼저 나와 실패했다. 주문 id 를 규칙 안으로 바꿔 형식 제한 커밋에 합쳤다 — 커밋마다 green 을 지키기 위해서다. 계획의 "규칙 밖의 입력은 세 개뿐" 은 **통과한 테스트만 센 것**이라 틀렸다.

### 5.2 중복 주문 생성 — 409 `DUPLICATE_ORDER`

`PaymentService.create` 가 `uk_payment_merchant_order` 위반(1062, `MySqlLockErrors.isDuplicateKey`)만 `DuplicateOrderException` 으로 번역한다. `uk_payment_payment_key` 위반(UUID 충돌)은 번역하지 않아 500 이다. 내용이 같아도 409 다 — "같은 내용이면 기존 결제로 응답" 은 Phase 1 종료 점검이다.

| 상황 | V5 (0 단계) | V7 (회귀 8·10) |
|---|---|---|
| 같은 가맹점, 같은 `orderId` 순차 | 2건 | 두 번째 409, 결제 1건 |
| 같은 가맹점, 같은 `orderId` 동시 2건 | — | 후속 INSERT 가 선행 커밋까지 **대기**(`LockWaitProbe` 로 확인) 후 409. 성공 1, 결제 1건 |
| 다른 가맹점, 같은 `orderId` | — | 각자 생성 |
| 대소문자만 다른 `orderId` | 각자 생성되지만 조회·취소가 구분하지 못한다 | 각자 생성, 조회·취소가 정확한 결제를 고른다. `Order-S6U-10` 은 404 |

동시 생성에서 선행이 롤백하고 대기자가 둘 이상이면 S5 5.6 의 데드락 모양이 여기서도 가능하다. 재현하지 않았다.

### 5.3 주문 기반 조회·취소 API

`GET /v1/payments/orders/{orderId}` (비잠금), `POST /v1/payments/orders/{orderId}/cancel` (`FOR UPDATE` 후 취소). 계약은 [API_CONTRACT.md 2.4](../API_CONTRACT.md).

- `merchant_id` 가 SQL 조건이다. 다른 가맹점의 주문은 결과가 없어 404 — 없는 주문과 같은 응답이다 (회귀 3). 기존 경로처럼 메모리에서 소유를 비교하지 않는다
- 취소 구현(`OrderLockingPaymentCanceller`)은 하나다. 잠금 읽기가 이 결제의 **첫 로드**라 S3 의 "락은 잡았는데 값은 잠그기 전" 함정이 없다. 본문은 S3 의 `PaymentSupport.cancel` 그대로다
- 멱등 조율자는 **취소 실행과 요청 hash 를 인자로** 받게 바꿨다 (먼저 동작 무변화 refactor). 주문 기반 취소의 fingerprint 는 `{"orderId","cancelAmount","reason"}`, `operation` 은 같은 `CANCEL` 이다. 같은 키를 두 취소 경로에 쓰면 409 `IDEMPOTENCY_KEY_REUSED` 다 (회귀 5, 양방향)
- 같은 결제를 두 경로로 동시에 7,000 + 7,000 취소하면 한 건만 성공, 잔여 3,000 — 두 경로 모두 결국 같은 PRIMARY 레코드를 `X` 로 잠근다. 양쪽 순서 모두 후속의 대기를 확인했다 (회귀 6)

**인코딩된 경로** — 내장 Tomcat 에 소켓으로 요청 바이트를 직접 써서 실측했다 (`OrderPathServerTest`). MockMvc 는 컨테이너를 거치지 않는다.

| 경로의 주문 id | 결과 |
|---|---|
| `order%2Fs6p-1`, `..%2Forder-s6p-1`, `order-s6p-1%00` | **Tomcat 이 MVC 전에 400.** 본문은 Tomcat 의 HTML — 우리 오류 형식이 아니다 (API_CONTRACT 2.2 의 범위 밖) |
| `order%20s6p`, `caf%C3%A9-order`, `order-s6p-1%20`, `order%2Es6p`, `order-s6p-1%3Bx` | 디코딩되어 컨트롤러에 오고, 형식 규칙이 400 `INVALID_REQUEST` |
| `order-s6p-1;x=1` (인코딩하지 않은 경로 파라미터) | **Tomcat 이 `;x=1` 을 떼어 내고** `order-s6p-1` 로 매핑된다. 조회 200, 취소 200 |

- 세 경우 모두 규칙 밖의 값으로 조회·취소가 실행되지 않는다 (부작용 스냅샷 동일)
- 경로 파라미터 제거는 서블릿 컨테이너의 경로 정규화다. 남은 값이 규칙 안이면 그 주문을 처리한다. `;` 뒤의 값은 애플리케이션에 닿지 않으므로 형식 규칙이 볼 수 없다. 규칙 안의 주문 id 로 같은 요청을 보낸 것과 결과가 같아 막지 않았다

**라우팅** (`RoutingContractApiTest`): `GET /v1/payments/orders` 는 `GET /{paymentKey}`(paymentKey=`orders`), `POST /v1/payments/orders/cancel` 은 `POST /{paymentKey}/cancel` 이 받는다. `GET /v1/payments/orders/cancel` 은 주문 조회(`orderId=cancel`, 6자)다. 검증 순서는 인증 → 본문(인자 해석) → 주문 id 형식 → 멱등키 형식이다.

### 5.4 V7 적용 전 데이터 정리

V7 이 스스로 걸러 주는 것은 중복 주문과 비ASCII 두 가지뿐이다. 정리 절차는 `docker/mysql/scripts/s6-order-cleanup.sql` 이고, 리허설 테스트(`OrderUniqueMigrationRehearsalTest`)가 이 파일을 `@step` 단위로 읽어 **같은 SQL** 을 실행한다. 전용 DB 에서 V6 까지 적용한 뒤 사례별로 확인했다.

| # | 사례 | 결과 |
|---|---|---|
| 1 | 중복 주문이 있는 채로 V7 | 실패 (`Duplicate entry`). 스키마는 V6 그대로 — 단일 인덱스 있음, unique 없음, ai_ci |
| 2 | 비ASCII (`café-order`) | 실패 (`Incorrect string value`). V6 그대로 |

- 작업 테이블은 임시 테이블이 아니라 일반 테이블(`s6_order_fix`)이다. 충돌 검사가 같은 테이블을 한 쿼리에서 두 번 참조하는데, MySQL 의 임시 테이블은 그렇게 쓸 수 없다 (`Can't reopen table`)
- 형식의 DB 강제(CHECK 제약)는 두지 않았다. 사전 조건은 **절차로만** 지켜진다. Flyway 는 애플리케이션 기동 때 V7 을 자동 적용하고 확인 1 을 대신 돌려 주지 않는다

## 8. 다음 단계에 남기는 것

- **S7 은 `payment_v5`(`AbstractV5SchemaTest`)에서 인덱스 없는 실험을 RC 로 다시 돌린다.** `SELECT FOR UPDATE` 는 이미 잠긴 행을 만나면 RC 에서도 기다릴 수 있다. `UPDATE` 의 semi-consistent read 와 비교하려면 같은 조건의 `UPDATE` 문이 필요한데 S6 은 만들지 않았다. 3.3 의 락(PRIMARY 전체 + 페이지 supremum)이 비교 기준이다
- **없는 주문의 갭락**(3.7)이 RC 에서 사라지는지 S7 이 확인한다. 그 결과로 주문 기반 취소를 "비잠금 조회 → PK 잠금" 으로 바꿀지 정한다
- **생성의 재전송 응답**은 종료 점검에서 정한다. 장치(unique), 오류 코드(`DUPLICATE_ORDER`), 주문 id 형식 규칙은 S6 이 남긴다
- **대량 픽스처(`BulkPaymentFixture`)와 락 집계 프로브(`LockWaitProbe.soleHolder`·`locksOf`·`recordLocksOf`)** 는 S10 의 배치 실험(10만 건 `UPDATE`)이 다시 쓴다. 갭 위치를 설명할 때는 페이지 경계를 함께 봐야 한다 (3.5)
- **slow log 의 `Lock_time` 은 행 락 대기를 포함한다** (3.8). S8 의 커넥션·락 대기 관측에서 "느린 쿼리" 와 "기다린 쿼리" 를 구분하는 근거로 쓴다
- **로컬 DB 는 V7 적용 전에 정리가 필요하다** (5.4). 확인 2 가 0행이 될 때까지 기동하지 않는다
