# S2 — 머니 잔액 동시 차감: 차감이 유실된다

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 계획: [plan/S2.md](../plan/S2.md) · 선행 기록: [phase1/S1.md](S1.md)

S1 은 **같은 결제** 한 건의 경쟁을 막았다. 그 조건부 UPDATE 가 잠그는 것은 `payment` 행 하나뿐이므로, **서로 다른 결제가 같은 지갑**을 건드리는 경쟁에는 아무 보호도 주지 않는다.

이 문서는 PR 1 까지의 기록이다. 재현과 원인, 그리고 원자적 감산 비교 실험 2개를 담는다. 락 비교(S2-a 낙관적 / S2-b 비관적)와 본선 전환은 PR 2 에서 이어 적는다.

### 1.1 전략을 어떻게 공존시켰는가

S1 은 갈래가 승인 구현 **둘**(naive / CAS)이라 `@Service` + `@Primary` 로 충분했다. S2 는 잔액 변경 전략이 **다섯**으로 갈라진다. 그래서 갈라지는 지점만 이음매로 뽑았다.

```java
public interface WalletBalanceUpdater {
  void debit(Long walletId, Long paymentId, long amount);   // 승인 차감 + PAY 원장
  Wallet credit(Long memberId, long amount);                // 충전 + CHARGE 원장
}
```

`PaymentSupport.approve` 는 이 전략을 **인자로 받는다.** 빈 하나가 가변 상태로 전략을 바꾸는 방식은 쓰지 않는다. 조합은 `ConcurrencyStrategyConfig` 한곳에 모았다.

| 빈 | 승인 | 잔액 변경 | 용도 |
|---|---|---|---|
| `naivePaymentConfirmer` | naive | naive | S1 재현 (기존 그대로) |
| `naiveDebitConfirmer` | CAS | naive | **S2 재현** |
| `atomicDebitConfirmer` | CAS | 원자적 감산 | 비교 실험 1 |
| `guardedDebitConfirmer` | CAS | 조건부 감산 | 비교 실험 2 |
| `casPaymentConfirmer` (`@Primary`) | CAS | naive | 본선 — **PR 1 시점에는 아직 결함이 있다** |

조합을 빈으로 등록한 이유는 `@Transactional` 프록시다. 프록시는 컨테이너가 만들므로 손으로 조립한 confirmer 에는 트랜잭션 경계가 생기지 않는다. 전략 자체는 호출자의 트랜잭션에 참여할 뿐이라 빈일 필요가 없지만, 조합을 한곳에서 읽히게 하려고 같이 등록했다.

충전을 `memberId` 로 받는 것도 같은 이유다. 지갑을 **어떻게 찾느냐**부터 전략마다 다르다 — naive 는 잠금 없이 잔액까지 읽고, 비관적 락은 id 만 찾은 뒤 `FOR UPDATE` 로 잠그며 읽는다. 호출자가 먼저 찾아서 넘기면 후자가 **잠그기 전에 읽은 엔티티**를 들고 있게 된다.

## 3. 관찰

### 3.1 차감 4건 중 3건이 사라진다

| 항목 | 값 |
|---|---|
| 요청 4건의 결과 | **전부 성공** (검사 시점에는 모두 10,000 을 본다) |
| `payment.status` | 4건 모두 DONE + `approved_at` |
| `wallet.balance` | **7,000** — 차감이 한 번만 반영된다 |
| PAY 원장 | **4건** (각 −3,000) |
| 원장 합계 | 10,000 − 12,000 = **−2,000** |

`wallet.balance(7,000) ≠ SUM(ledger)(−2,000)` — **불변식 1 이 깨진다.** 돈으로 보면 9,000 원이 결제됐는데 지갑에서는 3,000 원만 빠져나갔다.

### 3.2 충전과 승인의 경쟁 — 한쪽이 통째로 사라진다

잔액 10,000 에 충전 5,000 과 승인 3,000 을 동시에 보냈다.

| 항목 | 값 |
|---|---|
| 원장 합계 | 10,000 + 5,000 − 3,000 = **12,000** |
| `wallet.balance` | **7,000 또는 15,000** — 나중에 커밋한 쪽의 절대값만 남는다 |

**12,000 은 나오지 않는다.** 7,000 이면 충전이, 15,000 이면 차감이 통째로 사라진 것이다. 어느 쪽이 이길지는 정해져 있지 않으므로 테스트도 둘 중 하나로 단언한다.

충전 유실이 더 나쁘다. 결제는 실패하면 사용자가 다시 시도하지만, 충전은 **돈이 실제로 들어온 뒤**의 기록이다.

### 3.3 SQL 순서 — 네 트랜잭션이 같은 절대값을 쓴다

`org.hibernate.SQL` + `org.hibernate.orm.jdbc.bind` 로그다 (재현 1).

```
pool-2-thread-3  select ... from wallet where id=?          ┐ 네 워커가 모두
pool-2-thread-1  select ... from wallet where id=?          │ 막힘 없이 통과해
pool-2-thread-4  select ... from wallet where id=?          │ 같은 10,000 을
pool-2-thread-2  select ... from wallet where id=?          ┘ 읽는다
pool-2-thread-3  insert into wallet_ledger ...              ┐ 원장은 4건
pool-2-thread-1  insert into wallet_ledger ...              │ 전부 남는다
...                                                         ┘
pool-2-thread-3  update payment set ... where id=?          ← 결제는 서로 다른 행이라 경쟁하지 않는다
...
pool-2-thread-3  update wallet set balance=? ...  <- [7000] ┐ 같은 행이라 직렬화되지만
pool-2-thread-4  update wallet set balance=? ...  <- [7000] │ 네 문장이 쓰는 값은
pool-2-thread-2  update wallet set balance=? ...  <- [7000] │ 모두 7000 이다
pool-2-thread-1  update wallet set balance=? ...  <- [7000] ┘
```

**직렬화가 일어나는데도 유실된다**는 것이 이 로그의 핵심이다. 행 락은 네 UPDATE 를 한 줄로 세우지만, 각 문장이 쓰는 값은 이미 자기 트랜잭션의 스냅샷에서 계산된 절대값이다. 락은 "동시에 쓰는 것"을 막을 뿐 "낡은 값으로 계산한 것"을 막지 못한다.

S1 의 로그(`phase1/S1.md` 3.3)와 flush 순서가 같다 — 원장 INSERT → `update payment` → `update wallet`. 승인이 `payment → wallet` 순서로 잠근다는 전제는 유지된다.

## 4. 원인

read-modify-write 의 Lost Update 다.

- **읽기**: RR 의 일반 SELECT 는 consistent non-locking read 다. 잠그지 않으므로 넷이 모두 같은 값을 읽는다
- **계산**: `wallet.getBalance() - amount` — 스냅샷 값으로 계산한다
- **쓰기**: flush 시점의 `UPDATE wallet SET balance = <절대값>`. 행 락으로 직렬화되지만, 값은 이미 정해져 있다

읽기가 잠그지 않으므로 RC 에서도 같다. **격리 수준 전환은 해결책이 아니다.** 고칠 지점은 "읽은 값으로 계산한 절대값을 쓴다"는 것 자체다.

## 5. 원자적 감산 비교 실험 (SCENARIO 139~140행)

재현과 **같은 시작 데이터·같은 워커 수**에서 잔액 변경 전략만 바꿔 독립 실행했다. 달라지는 것이 하나뿐이어야 결과의 차이를 그 하나로 설명할 수 있다.

### 5.1 실험 1 — 검사 후 원자적 감산: 합계는 맞는데 잔액이 음수다

```sql
UPDATE wallet SET balance = balance - ? WHERE id = ?
```

| 항목 | 값 |
|---|---|
| 요청 4건의 결과 | 전부 성공 |
| `wallet.balance` | **−2,000** |
| PAY 원장 | 4건 |
| 원장 합계 | **−2,000** — 잔액과 일치한다 |

읽은 값이 아니라 **DB 의 현재 값**에서 빼므로 차감 유실은 사라졌다. 네 번의 감산이 모두 반영되고 `balance == SUM(ledger)` 도 회복된다.

**그런데 잔액이 음수가 된다.** 검사가 여전히 감산 문장 **밖**에 있기 때문이다.

```
pool-3-thread-2  SELECT balance FROM wallet WHERE id = ?        ┐ 넷이 모두
pool-3-thread-3  SELECT balance FROM wallet WHERE id = ?        │ 10,000 을 보고
pool-3-thread-4  SELECT balance FROM wallet WHERE id = ?        │ 검사를
pool-3-thread-1  SELECT balance FROM wallet WHERE id = ?        ┘ 통과한다
pool-3-thread-2  UPDATE wallet SET balance = balance - ? ...    ┐ 그리고 전부
pool-3-thread-4  UPDATE wallet SET balance = balance - ? ...    │ 감산에
pool-3-thread-3  UPDATE wallet SET balance = balance - ? ...    │ 성공한다
pool-3-thread-1  UPDATE wallet SET balance = balance - ? ...    ┘
```

**이 실험의 관찰이 S2 에서 가장 값지다.** 불변식 1 의 두 조건("합계 일치"와 "음수 아님") 중 하나만 깨지는 것을 보여 주기 때문이다. 잔액 합계만 보고 "고쳤다"고 판단하면 통과하는 결함이다. Phase 0 이 `UNSIGNED`/`CHECK` 를 일부러 넣지 않은 이유(V1 주석)가 여기서 회수된다 — DB 가 막았다면 이 실험은 SQL 에러로 끝나고 관찰이 사라졌을 것이다.

### 5.2 실험 2 — 조건부 감산: 검사까지 문장 안으로

```sql
UPDATE wallet SET balance = balance - ? WHERE id = ? AND balance >= ?
```

| 항목 | 값 |
|---|---|
| 요청 4건의 결과 | **성공 3 / 잔액 부족 1** |
| `wallet.balance` | **1,000** |
| PAY 원장 | 3건 |
| 거절된 결제 | `READY` (커밋된 `IN_PROGRESS` 없음), 원장 0건 |
| 불변식 1·2·3 | **모두 유지** |

S1 이 상태 전이에 쓴 방법과 같은 모양이다. 검사를 WHERE 로 들여보내면 검사와 감산 사이의 틈이 사라진다. 뒤늦게 도착한 요청은 앞선 요청이 커밋한 **최신 값**으로 조건을 재평가하므로, 네 번째는 1,000 < 3,000 으로 0 건 갱신이 되어 탈락한다. 완료 기준(SCENARIO 146행)을 이미 만족하는 유효한 해결책이다.

**탈락 판정에 잔액을 주장하지 않는다.** 탈락자는 아무 행도 바꾸지 않았고 RR 스냅샷은 앞선 조회 시점에 고정돼 있어서, 이어서 평범하게 SELECT 하면 1,000 이 아니라 **10,000** 이 돌아온다. S1 의 `lostConfirmRace`([phase1/S1.md 5.4](S1.md))와 같은 함정이다. 그래서 `InsufficientBalanceException.notEnough(walletId, amount)` 는 잔액을 메시지에 담지 않는다. 실제로 읽은 값을 아는 경로(naive / 원자적 감산 / 비관적 락)는 기존 생성자를 그대로 쓴다.

API 계약은 변하지 않는다. `ApiExceptionHandler` 는 여전히 409 `INSUFFICIENT_BALANCE` 로 매핑한다.

### 5.3 영속성 컨텍스트 — 원자적 UPDATE 가 결제를 `IN_PROGRESS` 로 커밋시킬 뻔했다

두 실험 모두 **`Wallet` 엔티티를 로드하지 않는다.** 스칼라 조회(`findBalanceById`) 또는 아예 조회 없이 native `@Modifying` UPDATE 만 쓴다.

엔티티를 들고 있으면 native UPDATE 뒤에 영속성 컨텍스트와 DB 가 갈라진다. 그걸 맞추려고 `@Modifying(clearAutomatically = true)` 를 켜는 것이 자연스러운 반응인데, `EntityManager.clear()` 는 **지갑만 골라서 비울 수 없다.** 승인 흐름에서는 그 시점에 `Payment` 가 관리 중이고, `PaymentSupport.approve` 는 **마지막에** 그 엔티티를 DONE 으로 바꾼다.

```java
else { updater.debit(...); }              // ← 여기서 em.clear() 가 일어나면
payment.setStatus(PaymentStatus.DONE);    // 이미 detached 다
payment.setApprovedAt(LocalDateTime.now());
```

결과는 `approved_at` 유실 정도가 아니라 **결제가 `IN_PROGRESS` 로 커밋되는 것**이다. S1 이 "이 단계에서 커밋된 IN_PROGRESS 로 설명하지 않는다"(SCENARIO 127행)고 못 박은 현상을 S8 보다 여섯 단계 앞서 사고로 만들어 내는 셈이다.

더 나쁜 것은 **실험 2 의 기대값(잔액 1,000 / PAY 원장 3건)은 그대로 통과한다**는 점이다. 잔액과 원장만 보면 보이지 않는다. 그래서 **모든 성공 경로 단언에 `status = DONE` 과 `approved_at IS NOT NULL` 을 넣었다.**

읽지 않으면 맞출 것도 없다는 것이 이번 선택이다. `flushAutomatically` 도 기본값으로 뒀다 — 이 UPDATE 앞에 먼저 반영해야 할 미반영 변경이 이 흐름에 없기 때문이다. (이 옵션은 Spring Data 가 `em.flush()` 를 먼저 부르지 않는다는 뜻일 뿐, Hibernate 의 자동 flush 를 금지하지 않는다. 두 이야기를 섞지 않는다.)

### 5.4 세 전략 비교

| 전략 | 차감 유실 | 음수 잔액 | 불변식 1 | 비고 |
|---|---|---|---|---|
| naive (재현) | **발생** | — | 깨짐 (합계 불일치) | 잔액 7,000 / 원장 −2,000 |
| 원자적 감산 | 없음 | **발생** | 깨짐 (음수) | 잔액 −2,000 = 원장 합계 |
| 조건부 감산 | 없음 | 없음 | 유지 | 성공 3 / 부족 1, 잔액 1,000 |

조건부 감산은 그 자체로 유효한 해결책이다. 그럼에도 본선은 비관적 락으로 갈 예정이다(SCENARIO 145행). 그 선택의 근거 — 낙관적/비관적의 경합 측정과, 취소·정산까지 같은 규칙으로 묶을 때 조건부 UPDATE 가 어디서 한계를 보이는지 — 는 PR 2 에서 이어 적는다.

## 6. PR 1 시점의 상태

- 본선(`@Primary`)은 **CAS + naive** 다. main 에 차감 유실이 그대로 남아 있다
- 낙관적 락(`version` 컬럼, V2), 비관적 락, 재시도, 경합 측정, 락 관측은 PR 2
- 테스트 **86개 green** (Phase 0 69 + S1 12 + S2 5)
