# S2 — 머니 잔액 동시 차감: 차감이 유실된다

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 계획: [plan/S2.md](../plan/S2.md) · 선행 기록: [phase1/S1.md](S1.md)

S1 은 **같은 결제** 한 건의 경쟁을 막았다. 그 조건부 UPDATE 가 잠그는 것은 `payment` 행 하나뿐이므로, **서로 다른 결제가 같은 지갑**을 건드리는 경쟁에는 아무 보호도 주지 않는다.

잔액 변경 전략 다섯을 같은 조건에서 돌려 비교했다. 재현(naive) → 원자적 감산 → 조건부 감산 → 낙관적 락 → 비관적 락 순이며, 본선은 마지막이다.

## 1. 전제

| 항목 | 상태 |
|---|---|
| 스키마 | V1 그대로. **마이그레이션을 추가하지 않았다** — 낙관적 락의 `version` 컬럼은 PR 2 의 V2 다 |
| 제약 | FK 0건, `wallet_ledger` FK 없음 (S4 의 대상), 잔액에 `UNSIGNED`/`CHECK` 없음 |
| 격리 수준 | REPEATABLE READ |
| 구현 | **S1 적용 누적** — 승인의 상태 전이는 조건부 UPDATE, 잔액 변경은 Phase 0 naive |
| 트랜잭션 경계 | 승인 전체가 단일 트랜잭션 (S8 전까지) |
| 워커 수 | 4 (게이트 대기 중 커넥션을 점유하므로 풀 크기 10 보다 작아야 한다) |
| 시작 데이터 | 지갑 잔액 10,000 (충전으로 심는다), 결제 4건 × 3,000, **워커마다 다른 결제** |

버전은 [phase0/README.md 1절](../phase0/README.md)과 같다.

**워커마다 다른 결제를 쓰는 것이 S1 과의 분리 조건이다** (SCENARIO 134행). 같은 결제를 쓰면 S1 의 CAS 가 한 명만 통과시켜 경쟁 자체가 사라진다. 공유하는 것은 지갑 하나뿐이다.

### 1.1 전략을 어떻게 공존시켰는가

S1 은 갈래가 승인 구현 **둘**(naive / CAS)이라 `@Service` + `@Primary` 로 충분했다. S2 는 잔액 변경 전략이 **다섯**으로 갈라진다. 그래서 갈라지는 지점만 이음매로 뽑았다.

```java
public interface WalletBalanceUpdater {
  void debit(Long walletId, Long paymentId, long amount);   // 승인 차감 + PAY 원장
  Wallet credit(Long memberId, long amount);                // 충전 + CHARGE 원장
}
```

`PaymentSupport.approve` 는 이 전략을 **인자로 받는다.** 빈 하나가 가변 상태로 전략을 바꾸는 방식은 쓰지 않는다. 조합은 `ConcurrencyStrategyConfig` 한곳에 모았다.

| 빈 | 승인 | 잔액 변경 | 용도 |
|---|---|---|---|
| `naivePaymentConfirmer` | naive | naive | S1 재현 (기존 그대로) |
| `naiveDebitConfirmer` | CAS | naive | **S2 재현** |
| `atomicDebitConfirmer` | CAS | 원자적 감산 | 비교 실험 1 |
| `guardedDebitConfirmer` | CAS | 조건부 감산 | 비교 실험 2 |
| `casPaymentConfirmer` (`@Primary`) | CAS | naive | 본선 — **PR 1 시점에는 아직 결함이 있다** |

조합을 빈으로 등록한 이유는 `@Transactional` 프록시다. 프록시는 컨테이너가 만들므로 손으로 조립한 confirmer 에는 트랜잭션 경계가 생기지 않는다. 전략 자체는 호출자의 트랜잭션에 참여할 뿐이라 빈일 필요가 없지만, 조합을 한곳에서 읽히게 하려고 같이 등록했다.

충전을 `memberId` 로 받는 것도 같은 이유다. 지갑을 **어떻게 찾느냐**부터 전략마다 다르다 — naive 는 잠금 없이 잔액까지 읽고(재현 경로가 여기 걸린다), 비관적 락은 id 만 찾은 뒤 `FOR UPDATE` 로 잠그며 읽는다. 호출자가 스칼라 id 만 조회해 넘기는 방식도 가능하지만, 그러면 두 조회 경로가 서비스와 전략에 나뉘어 놓인다. 어느 전략이 지갑을 어떻게 읽는지를 한곳에서 읽히게 하려는 **설계 선택**이다.

다만 호출자가 **엔티티를** 먼저 로드해 넘기는 방식은 실제로 위험하다. 그 뒤 `FOR UPDATE` 로 같은 id 를 조회해도 영속성 컨텍스트에 이미 있는 엔티티는 상태가 갱신되지 않아, 락은 잡았는데 값은 잠그기 전의 것이 된다.

## 2. 재현

| # | 배선 | 게이트 | 워커 |
|---|---|---|---|
| 재현 1 | `naiveDebitConfirmer` | `WALLET_READ` (`WalletRepository.findById` 반환 직후) | 4 |
| 재현 2 | `naiveWalletService` 충전 1 + `naiveDebitConfirmer` 승인 1 | `WALLET_READ` | 2 |

재현 2 의 두 워커는 **서로 다른 메서드**로 잔액을 읽는다. 충전은 `findByMemberId`, 승인은 `findById` 다. 둘 다 같은 `WALLET_READ` 지점으로 묶어 "모두 같은 잔액을 읽은 시점"을 맞췄다.

`WalletLostUpdateReproductionTest` 는 깨진 결과를 그대로 assert 하므로 **결함이 재현될 때 green** 이다. 본선이 바뀐 뒤에도 naive 전략을 고른 이 빈들은 계속 같은 결과를 낸다.

## 3. 관찰

### 3.1 차감 4건 중 3건이 사라진다

| 항목 | 값 |
|---|---|
| 요청 4건의 결과 | **전부 성공** (검사 시점에는 모두 10,000 을 본다) |
| `payment.status` | 4건 모두 DONE + `approved_at` |
| `wallet.balance` | **7,000** — 차감이 한 번만 반영된다 |
| PAY 원장 | **4건** (각 −3,000) |
| 원장 합계 | 10,000 − 12,000 = **−2,000** |

`wallet.balance(7,000) ≠ SUM(ledger)(−2,000)` — **불변식 1 이 깨진다.** 돈으로 보면 12,000 원이 결제됐는데 지갑에서는 3,000 원만 빠져나가 9,000 원이 어긋난다.

### 3.2 충전과 승인의 경쟁 — 한쪽이 통째로 사라진다

잔액 10,000 에 충전 5,000 과 승인 3,000 을 동시에 보냈다.

| 항목 | 값 |
|---|---|
| 원장 합계 | 10,000 + 5,000 − 3,000 = **12,000** |
| `wallet.balance` | **7,000 또는 15,000** — 나중에 커밋한 쪽의 절대값만 남는다 |

**12,000 은 나오지 않는다.** 7,000 이면 충전이, 15,000 이면 차감이 통째로 사라진 것이다. 어느 쪽이 이길지는 정해져 있지 않으므로 테스트도 둘 중 하나로 단언한다.

충전 유실이 더 나쁘다. 결제는 실패하면 사용자가 다시 시도하지만, 충전은 **돈이 실제로 들어온 뒤**의 기록이다.

### 3.3 SQL 순서 — 네 트랜잭션이 같은 절대값을 쓴다

`org.hibernate.SQL` + `org.hibernate.orm.jdbc.bind` 로그다 (재현 1).

```
pool-2-thread-3  select ... from wallet where id=?          ┐ 네 워커가 모두
pool-2-thread-1  select ... from wallet where id=?          │ 막힘 없이 통과해
pool-2-thread-4  select ... from wallet where id=?          │ 같은 10,000 을
pool-2-thread-2  select ... from wallet where id=?          ┘ 읽는다
pool-2-thread-3  insert into wallet_ledger ...              ┐ 원장은 4건
pool-2-thread-1  insert into wallet_ledger ...              │ 전부 남는다
...                                                         ┘
pool-2-thread-3  update payment set ... where id=?          ← 결제는 서로 다른 행이라 경쟁하지 않는다
...
pool-2-thread-3  update wallet set balance=? ...  <- [7000] ┐ 같은 행이라 직렬화되지만
pool-2-thread-4  update wallet set balance=? ...  <- [7000] │ 네 문장이 쓰는 값은
pool-2-thread-2  update wallet set balance=? ...  <- [7000] │ 모두 7000 이다
pool-2-thread-1  update wallet set balance=? ...  <- [7000] ┘
```

**직렬화가 일어나는데도 유실된다**는 것이 이 로그의 핵심이다. 행 락은 네 UPDATE 를 한 줄로 세우지만, 각 문장이 쓰는 값은 이미 자기 트랜잭션의 스냅샷에서 계산된 절대값이다. 락은 "동시에 쓰는 것"을 막을 뿐 "낡은 값으로 계산한 것"을 막지 못한다.

S1 의 로그(`phase1/S1.md` 3.3)와 flush 순서가 같다 — 원장 INSERT → `update payment` → `update wallet`. 승인이 `payment → wallet` 순서로 잠근다는 전제는 유지된다.

## 4. 원인

read-modify-write 의 Lost Update 다.

- **읽기**: RR 의 일반 SELECT 는 consistent non-locking read 다. 잠그지 않으므로 넷이 모두 같은 값을 읽는다
- **계산**: `wallet.getBalance() - amount` — 스냅샷 값으로 계산한다
- **쓰기**: flush 시점의 `UPDATE wallet SET balance = <절대값>`. 행 락으로 직렬화되지만, 값은 이미 정해져 있다

읽기가 잠그지 않으므로 RC 에서도 같다. **격리 수준 전환은 해결책이 아니다.** 고칠 지점은 "읽은 값으로 계산한 절대값을 쓴다"는 것 자체다.

## 5. 원자적 감산 비교 실험 (SCENARIO 139~140행)

재현과 **같은 시작 데이터·같은 워커 수**에서 잔액 변경 전략만 바꿔 독립 실행했다. 달라지는 것이 하나뿐이어야 결과의 차이를 그 하나로 설명할 수 있다.

### 5.1 실험 1 — 검사 후 원자적 감산: 합계는 맞는데 잔액이 음수다

```sql
UPDATE wallet SET balance = balance - ? WHERE id = ?
```

| 항목 | 값 |
|---|---|
| 요청 4건의 결과 | 전부 성공 |
| `wallet.balance` | **−2,000** |
| PAY 원장 | 4건 |
| 원장 합계 | **−2,000** — 잔액과 일치한다 |

읽은 값이 아니라 **DB 의 현재 값**에서 빼므로 차감 유실은 사라졌다. 네 번의 감산이 모두 반영되고 `balance == SUM(ledger)` 도 회복된다.

**그런데 잔액이 음수가 된다.** 검사가 여전히 감산 문장 **밖**에 있기 때문이다.

```
pool-3-thread-2  SELECT balance FROM wallet WHERE id = ?        ┐ 넷이 모두
pool-3-thread-3  SELECT balance FROM wallet WHERE id = ?        │ 10,000 을 보고
pool-3-thread-4  SELECT balance FROM wallet WHERE id = ?        │ 검사를
pool-3-thread-1  SELECT balance FROM wallet WHERE id = ?        ┘ 통과한다
pool-3-thread-2  UPDATE wallet SET balance = balance - ? ...    ┐ 그리고 전부
pool-3-thread-4  UPDATE wallet SET balance = balance - ? ...    │ 감산에
pool-3-thread-3  UPDATE wallet SET balance = balance - ? ...    │ 성공한다
pool-3-thread-1  UPDATE wallet SET balance = balance - ? ...    ┘
```

**이 실험의 관찰이 S2 에서 가장 값지다.** 불변식 1 의 두 조건("합계 일치"와 "음수 아님") 중 하나만 깨지는 것을 보여 주기 때문이다. 잔액 합계만 보고 "고쳤다"고 판단하면 통과하는 결함이다. Phase 0 이 `UNSIGNED`/`CHECK` 를 일부러 넣지 않은 이유(V1 주석)가 여기서 회수된다 — DB 가 막았다면 이 실험은 SQL 에러로 끝나고 관찰이 사라졌을 것이다.

### 5.2 실험 2 — 조건부 감산: 검사까지 문장 안으로

```sql
UPDATE wallet SET balance = balance - ? WHERE id = ? AND balance >= ?
```

| 항목 | 값 |
|---|---|
| 요청 4건의 결과 | **성공 3 / 잔액 부족 1** |
| `wallet.balance` | **1,000** |
| PAY 원장 | 3건 |
| 거절된 결제 | `READY` (커밋된 `IN_PROGRESS` 없음), 원장 0건 |
| 불변식 1·2·3 | **모두 유지** |

S1 이 상태 전이에 쓴 방법과 같은 모양이다. 검사를 WHERE 로 들여보내면 검사와 감산 사이의 틈이 사라진다. 뒤늦게 도착한 요청은 앞선 요청이 커밋한 **최신 값**으로 조건을 재평가하므로, 네 번째는 1,000 < 3,000 으로 0 건 갱신이 되어 탈락한다. 완료 기준(SCENARIO 146행)을 이미 만족하는 유효한 해결책이다.

**탈락 판정에 잔액을 주장하지 않는다.** 탈락자는 아무 행도 바꾸지 않았고 RR 스냅샷은 앞선 조회 시점에 고정돼 있어서, 이어서 평범하게 SELECT 하면 1,000 이 아니라 **10,000** 이 돌아온다. S1 의 `lostConfirmRace`([phase1/S1.md 5.4](S1.md))와 같은 함정이다. 그래서 `InsufficientBalanceException.notEnough(walletId, amount)` 는 잔액을 메시지에 담지 않는다. 실제로 읽은 값을 아는 경로(naive / 원자적 감산 / 비관적 락)는 기존 생성자를 그대로 쓴다.

API 계약은 변하지 않는다. `ApiExceptionHandler` 는 여전히 409 `INSUFFICIENT_BALANCE` 로 매핑한다.

### 5.3 영속성 컨텍스트 — 원자적 UPDATE 가 결제를 `IN_PROGRESS` 로 커밋시킬 뻔했다

두 실험 모두 **`Wallet` 엔티티를 로드하지 않는다.** 스칼라 조회(`findBalanceById`) 또는 아예 조회 없이 native `@Modifying` UPDATE 만 쓴다. (조건부 감산은 갱신 0 건일 때만 `existsById` 로 지갑 존재를 한 번 더 확인한다. 0 건의 이유가 잔액 부족인지 지갑 부재인지 구분하지 않으면 이 전략만 실패의 의미가 달라지기 때문이다 — 잔액은 여전히 읽지 않는다.)

엔티티를 들고 있으면 native UPDATE 뒤에 영속성 컨텍스트와 DB 가 갈라진다. 그걸 맞추려고 `@Modifying(clearAutomatically = true)` 를 켜는 것이 자연스러운 반응인데, `EntityManager.clear()` 는 **지갑만 골라서 비울 수 없다.** 승인 흐름에서는 그 시점에 `Payment` 가 관리 중이고, `PaymentSupport.approve` 는 **마지막에** 그 엔티티를 DONE 으로 바꾼다.

```java
else { updater.debit(...); }              // ← 여기서 em.clear() 가 일어나면
payment.setStatus(PaymentStatus.DONE);    // 이미 detached 다
payment.setApprovedAt(LocalDateTime.now());
```

결과는 `approved_at` 유실 정도가 아니라 **결제가 `IN_PROGRESS` 로 커밋되는 것**이다. S1 이 "이 단계에서 커밋된 IN_PROGRESS 로 설명하지 않는다"(SCENARIO 127행)고 못 박은 현상을 S8 보다 여섯 단계 앞서 사고로 만들어 내는 셈이다.

더 나쁜 것은 **실험 2 의 기대값(잔액 1,000 / PAY 원장 3건)은 그대로 통과한다**는 점이다. 잔액과 원장만 보면 보이지 않는다. 그래서 **모든 성공 경로 단언에 `status = DONE` 과 `approved_at IS NOT NULL` 을 넣었다.**

읽지 않으면 맞출 것도 없다는 것이 이번 선택이다. `flushAutomatically` 도 기본값으로 뒀다 — 이 UPDATE 앞에 먼저 반영해야 할 미반영 변경이 이 흐름에 없기 때문이다. (이 옵션은 Spring Data 가 `em.flush()` 를 먼저 부르지 않는다는 뜻일 뿐, Hibernate 의 자동 flush 를 금지하지 않는다. 두 이야기를 섞지 않는다.)

### 5.4 세 전략 비교

| 전략 | 차감 유실 | 음수 잔액 | 불변식 1 | 비고 |
|---|---|---|---|---|
| naive (재현) | **발생** | — | 깨짐 (합계 불일치) | 잔액 7,000 / 원장 −2,000 |
| 원자적 감산 | 없음 | **발생** | 깨짐 (음수) | 잔액 −2,000 = 원장 합계 |
| 조건부 감산 | 없음 | 없음 | 유지 | 성공 3 / 부족 1, 잔액 1,000 |

조건부 감산은 그 자체로 유효한 해결책이다. 그럼에도 본선은 비관적 락이다(SCENARIO 145행). 남은 두 전략과 그 선택의 근거는 6절이다.

## 6. 락 비교와 본선 전환

조건부 감산(실험 2)으로 이미 완료 기준을 만족했다. 그럼에도 락 비교를 하는 이유는 **선택의 근거를 관측으로 남기는 것**이 이 단계의 과제이기 때문이다 (SCENARIO 145행).

### 6.1 S2-a 낙관적 락 — `@Version` 을 어디에 붙일 수 있는가

차감 코드는 naive 와 **같다.** 읽고, 검사하고, 계산한 절대값을 저장한다. 달라지는 것은 엔티티에 `@Version` 이 있다는 것 하나뿐이고, 그래서 flush 시점의 UPDATE 가 `... WHERE id=? AND version=?` 가 된다. 내가 읽은 뒤 누군가 커밋했다면 0 건이 갱신되고 Hibernate 가 충돌로 보고한다.

**`Wallet` 에는 붙일 수 없었다.** 붙이는 순간 naive 구현까지 낙관적 락을 갖게 되어 S2 재현이 사라진다. S1 에서 CAS 를 `@Primary` 로 올리자 재현 테스트가 깨졌던 것과 같은 문제이고, 그때의 해법(구현을 갈라 공존시킨다)을 엔티티에 적용해 같은 `wallet` 테이블을 가리키는 두 번째 엔티티 `VersionedWallet` 을 만들었다. V2 는 컬럼만 추가한다.

**대신 보호 범위에 제한이 생긴다.** 다른 전략의 UPDATE 는 `version` 을 올리지 않으므로, 낙관적 락은 **참가자가 모두 optimistic 전략일 때만** 유실을 막는다. 실습 규약으로 고정했다 — 낙관적 실험은 참가자 전원이 optimistic 이고, 충전은 사전 시딩만 하며, 한 트랜잭션에서 두 엔티티를 함께 변경하지 않는다.

이건 실습의 편의가 아니라 **낙관적 락의 성질**이기도 하다. 버전을 올리지 않는 경로가 하나라도 남아 있으면 그 경로가 보호를 무력화한다. 실무에서 `@Version` 을 본선으로 쓰려면 그 행을 바꾸는 모든 코드가 같은 엔티티를 지나야 한다.

### 6.2 재시도는 트랜잭션 바깥에서

```
RetryingPaymentConfirmer (트랜잭션 없음)  →  optimisticDebitConfirmer (@Transactional)
```

충돌은 flush/commit 에서 터지고 **트랜잭션 전체가 롤백**된다 (SCENARIO 97행). 전략은 confirmer 의 트랜잭션 안에 있으므로 재시도는 confirmer 바깥을 감싸야 한다. 데코레이터에 `@Transactional` 을 붙이면 재시도가 이미 롤백이 예정된 같은 트랜잭션 안에서 돌아 아무 의미가 없다. Spring Retry 는 쓰지 않았다 — advice 순서를 확인하는 대신 경계가 코드에 보이게 했다.

**S1 의 트랜잭션 경계 결정이 여기서 값을 한다.** 롤백되면 CAS 의 `IN_PROGRESS` 전이도 함께 취소되므로(SCENARIO 127행), 재시도는 다시 `READY` 를 보고 CAS 를 정상적으로 통과한다. 만약 `IN_PROGRESS` 를 별도 트랜잭션으로 먼저 커밋했다면 재시도가 자기 자신의 상태 전이에 막혔을 것이다 — 그 경계 분리는 S8 의 주제다.

**재시도 대상은 낙관적 충돌뿐이다.** 잔액 부족은 이 요청의 업무상 거절이라 그대로 올려보낸다. 다시 해도 결과가 같고, 무엇보다 실패의 의미가 다르다.

`maxAttempts = 4`(최초 호출 포함)의 근거: 버전을 올리는 것은 **커밋에 성공한 차감뿐**이고 잔액 10,000 / 건당 3,000 이면 성공은 최대 3건이다. 따라서 어떤 워커도 최대 3회까지만 충돌할 수 있어 4번째 시도에서 반드시 판정이 난다. 실제로 상한 초과는 한 번도 나오지 않았다.

### 6.3 재시도 테스트를 둘로 나눈 이유

`ConcurrencyGate` 는 **스레드당 한 번만** 통과를 막는다. 그래서 2차 시도부터는 워커들이 동기화 없이 흩어지고, 상한 초과 여부가 **결정적이지 않다** — 우연히 겹치면 나고 아니면 안 난다. 참가자 수도 라운드마다 줄어(4→3→2) 고정 참가자 barrier 로 재무장하기 어렵다.

| 테스트 | 범위 |
|---|---|
| `OptimisticLockConcurrencyTest` (컨테이너) | 1차 충돌 → 전체 롤백 → 재시도 성공, 그리고 최종 상태(성공 3 / 부족 1, 잔액 1,000, `version = 3`) |
| `RetryPolicyTest` (컨테이너 없음) | 예외를 k 번 던지는 통제된 delegate 로 최대 시도·상한 초과·카운터·지연 |

충돌 **하한**은 결정적이다. 1차 시도에서 넷이 같은 버전을 읽으므로 커밋에 성공하는 것은 하나뿐이고, 나머지 3건은 반드시 충돌한다. 그래서 `충돌 ≥ 3` 은 단언에 쓸 수 있다.

### 6.4 S2-b 비관적 락 — 본선

```sql
SELECT ... FROM wallet WHERE id = ? FOR UPDATE
```

읽는 순간 X 락을 잡고 트랜잭션 종료까지 유지한다. 그래서 "읽고 → 검사하고 → 계산한 값을 저장한다" 라는 **코드 모양을 그대로 두고도** 유실이 사라진다. 뒤이어 온 요청은 앞선 요청이 커밋한 잔액을 보고 검사한다.

충전도 같은 순서를 따른다. **id 만 먼저 찾고**(`findIdByMemberId`) 잔액은 잠그며 읽는다. 지갑을 평범하게 읽어 둔 뒤 같은 id 를 `FOR UPDATE` 로 조회하면 영속성 컨텍스트에 이미 있는 엔티티가 그대로 돌아와, **락은 잡았는데 값은 잠그기 전의 것**이 된다. 이것이 `credit` 이 `memberId` 를 받는 실질적인 이유다.

회귀 3건 모두 green 이다 (`WalletLockRegressionTest`).

| 회귀 | 게이트 | 결과 |
|---|---|---|
| 서로 다른 결제 4건 | `PAYMENT_READ` ×4 | 성공 3 / 부족 1, 잔액 1,000, PAY 원장 3건 |
| 충전 1 + 승인 1 | `WALLET_LOCK_ATTEMPT` ×2 | 잔액 **12,000** = 원장 합계 (재현에서는 나오지 않던 값) |
| 같은 결제 5건 | `PAYMENT_READ` ×5 | 성공 1건 — **S1 회귀 유지** |

**게이트를 하나 추가해야 했다.** `FOR UPDATE` 조회의 **반환 직후**에는 게이트를 걸 수 없다 — 먼저 락을 잡은 워커가 거기서 대기하는 동안 나머지는 락에 막혀 게이트에 도달하지 못해 테스트가 영영 멈춘다. 그래서 **호출 직전** 지점 `WALLET_LOCK_ATTEMPT` 를 만들었다. 승인과 충전 두 경로가 wallet 락을 잡기 전에 만나는 유일한 공통 지점이고, 충전은 `PaymentRepository` 를 아예 타지 않으므로 `PAYMENT_READ` 로는 맞출 수 없다.

이 게이트가 보장하는 것은 **참가자 누구도 아직 wallet 락을 잡지 않았다**는 것뿐이다. 승인 워커는 그 시점에 이미 CAS 로 payment 의 X 락을 들고 있다. 또한 DB 락 **대기**가 실제로 일어났다는 증거도 아니다 — 동시 출발만 보장하며, 대기 관계는 6.6 의 캡처로 따로 남긴다.

### 6.5 경합 관찰 (SCENARIO 143행)

잔액 부족과 락 충돌을 분리하려고 **회차마다 넉넉한 잔액을 새로 심고** 전건 성공하는 조건에서 쟀다. 시딩·정리는 계측에서 제외하고 경쟁 구간만 쟀다. 워커 4, 건당 3,000, 단일 지갑, 5회차 (`LockContentionObservationTest`).

| 전략 | 총 소요(ms) | 요청 지연 평균(ms) | 최대(ms) | 충돌 | 재시도 | 상한 초과 | 백오프 합(설정, ms) |
|---|---|---|---|---|---|---|---|
| 낙관적 (백오프 20ms) | 108–143 | 59–89 | 108–142 | 6 | 6 | 0 | 120 |
| 낙관적 (백오프 0) | 34–46 | 21–29 | 34–46 | 6 | 6 | 0 | 0 |
| 비관적 | 15–18 | 11–13 | 15–18 | 0 | 0 | 0 | 0 |

**낙관적 락을 두 번 쟀다.** 재시도 사이의 대기는 우리가 정한 값이므로, 그걸 빼지 않으면 "낙관적 락이 느리다" 가 아니라 "우리가 넣은 sleep 이 길다" 를 관측하고 끝난다.

표의 백오프 합 120ms 는 **회차당 설정값의 합**(재시도 6회 × 20ms)이다. 실제 대기를 계측한 값이 아니고, 워커들의 대기가 병렬로 겹치므로 **총 소요의 구성 요소로 읽으면 안 된다.** 백오프가 차지하는 몫은 같은 조건에서 백오프만 0 으로 바꿔 본 결과가 말해 준다 — 총 소요 108~143ms 가 **34~46ms** 로 내려간다.

- **충돌 6건이 회차마다 같다.** 4명이 같은 버전을 읽으면 3건이 충돌하고, 남은 3명이 2건, 그다음 1건 — 3+2+1 = 6 이다. 동시 출발이 맞춰졌을 때의 상한이 그대로 나왔다
- **백오프를 없애도 비관적의 약 2배다.** 충돌한 트랜잭션은 통째로 버려진 작업이다. 이 조건에서는 회차당 커밋 4회 + 롤백 6회 = 10회의 트랜잭션을 실행해 4건을 처리한다
- **비관적은 대기가 락 큐에서 일어나고 작업을 버리지 않는다.** 그래서 이 조건에서는 소요도 지연도 가장 낮다
- **일반적인 우열이 아니다.** 단일 지갑에 워커 4를 몰아넣은 조건, 즉 충돌률이 사실상 100% 인 조건의 관측이다. 충돌이 드문 워크로드라면 잠그지 않고 지나가는 낙관적 락이 유리할 수 있다
- **성능 수치에는 단언을 걸지 않았다.** CI 임계값으로 만들면 flaky 해진다. green 조건은 정합성 단언(전건 성공, 잔액 == 원장 합계)뿐이다

본선을 비관적 락으로 정한 근거는 이 수치만이 아니다. 검사할 것이 늘어나도 같은 자리에서 표현되고, 취소(S3)·정산까지 같은 규칙으로 묶을 수 있으며, `payment → wallet` 선행 잠금이 S4 의 FK 락 승격 데드락을 예방한다. 조건부 감산도 유효한 해결책으로 남긴다.

### 6.6 락 관측

로컬 docker-compose MySQL 에 `root` 로 붙어 직접 봤다. 승인 트랜잭션이 `payment` 를 CAS 로 갱신한 뒤 지갑을 `FOR UPDATE` 로 잠그고 있고, 충전 트랜잭션이 같은 지갑을 잠그려 대기하는 상태다.

```
object_name  index_name              lock_type  lock_mode      lock_status  lock_data
payment      NULL                    TABLE      IX             GRANTED      NULL
payment      PRIMARY                 RECORD     X,REC_NOT_GAP  GRANTED      55891
payment      uk_payment_payment_key  RECORD     X,REC_NOT_GAP  GRANTED      's2-lock-probe', 55891
wallet       NULL                    TABLE      IX             GRANTED      NULL
wallet       NULL                    TABLE      IX             GRANTED      NULL
wallet       PRIMARY                 RECORD     X,REC_NOT_GAP  GRANTED      6
wallet       PRIMARY                 RECORD     X,REC_NOT_GAP  WAITING      6
```

`performance_schema.data_lock_waits` 의 대기 관계와 실제 대기 시간:

```
waiting_on      waiting_mode   waiting_data  blocking_mode
wallet.PRIMARY  X,REC_NOT_GAP  6             X,REC_NOT_GAP

charge_started  2026-09-22 23:23:15.077
lock_acquired   2026-09-22 23:24:07.153     (52.1 초 대기 - 승인이 커밋할 때까지)
```

- **승인은 `payment → wallet` 순서로 잠근다.** 한 트랜잭션이 payment 의 X 락(조건을 평가한 secondary unique index 와 갱신 대상인 clustered index 양쪽)과 wallet 의 X 락을 **함께 보유**한다. S1 이 남긴 전제가 여기서 확인되고, S4 의 데드락 논의는 이 순서 위에서 이뤄진다
- **충전은 wallet 에서만 기다린다.** payment 를 건드리지 않으므로 순환 대기가 생기지 않는다
- `REC_NOT_GAP` — 갭 락이 없다. unique 인덱스 동등 조건이고 대상 행이 존재한다. 갭 락은 S5 의 주제다
- 대기는 **승인이 커밋할 때까지** 계속된다. 이 캡처의 승인 세션은 `DO SLEEP(60)` 으로 트랜잭션을 길게 열어 둔 것이므로, 52초는 "트랜잭션이 열려 있는 동안 지갑이 잠긴다"는 사실의 예시이지 실제 경로의 측정값이 아니다
- **현재 코드에서 외부 호출은 지갑을 잠그지 않는다.** `PaymentSupport.approve` 는 CARD 면 카드사 호출만 하고 MONEY 면 지갑 차감만 한다. 그래서 카드 승인 호출 동안 붙들고 있는 것은 CAS 가 잡은 **payment 락**이고, 지갑 락은 MONEY 차감 구간에서만 잡힌다. 무엇을 얼마나 오래 잠근 채 기다리는지가 S8 의 주제다

관측은 로컬 컨테이너의 V1 스키마에서 했다. `version` 컬럼은 이 관측과 무관하다.

- **S4 — FK 락 승격 데드락.** 이번에 확인한 `payment → wallet` 선행 X 락이 그 데드락을 예방한다. S4 는 이 선행 잠금을 명시적으로 제거한 독립 비교 실험이다
- **S5 — 갭 락.** 이번 관측은 전부 `REC_NOT_GAP` 이었다. 범위 조건과 없는 행을 다루면 달라진다
- **S8 — 락 보유 시간.** 카드 승인은 CAS 가 잡은 payment 락을 붙든 채 외부 응답을 기다리고, MONEY 승인은 트랜잭션이 열려 있는 동안 지갑을 잠근다. 6.6 의 52초 대기는 후자가 길어지면 무엇이 막히는지 보여 준다 (그 캡처 자체는 수동 `SLEEP` 이다)
- **낙관적 락의 적용 조건.** 참가자 전원이 같은 엔티티를 지나야 보호가 성립한다. 지금은 실습 규약으로 고정했고, 본선으로 쓰려면 규약이 아니라 구조로 강제해야 한다
