# S4 — FK 락 승격 데드락: 원장 INSERT 도 지갑을 잠근다

> 상위 문서: [SCENARIO.md](../SCENARIO.md) · 계획: [plan/S4.md](../plan/S4.md) · 선행 기록: [phase1/S3.md](S3.md) · 이슈: #27

S1~S3 의 스키마에는 FK 가 없었다. 원장 INSERT 의 FK 검사 락이 차감 유실 관찰에 섞이지 않게 하려고 일부러 뺐다. 이번 실습은 `wallet_ledger.wallet_id → wallet.id` FK 를 처음 추가하고, **FK 검사도 부모 행을 잠근다**는 사실이 만드는 데드락을 재현한다. 그리고 S2 가 남긴 가정 — 본선의 wallet 선행 `FOR UPDATE` 가 이 데드락을 예방한다 — 을 확인한다.

## 1. 전제

| 항목 | 상태 |
|---|---|
| 스키마 | **V3** — `idx_wallet_ledger_wallet_id` + `fk_wallet_ledger_wallet`. 이 스키마의 첫 FK 이고 다른 FK 는 없다 |
| 과거 재현 | S1·S2·S2-a·S3 재현·비교는 **V2 DB** 에서 돈다 (1.1) |
| 격리 수준 | REPEATABLE READ |
| 구현 | S1~S3 누적 본선. 실패 구현은 wallet 선행 잠금을 뺀 **독립 비교 실험** |
| 트랜잭션 경계 | 승인 전체가 단일 트랜잭션 (분리는 S8) |
| 데드락 관련 서버 설정 | 기본값 — `innodb_deadlock_detect=ON`, `innodb_lock_wait_timeout=50`, `innodb_rollback_on_timeout=OFF` |

버전은 [phase0/README.md 1절](../phase0/README.md)과 같다 (MySQL 8.0.44, Hibernate 6.6.53, Spring Boot 3.5.16).

### 1.1 과거 재현을 V2 DB 로 옮겼다

SCENARIO 94행은 "과거 실패 재현은 전용 DB 를 해당 버전으로 초기화하고, 최신 스키마를 공유하지 않는다" 고 정했다. S2 의 V2(`wallet.version`)는 좁은 예외(additive·DEFAULT·미매핑 컬럼)로 넘어갔지만 V3 의 FK 는 아니다. 이번에 원칙을 처음 구현했다.

```
support
├── MySqlTestContainer      컨테이너 공용 홀더. 두 번째 DB 를 root 로 만든다
├── AbstractDatabaseTest    주입 도구 + 정리 규약 (공통)
├── AbstractIntegrationTest 최신 스키마 (@ServiceConnection)
└── AbstractV2SchemaTest    payment_v2 + flyway.target=2 (@DynamicPropertySource)
```

- `@ServiceConnection` 은 연결 정보를 프로퍼티보다 우선하므로 V2 베이스는 상속하지 않고 URL 을 직접 준다
- 두 베이스는 Spring 컨텍스트가 따로 뜬다. 게이트·Fake 카드사도 따로다
- `V2SchemaContextTest` 가 V2 컨텍스트가 정말 별도 DB(`payment_v2`)이고 V2 까지만 적용됐으며 FK 가 0건인지 지킨다. 배선이 조용히 최신 DB 로 붙으면 과거 재현은 green 인 채로 최신 스키마를 공유하게 된다

**FK 를 넣기 전에 옮겼다.** 옮긴 커밋에서는 V2 == 최신이라 결과가 같아야 했고, 실제로 같았다. 그다음 FK 를 넣었을 때 1.2 의 실패가 하나도 나오지 않았다. 순서를 거꾸로 하면 과거 재현이 빨개진 채로 커밋된다.

정리 규약(`DatabaseCleaner`)도 FK 에 맞췄다. 부모 테이블 TRUNCATE 는 자식이 비어 있어도 FK 가 있으면 실패한다. `FOREIGN_KEY_CHECKS` 는 세션 변수라 한 커넥션 안에서 끄고, 지우고, `finally` 에서 원래 값으로 복원한다. HikariCP 는 반환된 커넥션의 세션 변수를 되돌리지 않는다 — 검사가 꺼진 커넥션이 풀에 남으면 그 커넥션을 받은 S4 재현은 FK 락 없이 돌아 조용히 사라진다.

### 1.2 FK 하나로 과거 재현 5개가 바뀐다

계획 전에 임시 worktree 에서 FK 만 추가하고 전체 테스트를 돌렸다. **142개 중 6개 실패.**

| 실패 | 예외 |
|---|---|
| `WalletLostUpdateReproductionTest` 2건 (S2 naive 차감, 충전 경쟁) | `update wallet` 에서 `Deadlock found` |
| `DuplicateConfirmReproductionTest` MONEY (S1) | `update payment` 에서 `Deadlock found` |
| `OptimisticLockConcurrencyTest`, `LockContentionObservationTest` (S2-a) | `Deadlock found` — 버전 충돌 대신 |
| `SchemaConstraintTest.noForeignKeys` | 예상된 실패 |

naive 와 낙관적 락 전략은 `WalletLedger` 를 IDENTITY 로 **즉시 INSERT** 하고, 지갑 변경은 **커밋 시점 flush 의 UPDATE** 로 나간다. 코드에 쓴 순서(읽기 → 계산 → 원장)와 달리 SQL 순서가 "자식 INSERT → 부모 UPDATE" 다. **FK 를 넣는 순간 S2 의 Lost Update 재현이 데드락 재현으로 바뀐다** — 한쪽이 롤백되니 유실될 갱신 자체가 사라진다.

반대로 원자적·조건부 감산(`WalletDecrementComparisonTest`)은 green 이었다. `UPDATE wallet` 이 원장 INSERT 보다 먼저 나가 X 락을 선점하기 때문이다. 이 차이가 5.4 의 대조군이 됐다.

S1 MONEY 재현이 `payment` UPDATE 에서 데드락이 난 것은 같은 결제를 쓰기 때문이다. 순환에 payment 행이 함께 걸린다. 본 실험은 서로 다른 결제로 wallet 경쟁만 남겼고, 이 경우는 관찰로만 남긴다.

## 2. 재현

| # | 배선 | 동기화 | 워커 |
|---|---|---|---|
| 재현 1 | `ledgerFirstDebitConfirmer` — CAS + `LedgerFirstWalletBalanceUpdater` | `LEDGER_INSERTED` barrier | 2 |
| 재현 2 | `retryingLedgerFirstDebitConfirmer` — 위를 1213 한정 재시도로 감쌈 | 〃 | 2 |
| 대조 | `atomicDebitConfirmer` (S2 비교 1) | `WALLET_READ` barrier | 2 |

준비: 충전 100,000 → 같은 지갑의 MONEY 결제 P1(3,000), P2(3,000). 잔액이 충분하므로 잔액 부족이 섞이지 않는다. 결제가 서로 달라 payment 락은 겹치지 않는다.

`LedgerFirstWalletBalanceUpdater` 는 **명시적 순서**로 세 문장을 보낸다.

```
SELECT balance FROM wallet WHERE id = ?                 잠그지 않는다
INSERT INTO wallet_ledger ...                           FK 검사 → wallet S 락
UPDATE wallet SET balance = balance - ? WHERE id = ?     S → X 승격이 필요하다
```

감산이 **원자적**인 것이 요점이다. 읽은 값으로 계산한 절대값을 쓰면 Lost Update 가 섞여 실패 원인이 둘이 된다. 대조군인 원자적 감산 전략과 **같은 문장을 순서만 바꿔** 보낸다.

`LEDGER_INSERTED` 는 `WalletLedgerRepository.save` 반환 직후다. **락을 잡은 뒤에** 모으는 유일한 지점이다 — S 락끼리는 공존하므로 두 참가자가 모두 도착할 수 있다. X 락을 먼저 잡는 본선에 쓰면 두 번째 참가자가 도착하지 못한다.

## 3. 관찰

### 3.1 재현 1 — 한 건이 1213 으로 통째로 롤백된다

| 항목 | 값 |
|---|---|
| 요청 2건의 결과 | 성공 1, `CannotAcquireLockException` 1 — 원인 체인에 `SQLException` 1213 |
| 피해 결제 | **READY** — CAS 의 `IN_PROGRESS` 까지 함께 롤백 |
| PAY 원장 | 1건 — 피해자의 INSERT 도 롤백 |
| 잔액 | 97,000 == 원장 합계 |
| 불변식 1·2·3 | **유지** |

S1~S3 의 재현과 성격이 다르다. **정합성은 깨지지 않는다.** 데드락은 요청 하나가 실패하는 **가용성** 문제다. DB 가 피해자를 전체 롤백하므로 절반만 반영된 상태가 남지 않는다.

SQL 로그(재현 2 에서 캡처, 피해자는 thread-1):

```
thread-2  UPDATE payment SET status='IN_PROGRESS' WHERE payment_key=? AND status='READY'   ┐ 서로 다른 결제라
thread-1  UPDATE payment SET status='IN_PROGRESS' WHERE payment_key=? AND status='READY'   ┘ 막지 않는다
thread-1  SELECT balance FROM wallet WHERE id = ?
thread-2  SELECT balance FROM wallet WHERE id = ?
thread-1  insert into wallet_ledger ...                          ┐ FK 검사 S 락 두 개
thread-2  insert into wallet_ledger ...                          ┘ ── LEDGER_INSERTED ──
thread-2  UPDATE wallet SET balance = balance - ? WHERE id = ?   ┐ 승격 경쟁 → thread-1 이 피해자
thread-1  UPDATE wallet SET balance = balance - ? WHERE id = ?   ┘
thread-2  update payment set ... status=DONE                     커밋
thread-1  UPDATE payment SET status='IN_PROGRESS' ...            ← 재시도: CAS 부터 새 트랜잭션
thread-1  SELECT balance / insert into wallet_ledger / UPDATE wallet / update payment
```

### 3.2 락 캡처 — S 두 개가 공존하고, X 승격이 서로를 기다린다

로컬 docker-compose MySQL(임시 DB 에 V1~V3 적용)에 `root` 로 붙어 세 세션으로 재연했다. 두 세션이 원장 INSERT → `DO SLEEP` → `UPDATE wallet` 순서로 돌고, 세 번째 세션이 `performance_schema` 를 캡처했다.

**두 INSERT 뒤 (barrier 시점)**

```
trx     obj            idx      type    mode           status   data
169969  wallet         NULL     TABLE   IS             GRANTED  NULL
169969  wallet         PRIMARY  RECORD  S,REC_NOT_GAP  GRANTED  1
169969  wallet_ledger  NULL     TABLE   IX             GRANTED  NULL
169974  wallet         NULL     TABLE   IS             GRANTED  NULL
169974  wallet         PRIMARY  RECORD  S,REC_NOT_GAP  GRANTED  1
169974  wallet_ledger  NULL     TABLE   IX             GRANTED  NULL
```

- 원장 INSERT 가 **wallet 에** 락을 건다. 테이블에는 `IS`(의도 공유), 부모 PK 레코드에는 `S,REC_NOT_GAP`
- 두 트랜잭션의 S 가 **둘 다 GRANTED** — S 끼리는 공존한다. 여기까지는 아무도 막히지 않는다

**T1 의 UPDATE 가 기다리는 동안**

```
trx     obj     idx      type    mode           status
169969  wallet  PRIMARY  RECORD  S,REC_NOT_GAP  GRANTED
169969  wallet  PRIMARY  RECORD  X,REC_NOT_GAP  WAITING   ← 승격 요청
169974  wallet  PRIMARY  RECORD  S,REC_NOT_GAP  GRANTED

waiting_on      waiting_mode   blocking_mode  blocking_trx  waiting_trx
wallet.PRIMARY  X,REC_NOT_GAP  S,REC_NOT_GAP  169974        169969
```

T1 은 자기 S 를 쥔 채 X 를 요청하고, T2 의 S 에 막힌다. 아직 순환은 아니다 — T2 가 UPDATE 를 보내는 순간 순환이 닫힌다.

**`SHOW ENGINE INNODB STATUS` — LATEST DETECTED DEADLOCK**

```
*** (1) TRANSACTION: TRANSACTION 169969 ... UPDATE wallet SET balance = balance - 3000 WHERE id = 1
*** (1) HOLDS THE LOCK(S):             index PRIMARY of table `s4_obs`.`wallet` ... lock mode S locks rec but not gap
*** (1) WAITING FOR THIS LOCK TO BE GRANTED: index PRIMARY ... lock_mode X locks rec but not gap waiting
*** (2) TRANSACTION: TRANSACTION 169974 ... UPDATE wallet SET balance = balance - 3000 WHERE id = 1
*** (2) HOLDS THE LOCK(S):             index PRIMARY ... lock mode S locks rec but not gap
*** (2) WAITING FOR THIS LOCK TO BE GRANTED: index PRIMARY ... lock_mode X locks rec but not gap waiting
*** WE ROLL BACK TRANSACTION (2)
```

같은 행의 같은 모드 쌍이 서로를 기다린다. 두 트랜잭션 모두 `undo log entries 1` — 원장 한 줄씩 쓴 상태다. 순환을 닫은 T2 의 UPDATE 발행(`00.627`) 1ms 뒤에 T1 의 UPDATE 가 끝났다(`00.628`). 감지는 타임아웃을 기다리지 않는다. 결과 잔액 97,000 == 원장 합계.

### 3.3 재현 2 — 피해자를 새 트랜잭션에서 다시 하면 둘 다 성공한다

| 항목 | 값 |
|---|---|
| 요청 2건의 결과 | 둘 다 성공 |
| 데드락 / 재시도 / 상한 초과 | 1 / 1 / 0 |
| PAY 원장 | 2건 — 재시도가 원장을 중복시키지 않는다 |
| 잔액 | 94,000 == 원장 합계 |

**피해자의 재시도는 다시 순환을 만들지 않는다.** 재시도는 승자가 X 락을 쥔 동안 원장 INSERT 의 S 락에서 기다렸다가, 승자가 커밋한 뒤 진행한다. 3.1 의 로그에서 thread-1 의 재시도는 thread-2 의 커밋 뒤에 시작한다. 게이트는 스레드당 한 번만 막으므로 재시도의 두 번째 INSERT 는 barrier 를 그냥 지나간다.

**전체 롤백이라 재시도가 성립한다.** 피해자의 CAS(`IN_PROGRESS`)도 롤백되므로 재시도는 READY 를 보고 CAS 를 다시 통과한다. S1 이 승인을 단일 트랜잭션으로 둔 효과가 S2-a 에 이어 다시 나타났다.

### 3.4 대조 — 같은 문장을 UPDATE → INSERT 순서로 보내면 데드락이 없다

원자적 감산 전략(S2 비교 1)은 잠그지 않는 조회 → `UPDATE wallet` → 원장 INSERT 다. 같은 두 결제를 `WALLET_READ` 로 맞춰 출발시키면 **성공 2, 데드락 0, 잔액 94,000.** 먼저 나간 UPDATE 가 X 를 잡고, 두 번째 UPDATE 는 그 X 에서 기다린다. 원장 INSERT 의 FK 검사는 자기가 이미 쥔 X 안에서 일어난다.

**문장은 같고 순서만 다르다.** FK 락 승격 데드락의 원인은 "원장을 쓴다" 가 아니라 "부모를 잠그기 전에 자식을 쓴다" 다.

## 4. 원인

- **FK 검사도 락을 잡는다.** 자식 INSERT 는 참조하는 부모 행에 S 락을 걸고 트랜잭션 끝까지 유지한다
- **S 는 공존하고 X 는 배타적이다.** 같은 부모를 참조하는 자식 INSERT 둘은 서로 막지 않지만, 둘 다 부모를 UPDATE 하려는 순간 각자 상대의 S 에 막힌다
- **코드 순서가 아니라 SQL 순서다.** naive·낙관적 전략은 코드상 "읽고 → 계산하고 → 원장" 이지만, IDENTITY 원장이 즉시 INSERT 되고 엔티티 변경은 flush 에 나가 SQL 은 "INSERT → UPDATE" 가 된다 (1.2)

격리 수준과 무관하다. RC 에서도 FK 검사의 공유 락은 그대로다 (SCENARIO 206행, S7 에서 다룬다).

## 5. 개선

SCENARIO 168행대로 **ledger INSERT 전에 wallet 을 `FOR UPDATE` 로 잠근다.** 새로 만든 것은 없다 — S2-b 의 본선(`PessimisticLockWalletBalanceUpdater`)이 이미 그렇다. S4 는 그것을 확인했다.

### 5.1 본선의 락 — X 하나만 보인다

같은 재연을 본선 순서(`SELECT ... FOR UPDATE` → INSERT → UPDATE)로 돌렸다. 새 DB 가 아니라 3.2 의 데드락 재연을 마친 같은 DB 에서 이어 돌렸으므로 **시작 잔액은 97,000** 이다 (100,000 에서 데드락 승자의 3,000 이 커밋된 값). T1 이 커밋 전에 머무는 동안:

```
trx     obj            idx      type    mode           status
169976  wallet         NULL     TABLE   IX             GRANTED
169976  wallet         PRIMARY  RECORD  X,REC_NOT_GAP  GRANTED
169976  wallet_ledger  NULL     TABLE   IX             GRANTED
169981  wallet         NULL     TABLE   IX             GRANTED
169981  wallet         PRIMARY  RECORD  X,REC_NOT_GAP  WAITING
```

- T1 의 원장 INSERT 는 wallet 에 **S 락 행을 따로 만들지 않았다.** 이미 X 를 쥐고 있어 FK 검사가 그 안에서 끝난다 (3.2 에는 `IS` + `S` 가 있었다)
- 두 번째 트랜잭션은 **첫 문장**(`FOR UPDATE`)에서 기다린다. 원장을 쓰기 전이라 S 를 쥐고 있지 않으므로 순환이 생길 수 없다
- 두 번째는 1.69초 기다린 뒤(T1 커밋까지) 잠금 조회로 **94,000** 을 읽었다 — 시작 97,000 에서 T1 의 차감이 커밋된 값이다. 잠금 읽기는 최신 커밋 값을 읽는다 (phase1/S3.md 5.2). 자기 차감 후 최종 잔액은 **91,000 == 원장 합계**

### 5.2 원장을 쓰는 모든 경로

SCENARIO 168행 "모든 MONEY 변경 경로를 점검한다" 를 호출처 전수로 확인했다. `wallet_ledger` 를 쓰는 곳은 `WalletBalanceUpdater` 구현체뿐이다 (시드는 원장을 쓰지 않는다).

| 구현 | 경로 | 원장 INSERT 전에 wallet X 락? | 쓰는 곳 |
|---|---|---|---|
| `PessimisticLockWalletBalanceUpdater` | 차감·충전·환불 | **예** — 세 경로 모두 `lock(walletId)` 뒤 | **본선** 승인·충전·취소 |
| `AtomicDecrementWalletBalanceUpdater` | 차감 | 예 — `UPDATE wallet` 이 먼저 | S2 비교 1 |
| `GuardedDecrementWalletBalanceUpdater` | 차감 | 예 — 조건부 `UPDATE wallet` 이 먼저 | S2 비교 2 |
| `NaiveWalletBalanceUpdater` | 차감·충전·환불 | 아니오 — UPDATE 는 flush 때 | S1·S2·S3 재현 (V2) |
| `OptimisticLockWalletBalanceUpdater` | 차감 | 아니오 — 버전 UPDATE 는 flush 때 | S2-a (V2) |
| `LedgerFirstWalletBalanceUpdater` | 차감 | **아니오 — 의도적** | S4 재현 |

본선 배선은 `ConcurrencyStrategyConfig` 한곳에서 읽힌다 — 승인·충전·취소가 모두 `PessimisticLockWalletBalanceUpdater` 다. "아니오" 인 구현은 전부 재현 전용이고, FK 가 없는 V2 DB 에서 돌거나(naive·낙관적) FK 데드락 자체가 목적이다(ledger-first).

### 5.3 데드락 감지와 락 대기 타임아웃

| | 데드락 (1213) | 락 대기 타임아웃 (1205) |
|---|---|---|
| 판단 | 대기 그래프에 순환이 생기는 즉시 | `innodb_lock_wait_timeout` 경과 |
| DB 의 롤백 범위 | 피해 트랜잭션 **전체** | 기본 설정에서 **마지막 문장만** |
| 이번 재시도 정책 | 재시도한다 | 재시도하지 않는다 |

**관찰 경로를 나눴다.** DB 가 되돌리는 범위는 DB 의 동작이고, 호출자가 받는 예외 타입은 프레임워크의 변환 결과다. 예외가 `@Transactional` 경계 밖으로 전파된 뒤에는 Spring 이 트랜잭션 전체를 롤백하므로 DB 의 문장 단위 롤백 상태를 관찰할 수 없다. 그래서 DB 동작은 직접 관리하는 JDBC 트랜잭션에서, 예외 타입은 Spring 관리 트랜잭션에서 봤다 (`LockWaitTimeoutObservationTest`).

**측정값**

| 관찰 | 측정 구간 | 결과 |
|---|---|---|
| 데드락 감지 (재현 1, JUnit) | `LEDGER_INSERTED` barrier 해제(barrier action 의 `nanoTime`) → 피해 워커의 예외 수신 | **2 ms** (5회 모두) |
| 데드락 감지 (로컬 재연) | 순환을 닫은 UPDATE 발행 → 대기하던 UPDATE 완료 (`NOW(3)`) | 1 ms |
| 1205 (JDBC, 세션 타임아웃 1초) | 잠금 문장 발행 직전 → `SQLException` 수신 | 1,014 ms |
| 1205 (JPA, 세션 타임아웃 1초) | 트랜잭션 시작 → 예외 수신 | 1,023 ~ 1,079 ms |

재현 1 의 2ms 는 **순수 데드락 감지 시간이 아니다.** barrier 해제부터 두 UPDATE 발행, 감지, 롤백, 예외 전달, 스레드 스케줄링까지 모두 포함한 상한이다. 현재 테스트 장치로는 두 번째 UPDATE 의 발행 시각을 직접 측정하지 않는다 (어느 쪽이 두 번째인지도 정해져 있지 않다). 판정은 "타임아웃(50초)과 자릿수가 다르다" 까지다.

**1205 는 문장만 롤백한다 (JDBC).** 대기 세션이 먼저 다른 지갑을 `+1` 갱신한 뒤 잠긴 행을 잠그려다 1205 를 받았다. 같은 커넥션으로 다시 읽으니 `+1` 이 남아 있었다 — 트랜잭션은 열린 채 돌아왔다. 전제인 `innodb_rollback_on_timeout=OFF` 도 테스트가 확인한다.

**예외 타입은 번역 경로가 정한다.**

| 에러 | 경로 | 호출자가 받는 타입 |
|---|---|---|
| 1213 | JPA (Hibernate 의 예외 변환을 거친다) | `CannotAcquireLockException` |
| 1205 | JPA | `PessimisticLockingFailureException` |
| 1205 | `JdbcTemplate` (Spring 의 SQL 에러 코드 변환) | `CannotAcquireLockException` |

같은 JPA 경로 안에서는 1213 과 1205 의 타입이 다르다. 그러나 `JdbcTemplate` 경로의 1205 는 JPA 경로의 1213 과 **같은 타입**이다. 그리고 `CannotAcquireLockException` 은 `PessimisticLockingFailureException` 의 하위 타입이라, 부모 타입으로 잡으면 모두 걸린다. 계획(plan/S4.md 1.1)은 "타입으로 구분할 수 없다고 보고" 에러 코드를 쓰기로 했다. 측정은 이 결정을 더 정확한 형태로 뒷받침한다 — **타입 구분은 번역 경로에 따라 달라지므로 판정 기준으로 삼을 수 없다.** `MySqlLockErrors` 는 원인 체인을 끝까지 따라가 `SQLException.getErrorCode()` 를 본다.

**`innodb_deadlock_detect = OFF` (로컬 수동, 세션 타임아웃 3초)**

재현 1 과 같은 두 세션을 돌렸더니 순환이 감지되지 않고 **두 세션 모두 1205** 로 끝났다. 감지가 켜져 있으면 한쪽만 롤백되고 다른 쪽은 성공한다. 꺼져 있으면 먼저 타임아웃된 쪽도 문장만 롤백되고 **S 락을 쥔 채** 트랜잭션이 살아 있으므로, 상대도 자기 타임아웃까지 풀려나지 못한다. 전역 변수라 공유 테스트 컨테이너에서는 바꾸지 않았고, 확인 후 `ON` 으로 되돌렸다.

### 5.4 재시도 정책

`RetryingPaymentConfirmer` 가 재시도할 실패를 생성자 인자로 받는다. S2-a 배선은 `OPTIMISTIC_CONFLICT`, S4 실패 배선은 `DEADLOCK`(원인 체인의 1213) 이다.

- **실패 배선에만 씌웠다.** 이 실험이 확인하는 것은 본선의 wallet 선행 잠금이 **S4 의 FK 락 승격 데드락을 예방한다**는 것이다. 본선에 방어적 재시도를 씌우면 예방 여부가 재시도에 가려진다. 본선에 다른 데드락이 없다는 증명은 아니다 (8절)
- **1205 는 재시도하지 않는다 — 이번 실험의 정책 선택이다.** 상대가 락을 오래 보유하고 있다는 신호라, 보유자가 끝나면 재시도가 성공할 수도 있지만 대기열을 늘릴 수도 있다. 성공 재현만으로는 이 정책을 검증할 수 없으므로 `RetryPolicyTest` 에 사례를 더했다 — 중첩된 1213 은 재시도, 1205 는 호출 1회·재시도 0회, 두 조건은 서로의 실패를 재시도하지 않는다

### 5.5 데드락 로그

`innodb_print_all_deadlocks = ON` 이면 기본 `log_error_verbosity = 2` 에서도 트랜잭션·락 상세(`TRANSACTION ...`, `RECORD LOCKS ... lock mode S locks rec but not gap` 등)는 stderr 로 직접 출력되어 에러 로그에 남는다. 빠지는 것은 정보(Note) 수준으로 쓰는 제목 `[MY-012468] Transactions deadlock detected, dumping detailed information.` 과 결론 `[MY-012469] *** WE ROLL BACK TRANSACTION (n)` 이다 ([MySQL Bug #112117](https://bugs.mysql.com/bug.php?id=112117)). **제목과 롤백 대상까지 온전히 기록하기 위해 `log_error_verbosity = 3` 으로 설정한다.**

처음에는 verbosity 2 의 로그를 `grep -i deadlock` 으로만 찾아 "아무것도 남지 않는다" 고 잘못 판단했다. 그 단어가 들어간 줄이 바로 빠지는 제목 줄이다. 같은 시각의 로그를 다시 보니 상세는 남아 있었다. `docker/mysql/conf.d/s4.cnf` 에 두 값을 넣었다 — 컨테이너를 재시작해야 적용된다. 관측 중에는 `SET GLOBAL` 로 켰다가 기본값으로 되돌렸다.

## 8. 다음 단계에 남기는 것

- **FK 와 wallet 선행 잠금은 본선에 유지한다** (SCENARIO 171행). 원장을 쓰는 새 경로는 반드시 wallet 을 먼저 잠근다. 5.2 의 표가 점검 목록이다
- **롤백된 트랜잭션의 재시도 ≠ 커밋 후 재전송.** 데드락 재시도는 DB 가 이미 전부 되돌린 요청을 다시 하는 것이라 안전하다. S5 는 커밋까지 끝났는데 응답만 잃은 요청의 재전송이라, 같은 재시도가 **중복**을 만든다
- **예방한 것은 FK 락 승격 데드락 하나다.** S5 의 멱등키 테이블은 없는 키를 잠글 때 갭 락 데드락을 만든다 — 같은 1213 이지만 원인이 다르다. `MySqlLockErrors` 와 재시도 조건은 거기서 다시 쓸 수 있다
- **V2 컨텍스트의 수명.** S5 에서 멱등키 엔티티가 생기면 `ddl-auto: validate` 가 V2 컨텍스트 기동을 막는다. 과거 컨텍스트는 `validate` 를 끄거나 엔티티 스캔을 좁혀야 한다 — S5 계획에서 정한다. S6·S7 의 "인덱스 없는 스키마" 복원도 같은 장치(버전별 데이터베이스 + Flyway `target`)를 쓴다
- **1205 는 (기본 설정에서) DB 수준으로는 문장만 롤백한다.** S8 에서 외부 호출 동안 락을 오래 쥐면 이 타임아웃을 실제로 만난다. 그때 재시도 여부를 다시 정한다
